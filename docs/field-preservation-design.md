# 保留明确工作，分别处理日期和承接疑点

2026-11-15。用户明确要求不能因日期缺口直接取消任务，并授权针对已发现的问题调研、制定修改计划和检验。沿用 Python/SQLite、本地模拟器及 context-v1；默认 split-v3 不变。

## 调研依据与取舍

- [Purver 等：Detecting and Summarizing Action Items in Multi-Party Dialogue](https://www.eecs.qmul.ac.uk/~mpurver/papers/purver-et-al07sigdial.pdf)从会议子对话及发言作用分析行动项，支持分别判断工作、执行者和承诺；本项目不采用关键词直接判承诺。
- [TimeML 标注指南](https://timeml.github.io/site/publications/timeMLdocs/annguide_1.1.pdf)区分事件、时间表达与时间关系。由此借鉴“任务在下次会议之前”可先保留，不需要先填出 ISO 日期；这不是引入整个 TimeML 格式。
- [SOM-DST](https://aclanthology.org/2020.acl-main.53/)以字段操作控制更新；本项目采用字段疑点只限制对应操作的原则，不替换现有模型。
- [Clarify When Necessary](https://aclanthology.org/2025.findings-naacl.306/)将是否需要澄清与如何提问分开。本项目把缺少可选日期与真实冲突分别处理。

只改提示成本低，但不能消除程序硬阻断；全面重建语义图范围过大，现有失败尚不足以证明所有抽象都必需。本轮选择 context 专用字段处理、定向提示纠偏及限定修正实验。自动修正生产流程先不接入，避免核验同一阶段既改写又自我批准。

## 本轮行为契约

1. 新工作、内容/状态/关系受支持，已经表达相对期限但无法换算时，保留 due_text，due_date=null。若记录核验无时间问题、时间字段也支持该期限，则清除多余日期缺口；不追问日历日期，不取消任务。
2. 明确工作没有期限也是合法情况。若解释仍留下时间缺口，保留候选和原确认问题，日期不写入；不能从一个笼统缺口猜测它只是可选日期还是冲突。
3. 已确认存在工作的前提下，时间尚未决定或存在待确认时间，不执行该日期，仍保留候选。时间核验否定了描述里的时间、导致描述真实性受疑时，继续保留可见确认记录，不把可疑标题当作已核实事实。
4. accepted/self_committed/assigned 的承接核验不足或矛盾，不自动创建，保留内容有依据的候选并询问承接。suggested/conditional/declined/unknown 不借此提升为分派；原事件与核验保持不变，程序只决定输出方式。
5. 内容、指代、范围或旧任务关系真实存疑时仍保留待确认，不假装工作已经完整。隐式目的仍需确认，不能通过移除日期问题制造一个“看看某物”的不完整正式任务。
6. 旧任务明确改期、取消期限、进度汇报的行为不变；缺日期或未确认的旧任务改期仍不覆盖旧期限。权限、账号与受众校验不变。

## 提示与限定修正实验

解释提示明确新任务的相对期限可保留，旧任务具体日期更新才要求可执行的值；核验应指出真正冲突，不把 date=null 当成内容失败。承接按发言者、回应对象、当时已明确范围判断，“可以”既不自动判承诺，也不一概判建议。研究目的需要从背景推断时保留完整假设及具体问题。

限定修正实验以原话、原账本、被指出的问题为输入，仅请求重新解释指定记录；结果再走独立核验。验证旧 C03 的 UI 分类问题，同时检查邮件通知、未知材料和建议不会被补成新任务。此实验不写入正式任务、不计作生产修复，也不通过反复重采样选最好结果。

## 验证与边界

保存源码 before/final 快照。程序测试从 Service 入口检查创建或候选、日期原文保留、确认卡以及存储结果；使用旧失败响应做零模型机制对照。新增真实模型正反例在调用前冻结，另跑原六难例、完整分工窗口及 M1/M2。原语义标签不改，任务分数与候选保留/问题必要性分别报告。旧37份 evidence结果保持。首次失败与最多一次结构恢复分开记账。

下一场会议的日程检索与稳定事件绑定尚未实现；本轮只保留原文相对约束，不推测具体日期。多次矛盾更新、任务标题中旧日期仍是既有边界。
