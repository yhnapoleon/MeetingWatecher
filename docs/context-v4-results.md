# context-v4 实施与检验结果：失败实验

2026-11-16 归档结论：**本轮作为失败经验保留。** 目标是改善最终任务产物，结构版未优于低成本 A 对照，QA 扩展进一步退化；不因程序测试通过而记为修复成功。当前最好方案的分口径说明、接手入口和下一步见[最新交接](HANDOVER.md)。下面保留 2026-11-15 的原实验结果；本次归档未新增模型调用或修改评分。

2026-11-15。**已实现可选 context-v4 和独立 QA 实验，但没有证明整体修复有效，不晋级默认策略。** 在相同冻结上游、每例三轮的八例小集上，最终来源语义通过数为：仅补提示 A 18/24、结构版 B 17/24、结构加 QA 的 C 14/24。C23 原例三组均为 0/3。程序约束可以减少某些结构错误，不能替代工作边界和目的关系的语义判断。

## 1. 实际实施

| 改动 | 已实现行为 |
| --- | --- |
| 覆盖输出分离 | `new_work_findings` 不含旧记录关联字段；同一记录缺内容进入 `missing_details`；无法确定关系单独保留。程序派生旧内部 relation |
| 绑定局部修正 | 程序生成固定 target 槽位、源版本摘要和新增工作身份；模型只填写语义内容。未知槽位、额外身份字段、旧 scope 被拒绝 |
| 修正再核验 | 重建完整 record/event 后复用现有证据、分类、时间、授权和遗漏处置校验。只读记录不进入可写槽位；新增 finding 仍需得到完整处置 |
| 可选正常入口 | Extractor、Service、回放 CLI 支持 `context-v4`，默认 `split-v3` 不变；原 v1-v3 核心行为代码未修改 |
| 独立 QA 实验 | 原文生成必要信息问题；回答阶段只看问题与 work 描述；核验比较来源要求与描述答案，将遗漏派生为修正输入。QA 不默认启用 |

代码为 `meeting_eval/context_protocol_v4.py`、`context_v4.py`、`context_content_qa.py` 和四份 v4 提示。设计依据见[调研建议](context-v3-remediation-research.md)，步骤与接口见[实施计划](superpowers/plans/2026-11-15-context-v4-implementation.md)。

独立审查复现了三个 QA 接口缺陷：整项遗漏无法绑定 finding、局部再核验重开只读记录问题、背景记录被用来证明任务完整。已分别改为记录/finding 引用、保留首次问题绑定并限定再核验范围、仅向回答阶段提供 work 描述。真实首批还暴露修正接口只给示例、没有完整枚举的问题，现已提供完整动态 schema。上述问题均有失败到通过的回归证据，详见[审查与修复记录](../runs/2026-11-15-context-v4/code-review.json)。最终程序回归 **198/198**。

## 2. 同口径小集比较

八例为：M2、明确落实正例、同段第二工作、故意漏掉第二工作的版本、C23 原文、C23 改写、明确补问目的、信号问题已解决且会后只谈报名的反例。原例复用既有上游输出；三条新增 C23 对照先各运行一次相同 v3 跟踪/解释，再冻结供各组使用。A/B/C 都从这些相同状态开始，只运行核验及最多一次语义修正。因此这里比较的是核验和修正阶段，不是端到端分数。

| 最终对照组 | 可观察契约 | 加入来源语义复核 | 调用定位 |
| --- | ---: | ---: | --- |
| A：补齐覆盖规则与共同决定/实施边界说明 | 21/24 | **18/24** | `small-v1/A-r*`；此后 A 未修改，复用其首次结果 |
| B：A 的任务边界说明 + 分离覆盖结构、绑定修正槽位 | 20/24 | **17/24** | 审查修复后 `small-v2/B-r*` |
| C：B + 来源问题与描述独立回答 | 17/24 | **14/24** | 审查修复后 `small-v2/C-r*` |

首批未修复版本也完整保留：B 来源语义 16/24，C 17/24。不能只报审查后的单测通过；C 的代码缺陷修复后，模型又持续给出与合法工作答案范围冲突的 covered 判定，最终整体分数反而下降。各轮没有自动恢复或追加抽样挑成功。A 与 B 的接口及对应说明一起变化，不能将分差全部归因于某个字段。

| 隔离 M2 | 3/3 | 2/3 | 2/3 | B 一轮仍将范围决定变成需要负责人/承接的工作；C 一轮修正 JSON 解析失败 |

| 故意遗漏同段第二工作 | 0/3 | 0/3 | 0/3 | B 没发现遗漏；C 能提出真实新增工作，但范围问题的 covered 冲突阻断整轮 |

## 3. 仍然存在的系统问题

**工作资格判断在不同步骤之间仍不一致。** M2 的范围决定有时在解释中为 context_only，核验又将其当作落实动作。绑定身份让修正结构有效，却不能保证修正方向正确。最终 B 的失败已从结构拒绝转为合法结构中的错误任务提问。

**核验仍可能沿用已有记录，遗漏原文中的第二项工作。** 在故意漏掉“陈可今天下班前把测试结果发给客服”的输入中，最终 B 三轮均未提出 `new_work_findings`，程序没有足够的语义依据自行补出该工作。这是覆盖发现本身的失败，不是发现已经产生却被修正接口丢失。

**QA 的两个判断阶段会共享或引入语义错误。** C 的 source_requirements 把范围决定也提成工作要求。回答阶段正确地只看 work 描述，无法回答范围背景；核验却看到了完整上下文并把 R2 背景判 covered，程序因此拒绝冲突。放开这项检查会重新允许背景代替任务完整性，不能以减少报错为由放开。

**C23 的必要目的没有被来源问题阶段识别出来。** 原始 C23 的 source_requirements 仍输出空数组，后续没有问题可用于发现遗漏。将核验拆成独立阶段，没有自动形成更可靠的目的判断。原始口语对目的有上下文推断空间；保持原冻结标签，没有通过改标签提高分数。

另外核对了完整原始会议：选段前两句是“由于刚才我信号稍微不太好，没有完全听全”和“所以我从刚才我听到的……两个角度”。来源位置为 `data/mvp-v1/raw/vcsum_overall_context.txt`，id=216，context[54][5:9]。在相同冻结任务上，补入这两句做 C 组三轮来源窗口探针，最终仍没有修正目的关系，**0/3**。该结果表明此次单纯扩大相邻窗口未奏效，不证明上下文范围对所有病例都无关；探针分数不计入原八例。

## 4. 正常入口回放与验收补充

通过正常 Service 入口完成原始 M1→M2 和明确落实正例各两轮。M2 的同 GUID 完成、期限保留、范围决定替代均通过，落实正例均创建唯一陈可灰度配置/发测试工作；权限、历史、重复处理及重启检查通过。

但是，旧回放验收没有检查 M1 是否留下解释争议。本轮补上两场会议各自的解释争议、修正失败与提取错误检查后，结果如下：

| 回放 | 旧契约 | 补充完整流程检查 | 残留 |
| --- | --- | --- | --- |
| 原始跨会第 1 轮 | 通过 | 通过 | 无本轮检出的残留 |
| 原始跨会第 2 轮 | 通过 | 失败 | M1 监控面板记录的修正再核验输出非法 gap 字段，保留解释争议 |
| 明确落实第 1 轮 | 通过 | 失败 | M1 监控面板记录修正仍为需提问类型却未提供问题，保留解释争议 |
| 明确落实第 2 轮 | 通过 | 通过 | 无本轮检出的残留 |

因此，M2 目标契约四次通过，**完整流程仅 2/4 无上述残留**。不能把旧验收的 4/4 当作整体已修复。新增检查已进入本轮 runner，原检查结果另存 `original_contract_passed`。

明确落实第 1 轮的回放实际完成后，评估脚本因缺 `m2-input.json` 产物报错。补存当时实际使用的同一 `positive_meeting()` 输入后，对已有输出离线重评，没有重跑模型；原异常日志保留，后续 runner 已在运行前保存输入。

本轮共 **262 次真实模型调用、1,152,910 tokens**，262 次均收到响应，无网络失败；包含固定输入准备、首批与修复后比较、窗口探针及四次完整回放，零模型恢复调用。模型 JSON 解析/结构失败仍计入失败。平台写入均为本地 SQLite 模拟。统计见[总汇总](../runs/2026-11-15-context-v4/summary.json)。

## 5. 当前使用决定

保留结构版作为可选实验入口，QA 保留独立实验子类。默认策略不变；小集未过门槛，不扩大到完整 30 语料/33 对照/10 行为/13 更新回归。

后续优先检验“独立发现原文中的工作，再与已有记录对齐”的覆盖发现机制，并统一范围决定与实施动作的判定权。C23 应单独比较来源关系识别能力和标签解释边界。此次结果不支持继续增加同模型核验步骤，也不支持用更多重试弥补问题。

复现入口为 `experiments/task-boundary/run_context_v4.py`。运行目录必须使用新名称；`--mode small` 使用冻结上游，`--mode cross/positive` 使用正常 Service 入口。所有调用记录、首次失败、源码快照、测试日志和审查证据位于 [本轮产物](../runs/2026-11-15-context-v4/)。
