# 前置能力修复：工作边界、局部缺口、问题关闭

2026-11-14。本轮按用户确认的顺序完成调研、设计和第一批修复。当前实验版可以在已验证样例中把明确工作与相邻模糊内容分开，保留未承接的完整分工，并关闭后文已经回答的问题。**仍未达到默认切换条件：短片段 UI 分工、研究目的确认和模型输出结构仍有失败。** 默认保持 `split-v3`。

原来的 C20 把“剪辑视频，给大家确认”和“还有文稿”合成一项工作，文稿动作未知导致视频也被拦住。修复后，视频独立成为候选，只问具体负责人；文稿单独询问处理动作。这是本轮工作边界修复的直接检验。

## 调研与设计

[事件共指研究](https://aclanthology.org/Q15-1037/)按动作、参与者及语境识别同一事件，支持“相同名词或共用引文不代表同一项工作”。[行动项对话研究](https://aclanthology.org/2007.sigdial-1.4/)区分提出、讨论、分派与承诺，支持内容与承接分别判断。[SOM-DST](https://aclanthology.org/2020.acl-main.53/)通过保留、删除和更新操作维护字段状态；本轮借鉴局部更新，未引入它的训练模型。[必要时澄清](https://aclanthology.org/2025.findings-naacl.306/)提供评估澄清负担的依据，故把已回答还追问、约束误拆为任务列入新准则。

选择在现有流程内修复，没有新增模型阶段。方案及取舍见[设计文档](action-context-prerequisites-design.md)，具体步骤见[实施计划](superpowers/plans/2026-11-14-context-prerequisites.md)。

## 改了什么

**先分工作，再补缺口。** 跟踪与解释按可独立决定/执行的动作、对象、角色和场景划分工作。明确动作旁的未知材料单独保留，同一工作的目的和约束则附在原工作上。“内容可能较长”不再自动成为必须确认的范围；“两份结果分别保存”不再默认拆成另一项待分配工作。明确介绍或反复指代的无动作对象也保存在实体账本。

**核验指出具体失败字段。** 非支持的记录核验必须带 `issues`。只有负责人、承接或问题表述有疑问时，不再把已受支持的工作描述一起判成假设；执行规则仍阻止未经确认的自动创建。真正的内容、范围、时间或旧任务关系问题继续阻断。核验 assigned 时检查“是否确有分派”，不把“本人是否接受”作为分派成立的前提。

**已回答的问题有关闭出口。** 新增 `resolved`，用于会上已经解决的核对或选择；`withdrawn` 继续表示取消。旧任务完成仍使用原来的事件更新机制。已被记录涵盖的核验分歧只挂在该记录上，不重复生成遗漏原话卡；不同工作共享引用时仍分别保留。

独立代码审查发现两个缺口并完成修复：关闭类记录如果还挂着一个有效事件，过去会静默丢掉事件，现在明确拒绝这种矛盾输出；已是候选但负责人被质疑时，过去仍展示具体人，现在也清除未经支持的归属。正常 Service 入口测试同时验证了反例：关闭记录和明确工作分开，即使共用原话，明确工作仍可创建。

源码主要在 [context_state.py](../meeting_eval/context_state.py)、[context_pipeline.py](../meeting_eval/context_pipeline.py) 和三阶段 `*-context-v1.txt` 提示中。`task_events.py` 的旧证据流程规则未变。协议版本升至 3，防止新旧解析结果混用。

## 如何检验

旧 v2 语义标签保持不变。新[前置能力契约](../experiments/action-context/prerequisites-contract.json)在既有准则上增加工作互不阻断、关闭已回答核对、约束不另建任务、无重复确认等要求，共 15 例、48 条。另冻结两个[取消反例](../data/context-prerequisites-v1/manifest.json)，检查取消后的通知工作以及另一场活动的同名工作是否保留。

既有难例和连续窗口由独立代理逐项复核；合成与取消反例由本会话逐项核对原文、输出与历史，CP06 的确认问题另由独立代理复核口径。所有复核绑定输入、预测及契约哈希。标注均为代理标注/复核，不是人工金标准，也不是新会议系列盲测。

程序测试采用失败用例→修复→通过：最终 101 项通过，包含正常 Extractor→ContextPipeline→Service 路径的冲突校验。原有权限、来源版本、人工决定、回执恢复和旧任务更新测试继续通过。

真实模型的跨会议回放另计：简化核验版 `replay-final` 首次 12/12；当前提示 `guarded-replay` 首次 11/12，一次恢复后仍 11/12，失败项是旧任务完成状态更新。不能用程序测试通过替代这项失败。

## 迭代与实际结果

只修改工作边界规则时，C20/C21 都保留了完整工作内容，但 C21 把“我们”写成 speaker 而非 group，故内容正确不等于整项正确。加入字段与关闭类型后，完整上下文 UI 仍被核验当成无依据。

随后固定上游解释，将核验重点调整为“先还原连续分工，再分别核对字段”。三份冻结输入都恢复了 UI 候选，仅问承接。正常入口三轮也得到相同语义结果，但其中一轮先因日期格式失败，恢复一次后才成功。

简化核验同时带来回退：遗漏列表有时返回对象而非证据编号，并重新过度解释孤立材料或被动邮件。最终补回这些约束，使用 `check-guarded.txt` 的内容作为生产实验提示。

最后一步是**冻结上游、仅更换核验提示的局部对照**：复制原始模型调用缓存到新目录，再走正常评测/Service 入口，重新校验与生成提议。没有复制 SQLite 任务状态，也没有用标签驱动输出。`cache-provenance.json` 记录复用来源；汇总脚本确认所有新调用都只有 `check_work`。这批结果不能算新的独立全流程轮次。

上述局部对照指下表四组评测。另跑的 `guarded-replay` 只部分复用了上游：新数据库生成了不同的任务 GUID，M2 的历史任务输入随之改变，解释请求未命中缓存。因此它不是只改核验的对照，不能将其失败归因为核验提示。新增一次核验、两次解释调用（含一次恢复），共 19,269 token、63.7 秒请求时间。

| 检验范围 | 首次/中间结果 | 当前 guarded 局部对照 |
| --- | --- | --- |
| 六个既有难例 | 简化核验首次仅 3/6 处理成功；恢复一次后 4/6，内容 F1 44.4%，完全正确召回 2/6 | 6/6 完成；内容 F1 72.7%，完全正确召回 4/6；行为 15/20，全过 4/6 例 |
| 连续三角色分工窗口 | 原核验内容 F1 80%，缺 UI；简化核验三轮首次 2/3 成功，恢复后各 3/3 项完整正确 | 三份相同上游均保留全部三项工作，内容 F1、完全正确召回均 100%，行为各 5/5；UI 仅问承接 |
| 8 个中文合成样例 | 首次 7/8 完成；CP07 恢复后跟踪成功，但解释又因 case_id 错误失败 | 仍为 7/8，任务 5/6，内容 F1 90.9%；行为 20/23，全过 6/8 例 |

上一轮 context-v1 六例三轮均值为内容 F1 71.1%、完全正确召回 50.0%；更早 evidence-v1 为 75.2%/55.6%。本轮 guarded 的 72.7%/66.7% 是一组冻结上游局部对照，不能据此声称整体稳定超过它们。

当前 guarded 六例累计任务 token 为 106,515，其中多数来自复用上游；本次实际新增核验为 6 次、21,221 token、33.4 秒请求时间。33.4 秒不是完整处理六例的耗时。其他目录同样分别记录累计成本和新增调用，不能把已付出的上游计算当成免费，也不能把复制缓存当成再次付费。

## 已改善的可观察表现

- **C20**：视频工作独立保留，文稿动作另问；没有创建臆测的整理/发送文稿任务。
- **C21**：整理意见保留为团队承诺候选，只确认个人负责人，不再要求先确定篇幅。
- **完整分工窗口**：工业、UI、市场三项分开；UI 未承接仍保留工作内容，只问承接，不再重复出现多张遗漏卡。
- **CP02/CP03**：已回答的页面核对关闭；活动取消后名单撤回、已完成的安排核对与是否继续问题均不再追问。
- **CP04/CP05**：两个同名首页的检查工作保持独立，分别保存结果作为约束；无动作的说明书和演示设备进入实体账本。
- **PF01/PF02**：取消展会报名名单后仍保留通知报名者的善后工作；取消春季展会不影响秋季展会名单。

## 未解决的失败

**短片段 C03 仍漏 UI。** 上游解释把它写成“不明确具体动作或负责人”的 ambiguous，没有生成对应事件。新核验能指出这应是连续分工，但不会直接编造一个新事件，所以最终仍只有市场工作。完整上下文恢复成功不能替代短片段失败。

**C09 的研究目的确认仍失败。** 输出还是“看看说明书”并附上说明书堆积、无人使用的背景，给出 create 提议，没有形成“是否研究用户对说明书的看法/不使用原因”的具体确认。评分器把这项不完整 create 计为 1 个不合格创建提议；这是本地评测提议，不表示已经写入真实飞书。

**CP06 的问题仍太泛。** 它保留了用户不读指南、重复咨询及降低咨询量的目标，但只问“是否作为工作推进，具体做什么”。这让用户自己重新设计工作；按冻结准则，具体确认问题未通过。可选择的调查或改进方向仍需模型以推测形式提出，不能冒充会议决定。

**结构失败仍影响召回。** case_id、日期、引文及证据编号错误能让整项工作缺失。CP07 首次跟踪失败，恢复后检查点确实完成了隐式→明确工作的更新，解释却返回错误 case_id，最终仍无任务。有效的第8段检查点可获对应行为分，不能把最终空输出当作成功关闭旧问题。没有继续重采样成功语义或无限重试。

**跨会旧任务更新也出现契约失败。** M2 明确说“上周说的三个登录失败案例，今天早上我已经发到研发群了”，模型两次都正确关联旧任务并标记 completed，却把历史截止日期填入当前事件、不给对应原文证据。现有事件契约要求 deadline 有文字和证据，因此解释分支报 `Deadline requires explicit text and evidence`，整批任务更新未落地，旧任务仍未完成。这暴露了历史字段继承与当前证据契约之间的缺口；本轮没有放宽校验或反复抽样来通过回放。

文稿的核验理由还存在不一致：最终未生成文稿任务，但有理由仍倾向把文稿继承为“交大家确认”。它仍是模型边界判断不稳的证据。共享原话不同记录的语义去重也未由代码自动完成。

## 当前采用决定与后续重点

保留本轮已验证的工作边界、字段缺口和关闭机制，当前 `context-v1` 使用 guarded 核验提示，默认仍为 `split-v3`。

下一步应处理两个明确缺口：一是解释阶段已经漏掉工作时，如何用受支持的纠正意见补回最小工作表示；二是把业务目标转成具体、可选择的待确认工作方向。应使用新的冻结样例区分“合理建议”与“虚构已决定的任务”。模型结构输出可靠性另需收窄到 case_id、引用和日期这些已出现的失败，避免用重复采样掩盖问题。本轮没有宣称这三项已解决。

在扩大跨会实验前，还需先明确历史字段的证据来源及更新语义，保证汇报完成时不会因无须修改的旧截止日期阻断完成状态更新。
