# context-v3 残留问题：调研与修复建议

2026-11-15。结论：有可实施的方案。优先把覆盖关系和局部修正的约束移入程序，再单独实验必要信息覆盖核验。前者可以消除特定的矛盾表示与越界修改机会；后者是否改善中文会议中的目的理解，仍需真实模型对照。

本轮查阅论文、官方接口文档，并核对当前源码和已有失败请求，未新增模型实验。当前结果仍为定向来源语义 24/28、C23 0/2；context-v3 未晋级。详细基线见[实施结果](context-v3-results.md)。

## 1. 这次查明的具体缺口

| 问题 | 已核实的机制 | 修复能保证到哪里 |
| --- | --- | --- |
| 隔离 M2 | 核验把范围决定报成新工作，同时输出 `new_work` 与 `[R2]`，在 `plan_repair` 被拒绝 | 可以消除这类矛盾组合；不能仅靠结构保证范围决定分类正确 |
| 同段另一工作 | 只允许修正 R2/T2，模型却返回 R1/R2/R3；线程范围校验拒绝整个提案 | 可以让未选记录和身份字段不进入可写输出；错误内容仍需核验 |
| C23 | 最终任务保留“信号不清”的背景，但没有保留它与会后联系的目的关系；核验也认为没有遗漏 | 要改变核验任务的组织方式；有效性尚待实验 |

M2 另有可直接修复的提示缺口。旧版 `prompts/check-work-context-v2.txt:44` 明确规定 `new_work` 不关联旧记录、`same_work` 必须关联旧记录、已有记录分类错误不要重复报遗漏。当前 v3 没有这段完整规则；实际失败请求也不含这三句。v3 虽有“同一工作内容遗漏放 missing_details”的说明，但没有完整表达覆盖关系不变量。

核对对象为 `final-r1/M2/model/c03a754724db75a9d05f582b50e1ed8460c2d33b42d54bcd4164b432feb6f28e/request.json` 及同目录响应。响应确实为 `relation=new_work, related_record_ids=[R2]`。这证明模型收到的契约说明不完整，不证明补回提示就能解决语义误判。

源码位置：`meeting_eval/context_v3.py:22` 组装核验提示，`context_coverage.py:34` 规划修正，`context_v2.py:84` 起组装局部修正。v3 的修正结构仍从完整解释结构复制，要求模型重新返回 record/thread 等身份字段，扩大了局部修正的输出负担。

## 2. 覆盖关系与局部修正：让接口表达允许的操作

建议先做两项可分开验证的改动。

**覆盖检查分开表达“原记录有问题”和“另有遗漏工作”。** 原记录分类或内容错误只进入对应 record check；真正遗漏使用独立 `new_work_findings`，其结构不包含 `related_record_ids`。同一工作缺内容继续使用已有 `content.missing_details`。若模型无法判断是否重复，保留显式的待核对关系，不把它默认为新工作，也不自动删除。

程序生成 finding ID、绑定源版本，并在进入现有修正逻辑时派生旧内部 relation。这样不再需要模型同时生成 `new_work` 和“应为空的关联数组”。跨记录工作身份仍是语义问题：不能按 Q 编号相同就合并，因为同段可能确有第二项工作。

**修正接口只接受目标字段变化。** 程序冻结 target、原记录身份和允许修改的字段；模型输出目标的语义变化，不再输出 thread_ids、event_id 或全部 records。单目标请求可完全省略目标 ID；批量请求使用程序生成的固定目标槽位，未知槽位拒绝。新增遗漏工作走单独入口，ID 由程序分配。

实现步骤为：读取冻结原记录 → 在副本上应用允许的变化 → 重建 record/event → 运行原有证据、语义与处置核验 → 合并通过的结果。工作变成背景时，record/event 的变化必须作为一个依赖单元验证；失败时保留原状态和明确的解释争议，不能提交半份修改。未选记录保持原值，不把意外返回的整批记录静默截取为“修正成功”。

这一设计借鉴 [RFC 6902](https://www.rfc-editor.org/rfc/rfc6902.html) 的局部操作与 `test` 前置条件。项目适合实现小型业务补丁接口，不必开放通用 JSON 路径、move/copy 或任意数组索引。RFC 提及的 HTTP PATCH 原子性不会自动赋予本地代码；副本验证和提交边界需要程序实现。

对 M2 的语义边界，沿用当前任务政策，要求核验明确区分“范围值发生改变”与“要求某人采取实施动作”。例如“内部员工和试点客户都开放”对应范围决定；“陈可今天改灰度配置并发测试结果”才有独立实施工作。动作可以由对话上下文建立，不能用“没有负责人”或“没有动作关键词”机械否定工作。分类理由和 kind 冲突不能靠 JSON Schema 自动解决，仍需计入语义失败。

## 3. C23：从原文建立必要信息，再检查最终任务

当前核验同时看到原文和候选任务，最后认可了“会后联系；另有信号背景”。需要把两个问题分开：任务写出的内容是否有来源，以及原文必要信息是否进入任务。[FActScore](https://arxiv.org/abs/2305.14251) 将生成内容拆成原子事实检查支持率，主要解决前者；它本身不能发现未写出的必要目的。

[QuestEval](https://aclanthology.org/2021.emnlp-main.529/) 将问答用于两个方向：从摘要提问、到原文核对；从原文提问、检查摘要能否回答，并考虑信息重要性。可借鉴其方向设计本项目的覆盖检查，但论文的新闻摘要结果不能直接当作中文会议效果保证，也不需要引入原论文模型和依赖。

建议做一个范围受控的实验：

1. 仅根据原文及必要上下文，提取工作、对象和会改变执行内容的目的/范围/条件，记录 Q 证据，并区分原文明说、上下文推得、原文不足。此阶段不看候选描述。
2. 为必要内容生成不泄露答案的问题。随后只给最终任务描述和问题，要求回答并指明任务中的支持片段；不能把原文或期望答案一起交给这个回答步骤。
3. 比较来源答案与任务答案是否同义。答不出或答错才形成缺失项，再交给一次局部修正；最终仍检查有没有编造目的。不能只判“能回答”，也不能只匹配关键词。

C23 的问题应检查“会后联系要处理什么，以及与会上未听清内容有何关系”。当前“沟通其他几个问题；同时提到信号不清”没有明确建立后一关系。候选修订需要表达继续补问/澄清未听清内容的意思，不能仅追加“信号”二字。

这里有真实的不确定性：原话是口语，并未逐字说出“核对”。实验前应再次盲审完整来源，区分“联系的原因/目的”与“额外承诺核对某项材料”。保持冻结评分，同时允许记录标签争议；如确需修订标签，另报新旧口径，不能把改标签算作模型修复。也不能为通过 C23，给其他会后联系普遍补上未经支持的“核对”义务。

这个方案的风险是原文问题提取仍可能漏掉关系，或把普通背景误判为必要信息，因此需要正反例共同验收。

## 4. 其他路径为什么暂不优先

| 路径 | 判断 |
| --- | --- |
| 只补提示 | 可作为最低成本对照；先补回已丢失规则，但保留接口约束方案以消除冗余表示 |
| 再增加常驻分类器 | 暂不采用。此前 visible/blind 分类经完整下游处理均为 6/8，M2 各 1/2；上游判断会被下游推翻，见[既有实验](m2-repair-validation.md) |
| 增加重试次数 | 暂不采用。M2 已有一次带错误反馈恢复仍失败，不能用多抽样代替根因修复 |
| 换模型或微调 | 后置。先让失败类型与接口可测，再用相同冻结输入比较模型；当前样本不足以支持微调收益判断 |
| 原生严格结构输出 | 可做兼容性探针，但不是语义方案的前提 |

当前客户端使用 `response_format=json_object`。官方 [JSON Output 文档](https://api-docs.deepseek.com/guides/json_mode/)说明的是合法 JSON 输出；[Tool Calls 文档](https://api-docs.deepseek.com/guides/tool_calls/)另提供 Beta strict 模式，要求专用端点和支持的 schema，且所有对象属性必填、禁止额外字段，数组 minItems/maxItems 等不受支持。当前项目的网关是否支持需要单独核验，不能直接假定官方能力可用。即使启用 strict，授权关联、跨字段约束和语义正确性仍由应用检查。

## 5. 建议的实施与验收顺序

先冻结 v3 基线、输入、标签和调用预算，再分组比较：A 仅补齐覆盖提示；B 在 A 上加入覆盖结构与局部补丁；C 在 B 上加入来源到最终任务的必要信息检查。这样能区分接口改善与新增语义核验的收益。

先完成不调用模型的故障注入检查：矛盾覆盖关系不可进入内部计划；未知目标、改身份、越界字段、旧版本补丁被拒绝；record/event 依赖变化失败时不部分提交；同段真实新增工作能独立进入处置并关闭 finding。复用已有验证机制和标准库。

真实模型小集包含原始 M2、明确落实正例、同段第二工作及故意漏掉第二工作的版本；C23 原文、保持含义的改写、明确补问目的、信号问题已在会上解决且会后联系另有目的的反例。改写与预期在看新输出前冻结。各组至少三轮独立首次运行，模型、推理参数和修正次数固定；语义核验额外调用与成本单列，恢复结果另计。三轮用于暴露波动，不当作统计泛化保证。

验收看最终产物：C23 保留有依据的目的关系且不增加义务；M2 没有伪造范围任务或额外解释争议；真实工作和旧任务更新保留；越权操作为零。通过后再跑现有 14 例保护集与完整 M1→M2 正常入口，最后进入尚未完成的 30 语料/33 对照/10 行为/13 更新回归。首次失败继续计入，不能用修订后的成功覆盖。

推荐先实施 A/B，C 保持独立实验。A/B 的价值在于减少确定性协议错误；只有 C 的来源语义评分和保护反例共同通过，才有证据说必要目的遗漏得到改善。
