# 用户裁定后的问题修订与具体溯源

2026-11-16。用户重新判断五项问题后，M2 的业务预期与 C23 的评审门槛已调整。本文按新要求解释实际失败。此前“范围决定不能产生任务”“C23 必须写出补问目的”的标准不再作为当前结论。结构问题仍按保存的原始请求、响应和现有程序独立复现。

本次零项目模型 API 调用。证据在 [2026-11-16-user-review](../runs/2026-11-16-user-review/)，当前规则在 [review-policy-2026-11-16.json](../experiments/task-boundary/review-policy-2026-11-16.json)。

## 1. M2 可以是任务，多余追问来自哪里

原话：“登录改版第一批的范围今天改一下，内部员工和试点客户都开放。”按用户定义，工作动作、范围和“今天”的时间约束已经明确，可以保存范围决定，也保留执行工作。不能因为没有说出改配置等底层步骤就排除任务，也不能自行补造这些步骤。

原话没有指定具体负责人。如果需要分配到人，只需确认“这项范围调整由谁负责”；也可先以待分配工作保存。没有必要再次询问工作内容或是否决定执行。“今天”应保留，不自行添加“下班前”或其他更精确时点。明确改配置的正例还需检查两项描述是否是同一工作，不能将同一实施重复建项。

实际失败样例是 v4 small-v2/B-r2/M2。最终问题为：“请确认这项工作的具体内容、负责人，以及是否决定执行。”这是归约器拼出的通用问句，并非最终模型原封不动输出。链路已零调用完整复现：

| 阶段 | 真实数据与动作 |
| --- | --- |
| 修正输出 | R2 为 work，只有 owner 缺口，问“登录改版第一批范围今天调整这项工作由谁负责？” |
| 再核验 | owner gap 被判不需要，question 清空；check.issues 仍有 owner/question，用于表示原记录需要修正 |
| reduce_v2 | 根据 gap_checks 得到 missing_fields=[]、question=null |
| reduce_context | 将 check.issues 中 owner 当作仍缺信息重新加入；随后因 commitment=unknown 加入 commitment |
| 显示 | 两个缺口没有单字段专用问句，套用“具体内容、负责人、是否决定执行”的通用模板 |

确定的问题有两个：修正指示和仍待用户补充的信息混用；通用问题会追问并不缺失的内容。另一个产品边界是“决定执行”与“某个个人已经承接”需要分开，不能因为尚无个人承诺就反问是否要做。这份样例的检查理由仍坚持旧标准，属于已废弃的业务口径，不能作为新规则依据。

代码位置：context_v2.py 的 reduce_v2；context_state.py 的 reduce_context，尤其是将 issues 合入 missing_fields、追加 commitment 及默认问句三处。[question-trace.json](../runs/2026-11-16-user-review/question-trace.json)记录进入最终归约器前后的原值。

## 2. introduced_by 为什么缺失

来源：本轮 A-r1/G-omitted 的原始 repair_work 响应已经缺该字段，后处理没有删除它。模型写出了 R_O1_1 和 disposition added→R_O1_1，却没有写 introduced_by=O1。

已确认的接口缺陷：

1. context_protocol.py 先通过 obj 创建 RECORD 的 properties/required，再单独把 introduced_by 加入 properties，未加入 required。
2. v3 的 REPAIR 深拷贝该结构。示例生成器仅输出 required 字段，因而模型看到的“完整 JSON 结构”没有 introduced_by。自然语言修正说明却要求新增工作填写它。
3. 初次 schema 校验允许字段缺失；解释转换、记录规范化和再核验都继续接受。新增记录身份仅在末端 apply_repair 直接读取 r['introduced_by'] 时被检查，最终失败。
4. 现有主要成功测试直接构造了带 introduced_by 的新记录，因此不能证明模型收到的结构示例会引导其产生这个字段。v4 的程序绑定机制已经解决了一部分身份生成问题，但本轮 A 继承 v3，没有采用 v4 的修正适配。

因此可确定的是：自然语言说明、生成示例和下游必需契约不一致；缺失校验也过晚。无法仅靠这一次输出证明模型遗漏字段完全由示例导致，但程序允许缺失一直流到合并是可复现的。

新增绑定属于程序已知身份。后续可复用 v4 的受控绑定，或为新增记录单独构造包含绑定的完整协议；不宜给所有旧记录无条件增加必填字段。此处尚未修改生产代码。原样合并失败、仅补绑定后成功的离线对照保存在上一轮 [binding-counterfactual.json](../runs/2026-11-16-baseline-reassessment/binding-counterfactual.json)。

## 3. “仅收集”的待定事项

可以独立设置，建议称“待定事项”或“暂缓议题”，避免把所有没有日期的任务都归进去。例：“上线后要不要做监控面板？先放着，今天不定。”应保存议题、暂缓状态、来源和会议时间，不创建当前执行任务，不立即追问负责人、承接或期限。后文明确决定推进后，再转成工作。

现有 facts 分支的 unresolved 已能把这句话收集为未决问题，并在纪要展示。当前重复追问来自任务分支：共同需求规则把仍待决定的问题纳入 implicit_need，而 canonical_records 又要求 implicit_need/ambiguous 必须有 question；reduce_context 也会将它们放入需求确认列表。仅新增一个枚举名称而不改这些路由，仍会追问。

可落地的边界是“明确暂不推进”，而非“没有截止日期”：已确定要做但未定日期仍是正常工作；已指定今天调整范围更不属于待定事项。本轮已记录该分类设计和现有承载路径，尚未实现新类别或迁移历史记录。

## 4. Incomplete event checks 的真实原因

前次将其解释成“漏掉事件核验”不准确。原始响应显示，两例都完整核验了 E1，并额外生成了输入不存在的 E2。

| 失败位置 | 输入事件 | 输出核验 | 额外 E2 的内容 |
| --- | --- | --- | --- |
| a-cross-r2 / M2 | E1：旧案例任务完成 | E1、E2 | 模型将范围调整改判 work，直接开始核验一项尚未生成的范围任务 |
| D-r2 / G-omitted | E1：旧案例任务完成 | E1、E2 | 模型发现发送测试结果的遗漏，并直接核验一项尚未生成的发送任务 |

两份响应均正常 finish_reason=stop，不是截断或传输失败。错误原因是核验阶段越过职责边界：它同时需要审查已有事件、建议分类和发现新工作，输出时将“建议有这项工作”当成“这项工作已有 event_id”。正确协议应让分类建议进入 record_check、新工作进入 coverage_findings；由修正阶段真正创建事件并由程序分配身份，随后才核验新事件。

现有提示已要求每个输入事件核验一次，但输出 schema 的 event_id 只是任意字符串，未按输入限定集合。末端 canonical_checks 将缺项、多项和重复都报成 Incomplete event checks，因此错误名掩盖了真实原因。它拒绝整组输出，而 ContextV2Pipeline 在该检查失败时退出，尚未进入 repair；即使 E1 的六字段核验正确，也没有形成可执行的旧任务更新。

离线诊断只移除额外 E2、保留 E1/记录检查/遗漏发现，两个响应都通过现有 check；a-cross-r2 随后仍需要修正 R2，D-r2 仍需要补 O1。这证明首个阻断点是事件身份集合，不代表可以删除新工作或把干预结果算成通过。完整证据见 [protocol-trace.json](../runs/2026-11-16-user-review/protocol-trace.json)。

按用户的新 M2 判断，a-cross-r2 对范围调整提出 work 不再算语义错误；在核验阶段伪造 E2 仍是协议错误。后续应绑定待核验事件集合，并将分类/新增建议与已有事件核验清楚分开。错误信息也应分别列出 missing/extra/duplicate IDs。

## 5. C23 已按新标准重评
