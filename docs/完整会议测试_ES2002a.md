## 阻断原因

工作解释接口要求证据为原始发言ID字符串数组，例如：

```json
{"evidence":["ES2002a.B.dialog-act.dharshi.196"]}
```

模型两次都返回带`segment_id/start/end`的对象数组。第一次有26个错误引用槽位，第二次有27个；其中96和90个引用对象的segment_id全部确实存在，因此本轮直接失败原因是引用结构，而非编造不存在的发言编号。两次返回均完整结束，未耗尽输出token上限。

实际发送的提示存在冲突：正文要求“原始segment_id数组”，`context_wire.wire_prompt`追加的末句又解释“证据对象的start/end”。输入ledger也使用对象形式。校验器`reference_issues`只接受字符串数组；`ReferenceRepair.prepare`先按字符串数组契约校验整份草稿，因此拒绝这类对象结构，未触发证据补丁。节点内第二次尝试仍返回对象，最终为`recovery_required`。这给出了明确的修复方向：统一输入引用说明与输出引用契约，并用本次已保存失败响应验证边界处理；之后只恢复受影响分支，无需再测整套数据集。

诊断采用保存的请求、响应及当前校验函数，无额外模型调用。[逐次诊断](../runs/2026-11-17-full-meeting-ES2002a/failure-diagnosis.json)。本轮未修改生产代码，也未将未校验草稿强制转成正式结果。
