# M2任务边界、遗漏修正与确认资格设计草案

2026-11-15。状态：供评审的研究与设计建议，尚未实现，也未证明模型收益。依据为[系统根因调查](../../m2-system-diagnosis.md)和[两轮M2复测](../../m2-validation-results.md)。本轮用户要求探查、分类、寻找系统根因并设计解决方法；以下技术选择由本次调查提出。

## 1. 用户应看到的结果

原始M1→M2只完成同一GUID的案例整理任务，原期限保留；新范围替代旧范围并可在纪要中读到。M2没有额外范围candidate、负责人确认、截止日期或重复遗漏卡。追加“陈可今天下班前改好灰度配置并发测试”—“好，我来”后，只增加这一项真实工作，负责人、承接和期限保留。

相邻保护例：C20的视频任务保留，不能擅自把文稿并入确认动作；P07b保留本人已接受的“会后细化这个场景”，无需猜场景名称。确有竞争指代、待选择方案、未接受分派和条件工作时，仍应保留其真实待决定事项。当前范围是在本地模拟器验证这些行为。

验收分别衡量任务正确性、确认必要性、决定/上下文保留、写入与幂等、首次结构成功率。把错误确认移到别的栏目仍是未解决项；不能用隐藏争议或减少输出提高表面成绩。

## 2. 可选路线与建议

| 路线 | 具体改法 | 取舍 |
| --- | --- | --- |
| A：提示与示例 | 在现有三个阶段对齐工作资格、缺口必要性和完整JSON示例 | 调用不变，可作低成本基线；无法提供缺失的遗漏身份与关闭流程。 |
| B：现有阶段的局部协议调整，建议主线 | 为遗漏引入可修正身份，为确认提供独立依据，为字段缺口表达影响；复用一次修正、原执行器和权限机制 | 改动有明确调用方和故障依据；模型语义仍需实测，不能仅凭协议宣称修好M2。 |
| C：新增原文分类及统一合并 | 分类先独立判断原文，再与现有解释合并；通过visible/blind区分前序影响 | 增加调用与延迟；只有配对实验证明收益后才考虑生产接入。 |

建议将B拆成可单独出分的改动，用A作语义提示对照，C先做隔离实验。保留现有Service、授权历史投影、任务身份和一次修正预算。此次不扩建通用工作流框架，不引入多模型投票或训练新模型。

## 3. 解释、核验和用户确认各自回答什么

继续使用现有records、events和kind，不再增加一套重叠的全量话语标签。明确各自职责：

- **记录分类**：当前语境表达工作、潜在需求、非任务背景，还是原文自身有待决定的工作含义。必须指出支持该用途的原文；活动未来发生或产品决定刚发生不构成新增实施工作的证据。
- **事件字段**：在工作成立后，检查动作/对象、执行者、承接、时间和旧任务关系。模型不得用“owner未知”反向证明任务存在。
- **用户确认资格**：原文是否真的留下一个会影响工作或执行的决定。模型前后意见不同本身不构成用户欠缺信息。

首轮实验对现有record check增加两个有限输出，避免重写所有事件结构：

```json
{
  "record_id": "R2",
  "verdict": "contradicted",
  "issues": ["classification"],
  "reason": "这里改变的是开放范围，未另行安排落实动作",
  "evidence": ["Q2"],
  "proposed_kind": "context_only",
  "clarification": {
    "status": "not_needed",
    "basis": null,
    "fields": [],
    "question": null,
    "evidence": []
  }
}
```

`proposed_kind`仅在classification问题时使用，取现有kind或null；只是待修正建议，不自动改变记录。`clarification.status`为 `needed/not_needed/unresolved`：

- needed：`basis`具体说明尚未决定的内容或当前执行缺口，fields与question必须对应，有原文支持工作或需求的前提。缺负责人可由已明确分派而未点名支持，不要求原话另说“负责人未知”。
- not_needed：question=null、fields=[]；记录仍可能需要内部修正，例如将错误work改成context_only。
- unresolved：系统尚不能判断提问前提，保留在trace及统一的“待核实含义”展示，引用原话并说明仍有分类争议，不自动补“谁负责、何时做”。此状态仍计作未解决的可见残留，M2验收不通过，不得作为减少错误确认的捷径。

解释阶段仍可提出缺口；核验输出为每个缺口明确 `blocking_for=content|operation|none` 与理由，替代“仅有字段名就整体阻断”的做法。第一版可在check侧输出 `gap_checks`，由reducer从核验结果导出最终missing_fields，不维护两份相互独立的真值。只有经过核验的缺口参与最终路由；missing_fields和question的历史输出格式通过确定性投影继续提供。

`gap_checks`每项包含field、verdict、blocking_for、reason、evidence；field取现有缺口字段，verdict仅supported/unsupported。须覆盖解释器提出的每个缺口以及核验新指出的缺口，禁止同字段重复。unsupported必须blocking_for=none；supported且为content/operation才投影到最终missing_fields。移除原缺口、改变分类或提问时，顶层record verdict也须标记为需修正并附对应issues，不能出现“全记录通过但要求修改”的协议冲突。此处结构一致性可由程序校验，缺口是否真实仍由语义实验判定。

`clarification.status=unresolved`时，该记录不产生新的自动执行提议；若工作内容已核验支持，可作为待核实候选保留，否则只显示原话与含义争议。原任务无关的已支持更新照常执行。unresolved需要模型说明争议具体落在分类、内容还是问题前提，不能只给一个空原因。它不等于用户必须提供负责人或日期。

最终路由的优先级固定如下，所有展示层使用同一份派生结果：

1. **结构不一致**：needed却无受支持的待决定字段，或not_needed同时有content/operation缺口，属于协议错误；不由代码猜选一个结论。提议采纳、条件是否成立统一对应commitment，潜在需求是否转成工作对应work，所以needed不能靠空fields逃过验证。该次check输出不生效，保留此前有效阶段及错误，按现有partial/独立结构恢复契约处理。
2. **真实内容缺口已获支持**：记录忠实表达了已有工作/需求及其真实不确定性，record check=supported，clarification=needed，且gap_checks中有supported/content缺口时，保留已知工作并只问该缺口，阻断受影响的操作。例如两场景确有竞争时只问选择哪一个；event.work可因对象尚未选定而insufficient，不因此把它变成系统争议。这里record supported表示“连同缺口的描述忠实”，不表示所有执行字段已齐全。
3. **工作前提或缺口判断本身未通过**：排除前一类后，分类、动作存在性、指向或缺口必要性仍被否定或无依据时，不产生该记录的自动执行。即使clarification=not_needed，也只表示不应向用户问原问题，不能据此应用proposed_kind。先尝试预算内修正；若失败或预算用尽，确定性派生一项unresolved含义记录，用原话说明尚未可靠解释。错误任务描述只留trace，不作为已成立事实展示。M2/C20仍判未解决。
4. **内容支持、局部操作缺口成立**：沿用现有候选保留规则，结合经过核验的owner/commitment/time等缺口问具体问题；clarification=needed不得引入原文无依据的新动作。已存在任务的更新继续遵守原来的字段与负责人权限检查。
5. **内容支持且无阻断缺口**：才按原事件/执行规则创建、更新或保存上下文；not_needed不隐藏任何有效工作。clarification=unresolved按前段限制该记录自动执行并明确保留残留。

修正结构失败不重写首次有效records/checks；上述路由在其上应用，因此“保留首次有效结果”不等于恢复旧的泛化确认。此条是派生路由契约，需要和失败恢复、未选中记录保持一起测试。

| 情况 | 记录与操作 | 确认 |
| --- | --- | --- |
| M2范围决定 | context_only，决定保留，无任务event | not_needed |
| P07b正常名称省略 | work，“这个场景”原样保留，accepted；reference为none | not_needed，不补场景名 |
| 两个场景竞争且选择影响动作 | work/ambiguous，content阻断该项创建 | needed，只问选哪个对象 |
| 已明确团队工作无具体账号 | work保留candidate，operation缺口 | needed，只问个人负责人 |
| C20附带材料提及，未安排处理 | 原话作为非任务上下文；不补文稿动作 | 不问预设处理动作的负责人；若仍有模型争议，记unresolved并判该例未解决 |
| 提议/条件工作 | 保留原有proposal/conditional_work语义 | 问采纳或条件，不泛问已承诺任务 |

“竞争解释”用于内容消歧，不强制每个负责人缺口编造两个候选人。对语料外确实只有一句模糊工作请求的情况，可以说明动作缺失；不能把“没有具体名词”一律当成竞争解释。核验给出的证据也需人工抽查，schema只能约束结构。

## 4. 遗漏是待验证的工作假设，必须有处理结果

新协议将 `uncovered_spans` 的模型输出改为 `coverage_findings`，每项包含工作描述与证据，而非只返回整段Q编号：

```json
{
  "description": "将合同发给法务",
  "evidence": ["Q2"],
  "relation": "new_work",
  "related_record_ids": []
}
```

relation仅为 `new_work/same_work/uncertain`；same_work必须关联已有record ID。模型只提出对应关系，程序验证ID存在，不能用相同Q自动认定同一工作。相同段落中的“改配置并发测试”和“另外通知客服”可为两项；范围决定与配置任务也能共享证据。

程序接收并验证完整check输出后，为每个finding分配稳定的 `O1/O2` 身份，随本次源版本、首次核验结果保存；恢复复用已保存身份，不按描述字符串重新算ID。它与record ID分开，避免把待验证遗漏直接变成可添加任务的U卡。

一次修正的输入目标包括finding IDs；record目标集合在调用前固定为“失败record IDs，加上same_work/uncertain finding明确关联的record IDs”。后者可以包含首检通过记录。例如已有记录只写“改配置”，finding指出同一工作还要“发测试”，可在原record上补全约束，不能强行另建一项重复工作。扩大的目标和原因均写入trace，输入同时保留其首检版本。new_work要求related_record_ids=[]；同一个finding不能一边声明独立新增，一边要求改写已有记录。

扩大目标后的既有record/event/thread身份保持原契约；未选中记录逐字段不变。same_work若仅确认已经覆盖，无需修改该记录。预算内修正不得再擅自扩大到输入集合外的记录；如发现还需改其他记录，finding保留unresolved，留作下一次显式处理，不隐式启动第二轮。如果只有finding也可以触发同一次修正，不增加第二轮。输出包含原目标records的修正、由finding产生的新records，以及每个finding的disposition：

- `covered`：关联最终record，说明同一工作已经被表达；可以关联被核验支持的context_only，表示首次遗漏假设其实是非任务。
- `added`：关联本次补出的一个或多个新record，按正常解释与字段核验决定任务/确认。
- `rejected`：原文不支持该遗漏假设，给出原文依据。
- `unresolved`：仍不能判断，保留一个未解决finding。

新record ID由程序预分配合法命名空间，例如由O1派生R_O1_1；保留 `introduced_by=O1`。既有record的身份及thread关联仍保持；新增record可 `thread_ids=[]`，但必须有授权原文证据。若一个finding包含两项独立工作，允许映射多个新record，不能为满足固定数量强行合并。

再核验只覆盖修正的records及这些finding的disposition，提供所有未改记录供同一工作/重复判断，不把uncovered固定为空视作“已解决”。每个finding必须得到且只得到一个核验结果：支持则应用disposition；语义不支持则保留unresolved，缺失结果为协议错误。covered/added只有在所关联的最终记录及对应关系均通过核验时才能关闭；不能仅因关联ID存在就关闭。

合并分两层：整批结构校验失败时保留首次有效结果；结构有效后，按语义核验结果形成新的完整快照，再一次替换。首检通过而因finding扩大进目标的记录，若修正后的内容/分类反而未通过，保留它的首检支持版本，并将依赖该修改的finding置为unresolved。原本未通过的记录若修正仍未通过，按第3节保留一个含义争议。新增record未通过则不能关闭其finding。这个保留规则保护已支持内容，不证明模型两次都支持的错误内容正确；后者仍依靠语义对照发现。首次finding、处置及被拒绝的修改都保留trace。

所有最终任务、确认和遗漏展示从同一批已核验记录与未解决finding派生。covered/added/rejected不另建U确认；unresolved最多展示一次，带同一finding ID，pending和review共用该ID，纪要避免再展示一遍。这里关闭的是已核验对应关系，绝不是所有共享原话的记录。

## 5. 证据与schema独立改进

先做可单独验证的规范统一：一个完整的机器可校验示例包含 `time.change`、`other_changes` 及所有当前必填字段；提示示例和验证器用同一版本维护。错误信息区分“原文无该引文”“重复引文未定位”“缺必填字段”，保留JSON路径和段号，便于一次定向结构恢复。先完成schema检查并列齐同批缺字段问题，再做引用/关联检查，避免只看到第一个引文错误而漏掉同次响应中的其他必填字段错误。

引用ID作为独立实验，先复用核验阶段已有的证据目录：程序为授权原文生成稳定段落ID及可选的连续子句ID，保存源版本、segment、start/end和原文。模型返回ID；角色身份直接引用已授权person_ref/speaker元数据，不把姓名拼入正文。时间、承接、动作依然分别引用证据，不能用“所有字段都引用整段”代替语义检查。

首轮以完整段落引用作为必有选项，子句切分只按确定性标点并保存原位置；跨句语义可选多个ID，原文全文始终在输入中。同段重复短语通过程序位置区分，不让模型数occurrence。整个源版本变化时重建目录和缓存；检查点只暴露当前及此前ID，保证不见未来。若实体mentions需要更细定位，先保留现有精确子串通道作受测对照，不静默接受不存在的mention。

JSON Schema strict模式可以单独验证缺字段率，但需要确认当前模型端点支持。它不能保证引用ID选对、决定分类正确或不同记录对应关系正确；不把provider迁移与M2语义实验合并。当前阶段也不做“单条坏记录直接跳过继续自动执行”的容错，以免未验证的跨记录依赖被忽略。

## 6. C3怎样检验前序解释影响

先做阶段级诊断：冻结同一份授权原文、名册、旧任务投影和证据目录，选择失败M2、落实正例、C20、P07b四份输入。每份两轮、每轮visible/blind配对，共16次分类调用。模型、提示、推理预算和输出schema相同；visible附带冻结的ledger/records/events，blind完全不附带。两组均读取全文，不以既有R2或候选段筛选输入，避免通过选段泄漏前序结论。历史先沿用当前tasks投影，加入历史decisions另作C1类实验。

分类输出当前语境中的语义记录，使用既有kind、描述和原文引用，并为每条记录输出本设计的clarification及gap_checks，不输出平台写入。ID为该调用内部ID，不借用冻结R2定位或生成问题。单独计工作分类、真实工作损失、澄清资格判断和结构失败。该阶段只能证明分类差异，不能宣称最终纪要改善。

若需要评估端到端收益，两组都使用相同合并解释调用：输入原文、冻结原解释和分类结果，输出统一records/events，再走相同check及最多一次repair。分类与合并各增加一次调用；与不新增调用的基线比较时明确报告这两次成本。visible/blind之间才用于分析“是否看前序解释”，不把新增计算或不同提示的收益当作去偏收益。任何一组都不能按证据交叠直接删工作。

合并可能重新引入原错误，所以保存分类、合并、核验和修正各阶段结果，单列正确→错误及错误→正确的转换。关闭/开启核验推理是另一个变量，如需研究另开等输入实验。

本轮设计预先采用以下晋级条件：每个case/round按该例全部语义要求判整例通过；结构失败和unresolved都计失败，不能排除后只算可解析输出。blind的原始M2两轮都须判为非独立工作，实施正例两轮都须保留真实工作；C20视频工作和P07b承接不得相对visible退化。每轮blind通过例数不得少于visible，且至少一轮严格更多，才以“去除前序输入可能有收益”为依据进入共同合并实验。若两组同样正确，只能说明该分类调用可用，不能支持blind优于visible；改以额外分类调用与简化现有阶段作成本比较。若两轮方向相反或保护例退化，本批不晋级，不追加抽样挑好结果；要继续必须先说明新假设并冻结新批次。

端到端保留条件更严格：原始M2及实施正例两轮首次都满足第7节标准，C20/P07b及竞争指代保护对照无新增退化，且相对同输入的当前流程改善用户可见错误；阶段分类正确但最终输出失败仍算失败。新增调用、token和耗时单列。较简单路线达到同样结果时优先保留较简单路线。这是开发集上的局部选择门槛，不是统计显著性或新会议泛化保证。

## 7. 实验顺序、样例和通过条件

这是研究顺序，不是已执行的实施计划。每一项单独冻结提示、协议、源码和预期；选出有效改动后才组合，组合后再从Service入口回归。

1. **确定性契约**：将本轮四个干预变成失败测试，先补遗漏单独触发、处置后关闭及未选中记录保持。增加同段第二项工作，防止用段号粗暴去重。
2. **提问资格与缺口**：冻结初始解释，比较现有check与新check。M2、C20、P07b和配对保护例每组至少两轮；统计所有被挡住的真实任务及unresolved，不只统计问句减少。
3. **分类对照C3**：按上节先分类诊断，有信号才进入共同合并流程；保持两轮全部首次结果，结构恢复单列。
4. **结构协议**：完整schema示例、引用ID各自单独对照C19/P07a/P08b/positive-r1型输入，再检查条件原话、跨8段、角色接受和引用归属。输出成功且语义正确才算成功，不能只看JSON可解析。
5. **候选方案组合**：重放完整M1→M2与落实正例，再按实际改动回归旧任务、条件候选、长上下文、取消、权限和幂等；变更全体context协议时执行30段语料及33例对照，保留原/审计双口径。

必须固定的区分样例：

| 能力 | 不产生额外工作的输入 | 必须保留/补出的输入 |
| --- | --- | --- |
| 决定与实施 | 原始M2.2，不改写成更清晰的负例 | 原M2加明确改配置及本人接受 |
| 同段覆盖 | 已有记录涵盖范围决定，却被再标遗漏 | 同一句另说“另外把测试结果发给客服”且已有记录确实未包含它 |
| 真实对象省略 | P07b的“这个场景”且本人接受 | 登录与支付两场景均为可能指向、后文无法区分，只问对象 |
| 材料动作继承 | C20附带文稿提及 | 明说“文稿也发给大家确认”，保留工作 |
| 本人接受 | 对应执行人说“好，我来” | 换成其他人“好”、明确拒绝或条件承接，结果应相应变化 |
| 证据定位 | speaker姓名不在正文，不得伪造成mention | 正文有重复称呼、引用中有人名，引用ID仍指向正确位置与归属 |

通过标准：原始M2至少两轮配对首次完整流程均零额外items、零错误确认/未解决含义、零重复遗漏；原任务同GUID完成且due_date/due_text保留，决定替代及权限正确。落实正例每次保留唯一实施工作、负责人、承接、期限。真正遗漏能在一次修正预算内补回；无法解决时只保留一个准确标识的残留，不伪称完成。P07b不能以删除全部reference检查来通过，竞争指代仍受保护。六个关键输出层分别出分，不用持久化任务数或程序测试代替语义审查。

## 8. 改动位置、版本与交付

| 位置 | 具体职责 |
| --- | --- |
| context三阶段提示与协议定义 | 完整schema、clarification/gap checks、coverage findings；语义提示对照单列 |
| `context_pipeline.py` | finding目标、受限新增record、再核验处置与原子合并；保留首次trace |
| `context_state.py` | 核验后的缺口与确认路由；共用finding身份；不推断新工作 |
| `task_events.py`及证据投影 | 引用校验及精确错误类别；执行规则保持原入口 |
| `requirement_review.py`、`Service.minutes` | 只展示最终一次确认；未解决含义不带虚构工作前提；原权限与手动确认契约继续验证 |
| 评测入口 | 当前语义预期独立版本、结果hash、首次/恢复分开、阶段转换与用量 |

实际实验改动前保存新快照，协议与验证配置升版、使用新目录和新SQLite，旧缓存不混用。纯诊断保留当前生产配置。若引入会影响确认身份的协议变化，不迁移旧已处理会议；旧输出继续按原版本可读，新输入使用新版本。构建者可决定内部类/函数组织、目录和字段拼写，只要不改变上述语义、单轮修正预算和验收条件。

交付时同时给出可用路径、具体残留和新增成本。C20/P07b在本设计中是同机制保护例，是否扩展为完整独立调优阶段取决于局部实验结果；不因为M2一次通过就扩大为项目全部问题已解决。
