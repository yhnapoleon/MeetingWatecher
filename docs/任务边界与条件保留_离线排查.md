# 任务边界与条件保留：离线排查

2026-11-17。本轮从已有原始输出定位 GN29 的误提取和 GN25 的条件任务漏项，确定下一步值得修改的共同机制。生产代码、提示词、模型配置和冻结标签保持原状；本轮模型请求为 0。

**GN29 的 R8/R23 已确认存在确定性流转问题：带时间设置的进度汇报未进入 report 分支，随后被包装成允许新建任务、却没有确认问题的卡片。GN25 的条件支付在解释阶段被归为背景，核验重复认可了这个判断；覆盖提示遗漏了已被背景引用的这句话，但完整输入与修复契约仍支持发现、报告这项工作。** 后者的提示设计是否造成模型漏检，尚需控制实验才能判断。

## 1. GN29：进度汇报如何变成新任务确认卡

原文 `qm.Bed005.427` 报告明年夏季交付物完成了一半。解释记录 R8 是 `work`，事件 E5 为 `progress + new`；`new` 表示没有匹配的历史任务。模型同时填写 `time=deadline / next summer / change=set`。核验认可了记录和全部事件字段，没有需要询问的缺口。

R23/E15 的路径相同：记录第三方 ontology 工作进度，事件为 `progress + new`，同时填写 `deadline / next Monday / change=set`。其描述还混入了展示示例的未来工作，而该工作已由 R24 单独输出。这是额外的模型拆分问题，不能靠状态分流自动修正描述。

| 环节 | 观察到的输入与结果 |
|---|---|
| 解释与核验 | R8/R23 均保留 `progress`；缺口为空，问题为 null，核验 supported |
| `context_new_work.reduce_untracked_report` | 仅接受 `time.change=keep`；这两条因 `set` 返回 None |
| 其他归并分支 | `reduce_new` 只接未来工作；底层事件归并不生成新任务或更新，返回 `no_supported_state_change` |
| `context_state.reduce_context` | 因存在 pending 生成 ambiguous 卡；没有缺口可生成问题，得到空字符串 |
| 新建许可 | `can_add_task` 只核对 `relation=new` 及关系核验，没有检查 `state`，结果为 true |
| Service | 原样提供两张确认卡，并保留 `no_supported_state_change`；`collected_issues` 为空 |

源代码入口：[report 分支](../meeting_eval/context_new_work.py)、[记录归并](../meeting_eval/context_state.py)、[确认入口](../meeting_eval/requirement_review.py)。`can_add_task` 也是人工确认接口允许创建的条件之一，因此这个值有实际操作含义；本轮没有调用人工确认写入，原自然会议仍无账号映射，任务表为 0。

### 最小回放

读取冻结模型结果，通过生产 `reduce_v3` 回放，items、review_records、pending、reports、item_records 均与历史 Service 保存结果一致。随后分别复制完整输入，只把 R8 或 R23 的 `time.change` 从 `set` 改成 `keep`：

| 对照 | 对应确认卡 | 对应进展记录 | 其他输出 |
|---|---|---|---|
| 原始输入 | 可新建，问题为空 | 无 | 与历史输出一致 |
| 仅 R8 改 keep | R8 卡消失 | 新增 R8 report | items、updates、其他确认卡及原有 reports 不变 |
| 仅 R23 改 keep | R23 卡消失 | 新增 R23 report | items、updates、其他确认卡及原有 reports 不变 |

原基线已有另外 3 条正常 report。这里比较的是新增 report，不把已有报告清空。通过独立 SQLite 的 `Service.process → requirements` 正常入口回放，用户可见的两张卡、Service.pending 也复现，排除了仅指标脚本误计或 SQLite 保存损坏。

另用既有支持性事件夹具检查 5 种流转：无关联旧任务的 progress+keep 进入 report；progress+set 复现误入确认卡；future_work 产生任务项；conditional future_work 保留候选与条件确认卡；existing progress+set 产生日期更新。它们隔离了状态、关联和时间操作的区别，未调用模型重新判断语义。

### 修改边界

值得优先修改的是统一流转契约：**没有可执行更新，不意味着存在一项待新建的未来工作。** 对核验支持的、无历史任务关联的进度/完成汇报，按报告保存；时间和其他变化仍应保留供追溯。确有解释矛盾或无法执行的变更，应进入相应复核或能力限制分支，不能因回退而获得新建任务许可。

本轮把 set 改为 keep 只用于定位分支，不能直接作为生产修法。对已有任务的真实改期这样处理会丢失更新；R23 的混合描述也不会因此自动拆好。后续修正应同时覆盖报告、未来工作、条件工作及已有任务更新，避免只过滤 R8/R23 或按中文关键词删除记录。

## 2. GN25：条件支付已被读到，但工作资格被否定

`qm.Bed011.639` 的完整原话是：

> Um a student rate shouldn't be very high . So , if we all decide it 's a good idea for you to go then you 'll {disfmarker} we 'll pay for it .

上文 Grad B 询问费用并表示还未计划参加；Professor D 在这句中表示，如果大家认为参加合适，就支付费用。后文“目前没有倾向”继续谈参会是否合适。按冻结任务 T3 口径，应保留带条件的团队支付，不能升级为已经决定付款，也不能因条件尚未成立而当作没有工作。

解释 R6 将来访、NAACL 缺席、Santa Barbara 参会和费用讨论合在一条 `context_only` 中，描述实际写到了“if they all decide ... pay”，但以没有决定或分派收尾，没有生成支付事件。核验又给出 `qualification.work_basis=none`、supported、无需澄清；其证据也包含 639。原始核验经既有结构规范化后 `coverage_findings=[]`，修复计划 `needs_repair=false`。

这说明漏项发生在解释及核验对工作资格的判断中。源文、跟踪和记录都保留了条件支付信息；之后程序依据受支持的背景分类保存 context_record，不会主动把自然语言重新拆成支付任务。

### 覆盖机制的实际限制

`context_v5` 把所有 records/events 引用过的 segment 都视为 represented。639 已被 R6 引用，因而不在 `coverage_review.unrepresented_evidence` 中，尽管支付从未成为工作记录。现有覆盖提示重点要求扫描这个未引用清单，**引用覆盖与工作覆盖在这里并不相等**。

但不能把这一点写成“程序禁止检查已引用原话”：完整 93 段仍在核验输入，record_check 也可以纠正背景分类，coverage_findings 可以引用全文中的任意有效编号。核验已经在 R6 的依据里使用 639，说明它并非完全没看到这句。

离线重建原始核验 payload，核对 scope 与历史值完全一致；规范化响应通过当前契约。然后在副本中加入引用 639/Q87 的 `new_work` finding，保持其他核验结果不变：`expand_checks` 接受，`plan_repair` 生成 O1，`needs_repair=true`。所以已有通路能把背景旁遗漏的独立工作送入修复；本轮没有执行修复生成或验证模型能自行产生这个 finding。

### 可验证的后续改法

核验需要区分“记录忠实概述了一段讨论”与“这段讨论中的每项独立工作均已保留”。可先在同一次 check 中，对被非工作记录引用的发言增加独立工作覆盖检查，并明确已有引用不代表工作已覆盖；真正遗漏仍进入现有 coverage_findings，不新增整场模型阶段。

这是待验证方案，不能据离线注入结果宣布条件支付已修复。最小真实对照应固定 GN25 的原文、解释结果、核验配置及预算，只改变覆盖检查设计；同时使用有条件工作与纯背景的对照，观察是否增加误提取。现有提示已经规定 conditional、背景旁另建 work，不宜再追加同义口号或特设“会议费用”规则。

## 3. 证据与复现

运行入口：[replay.py](../experiments/task-boundary-diagnosis/replay.py)。在项目根目录选择一个尚不存在的输出目录执行：

```powershell
$env:PYTHONUTF8='1'
python experiments/task-boundary-diagnosis/replay.py --out runs/task-boundary-diagnosis-replay
```

脚本使用冻结模型输出，禁用 socket 连接，不读取凭据，不续跑历史 runner。生产代码与原始输入的 SHA-256 写入 source-hashes，并在结束前检查一致。

当前通过结果：[offline-r2/diagnosis.json](../runs/2026-11-17-task-boundary-diagnosis/offline-r2/diagnosis.json)。同目录保存 Service 回放 JSON/SQLite、GN25 契约探针和来源摘要。初次 offline-r1 因诊断脚本误把“新增一个 report”断言成“全场只有一个 report”而停止；修正为增量比较后 offline-r2 全部通过。这个失败属于诊断夹具，不是生产失败，也未产生模型调用。

本轮没有新的任务质量分数。最新真实模型成绩仍为 GN29 8TP/7FP/0FN、GN25 2TP/0FP/1FN；R17 和负责人边界争议仍按原报告保留。GN29 其余方案讨论升级为任务、字段条件丢失等问题也未由本次回放解决。
