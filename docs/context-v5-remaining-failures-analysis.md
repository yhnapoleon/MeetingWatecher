# 网络恢复后 12 次失败：分类与溯因

2026-11-16。网络恢复后剩余的 **12 次失败对应 9 个不同场景**。已将每次实际用于评分的输入、输出、请求响应、阶段校验、SQLite 状态和操作日志单独复制到 [失败证据集](../runs/2026-11-16-context-v5-failure-analysis/README.md)，逐文件验证副本与来源一致。其中 r1/C17 使用网络恢复后的结果，其他 11 次使用原全量输出。

最集中的问题是：**模型把“没有新增待办”误当成“不是需要保留的工作信息”，将完成／进展汇报降为背景。** 这涉及 7 次执行。其余分别是再检查越界、逐字引文被改写、线程顺序倒退，以及短切片中的省略分工判断。HT06 的两次失败同时有语义误判和协议错误，不能只修最后抛异常的地方。

## 一、完成与进展汇报被背景分类吞掉：7 次

### 不是没有读到旧任务，而是检查结论内部矛盾

HT05 的原话是“陈可的三个登录失败案例已经整理好发到研发群了，他今天不在。”HT06 则由陈可本人报告旧案例已发出，并承诺新的支付案例任务。两轮的初始解释都正确产生了 `work + completed + existing`。原始 check_work 请求中也确实包含 H-HT05 或 H-HT06，状态为 open，因此不能归因于历史任务没传入、目标丢失或负责人字段缺失。

更关键的是，四次检查的 **work、owner、commitment、time、state、relation 六字段全部为 supported**，却同时要求把所属 record 改成 context_only。理由反复使用“没有新增待办”“没有独立跟进动作”。这说明模型认可“旧任务已完成”这一事实，却错误地拿“是否产生新任务”决定它能否作为工作记录存在。原始字段对照见 [检查矛盾证据](../runs/2026-11-16-context-v5-failure-analysis/semantic-boundary-evidence.json)。

后续程序按既定契约工作：record 分类未通过就不能执行对应事件；若修正把 record 改为 context_only，则不允许携带 event。因此 HT05 第一轮静默丢掉确认入口，第二轮保守输出 interpretation_unresolved；HT06 旧任务未更新。这里不是执行器找不到正确事件，而是已经正确提取的事件在语义检查和修正中被否定了。[归约入口](../meeting_eval/context_v2.py)的 reduce_v2（第 136 行起）可复核这一处理顺序。

HT05 的正确结果应保留第三方完成报告，进入负责人确认或核对流程，旧任务暂不自动完成；HT06 是负责人本人报告，应更新旧任务完成。两者不能统一处理成“无需记录”，也不能统一放开自动更新。

### C17/P11a 丢的是结构化状态，原话文字仍在

C17 两轮和 P11a 第二轮包含“纪要已发出／正在放入共享文件夹”。这些信息保留在 facts 或 context_only 的文字中，没有凭空生成新任务，但 reports 为空。其影响是完成／进展状态无法被下游作为报告使用，严重程度与 HT06 的旧任务未更新不同。

程序已有支持：reduce_untracked_report 能把无旧任务关联的 completed/progress 事件保存为报告，不新增待办。P11a 第一轮也实际输出了 completed 和 progress 两条报告，是同一输入的成功对照。因此问题不是缺少整个报告功能，而是模型有时根本没有让这类输入进入该路径。[报告归约器](../meeting_eval/context_new_work.py)位于第 31 行起。

### 更深层的设计因素与证据边界

提示中确实写了“旧任务完成应保留事件”和“无关联旧任务的完成／进行中汇报可保留 work”；不能说规则完全缺失。但 context_only 的一般定义在多个阶段反复强调“无独立跟进工作”，给了模型一个容易被过度使用的判断标准。追踪阶段没有 history.tasks，解释和检查阶段才收到旧任务；HT06 第一轮的检查理由还直接援引了错误 ledger 分类。

已确认的是分类逻辑错误、字段间矛盾以及传播路径。**“背景规则压过汇报规则、账本对检查造成偏置”是有原始输出支持的解释，但尚未通过提示消融实验确定各因素的因果贡献。** 不应仅加一句提示就宣称解决，也不应为了让事件通过而跳过语义检查。

修复方向应先统一三个问题：是否为工作相关记录、处于何种状态、是否产生平台操作。使用已有 state/relation 即可表达报告，无须先增加新类别。验证至少分别覆盖：无旧任务的完成／进展报告、本人报告已有任务完成、第三方报告需确认，以及同句报告旧任务并承担新任务。检查器认可 completed/existing 却判 record 为背景时，应明确视为需要解决的解释矛盾。

## 二、再次检查把只读参考也当输出目标：3 次，与上类重叠 2 次

| 执行 | 允许检查的记录 | 只读参考记录 | 实际返回 |
|---|---|---|---|
| r1/CP02 | R2 | R1 | R1、R2 |
| r1/HT06 | R1 | R2 | R1、R2 |
| r2/HT06 | R2 | R1 | R1、R2 |

三次多余字段恰好都来自 context_records。生成 schema 的代码只允许目标 records，映射没有把只读记录误加入允许集合；错误发生在模型输出。请求同时携带待查记录和带身份字段的只读参考，模型把两者都写进 record_checks，本地 closed_validate 随后拒绝整份输出。

原始请求的 response_format 是 `{"type":"json_object"}`；output_schema / output_contract 位于消息数据中。本次调用没有通过请求参数要求服务端强制执行这份 JSON Schema，因此“提示里有 additionalProperties=false”不等于生成时绝不会多字段。[调用配置](../meeting_eval/model_client.py)第 13 行及 [目标契约](../meeting_eval/context_protocol_v5.py)可核对。本分析没有查询该模型服务是否另有可用的严格 schema 能力。

离线复现中，仅从内存副本删除对应多余记录键，三次 expand_checks 都从拒绝变为通过，确认了结构阻断原因。**这不代表三例整体已修好**：HT06 的修正结果已经把旧完成事件删掉，只修多余键仍会丢旧任务更新。CP02 则是主体任务正确，resolved/context_only 的非执行类别变化触发修正，最终产生无用的解释失败卡片。

后续应优先让输入中的只读参考与输出目标显著分离，并保留未知身份的严格拒绝。是否采用服务端 schema 约束需另行确认。不能把“丢弃任意额外字段”当通用修复，否则可能掩盖身份错配或真正遗漏。

## 三、引文是模型重新写出来的，而非稳定原文引用：2 次

**PF02 是新引文的改写错误。** 原句为“今天分别安排春季展会和秋季展会的准备工作。”模型为春季对象生成“春季展会的准备工作”作为 quote，该连续字符串出现 **0 次**。错误文案同时涵盖找不到和多次出现，但本例不是重复引文，补 occurrence 也不能解决。只在诊断副本中将这一处改为完整原句后，canonical_ledger 通过。

**CP07 是旧证据在第二窗口被改写。** 第一窗口保存的 quote 为“用户经常来问设备怎么恢复出厂设置”，位置 start=4、end=20。第二窗口复述 previous 时删掉“怎么”，却保留原位置；这种改写出现在四处引用。恢复这个词后，整个第二窗口 ledger 校验通过，说明前一窗口及位置本身没有错。

两例共同暴露了模型承担原文复制工作的脆弱性，但发生点不同：PF02 是首次选择引用，CP07 是重抄已经验证的历史证据。后续可考虑让模型选择稳定的证据 ID，旧账本由程序保管、模型只输出增量。逐字校验应保留；用模糊匹配放过改写会破坏可追溯性。[位置和引文校验](../meeting_eval/task_events.py)分别在第 44、78 行附近。

## 四、线程更新没有按原文顺序输出：1 次

C14 第二轮同一线程的更新位置是 **0 → 3 → 5 → 4**。最后一次更新回到已处理过的位置，canonical_ledger 以 Invalid or future thread update 拒绝。它不是引用未来证据，也不是条件意愿被误判为无条件任务；模型尚未进入任务解释阶段。

离线仅把这四次更新按 **0 → 3 → 4 → 5** 排列，该 ledger 校验通过。这确认了当前阻断项是顺序。后续应让原文位置参与增量结构的构造和检查，保留历史前缀不可变约束；不能据此推导所有历史更新都可随意重排。[顺序校验](../meeting_eval/context_state.py)位于 canonical_ledger 第 30 行起。

## 五、C03 的短切片和省略分工边界：1 次，需保留判断余地

C03 开头只有“Um for user interface, technical functions … what it'll actually do.”，后面是 Marketing 的明确分工。第一轮追踪已把 UI 记为 work，但解释认为它只是在描述功能范围，检查也支持，于是少了一项候选任务。

同一短输入第二轮保留了 UI；完整角色上下文 CTX 的两轮也都保留。CTX 多出的前文包含“在下一次会议前，作为工业设计师，你要做实际工作设计”等分工起点，使后续 UI 的省略更容易恢复。

因此可以确认“解释阶段对省略分工判断不稳定”和“短输入缺少前导分工句”。但不能确定截断是唯一原因，更不能把该片段描述成毫无歧义的直接指令。当前冻结标签要求 UI 候选，所以保留失败分；后续应先明确基准是否允许补充必要上下文，再验证模型恢复能力，不宜靠硬编码角色或关键词补任务。

## 验证范围与处理顺序

本次进行了 **6 次离线边界复现**：三次再检查越界、两次引文错误、一次顺序错误，均复现原拒绝，并验证只在内存纠正相应问题后能够通过对应结构校验。没有追加模型请求，没有修改生产算法、原始证据或评分，也没有将这些诊断副本计为成功。结果见 [offline-boundary-checks.json](../runs/2026-11-16-context-v5-failure-analysis/offline-boundary-checks.json)，可运行 [复现脚本](../experiments/task-boundary/replay_failure_boundaries.py)。语义原因通过原始阶段链、历史任务输入、成功对照和检查字段矛盾溯源，没有用结构通过冒充语义通过。

建议先处理影响最多的汇报分类及 record/event 结论一致性，再处理只读记录越界、证据历史复制和顺序构造。C03 另作输入／标签边界核对。修复 HT06 时还必须一起验证此前已复现的 Service 接入遗漏：context-v5 未被列入同段独立事件分支，即使模型正确输出新建和更新，仍可能被 create_update_conflict 双双阻止。这一服务缺陷不是这 12 次的直接触发项，不能加进失败次数，但会阻碍修复后的完整闭环。

不建议把所有问题统一归因于“模型不稳定”或“schema 不严格”：7 次有明确重复的语义误判，3 次有已定位的只读身份越界，另 3 次发生在追踪证据／顺序边界，C03 则涉及输入充分性。各类需要不同的修复与验证条件。
