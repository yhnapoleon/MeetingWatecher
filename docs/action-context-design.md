# 对话中的工作补全与待确认需求

2026-11-14。用户提出四项方向并授权调研、方案与检验。本轮选择新增实验策略 `context-v1`，默认保持 `split-v3`。

## 问题与判断

C03 的界面分工已被定位，却因省略动作被删除；C09 的任务只剩说明书对象，用户不使用说明书的研究问题消失。核验接受前一步解释，未恢复含义。当前事件契约要求完整动作，无法表达只有对象或尚在形成的需求。

四项建议合理，但需作如下区分：

- 指代同一实体、实体之间有关联、继承同一分工句式是三种关系。“界面功能”与“用户界面”可相关，不自动等同；同一实体也不意味着同一任务。
- 隐式需求指从问题或背景推测的工作目的；模糊工作指内容、指向、承接等仍有缺口。明确的工作也可能无人承接，分别记录内容类型与承接状态。
- 补全允许新增、纠正、否定及取消，不只是累积。晚来的“不是这个”“先不做”必须能改变最终输出。
- 提问针对具体缺口。纯实体保存在上下文中；会后只展示与后续工作有关的模糊项，不把所有名词都变成待确认任务。

## 研究依据与适用范围

1. [Purver et al., 2007](https://aclanthology.org/2007.sigdial-1.4/) 将行动项视作提出、讨论、分派、承诺的子对话，支持从整段互动判断工作，而非只找祈使句。
2. [CREAD, NAACL 2021](https://aclanthology.org/2021.naacl-main.265/) 联合建模指代和省略补全；这里借鉴“指向原文、最小补全”，不引入训练框架。
3. [Context-Aware Tracking, ACL Findings 2024](https://aclanthology.org/2024.findings-acl.127/) 逐轮维护关键短语，供后续省略和指代解释使用。这里采用带证据的实体与工作线索账本。
4. [Dialogue State Tracking with Incremental Reasoning, TACL 2021](https://aclanthology.org/2021.tacl-1.34/) 支持随对话更新需求状态；其多领域任务型对话结果不是本项目会议效果的保证。
5. [Clarify When Necessary, NAACL Findings 2025](https://aclanthology.org/2025.findings-naacl.306/) 讨论何时澄清及澄清与使用负担的取舍；本项目以缺少可执行信息或存在多种合理解释作为提问条件。

以上支持设计方向，是否解决现有失败仍由本轮实验决定。

## 方案选择

只修改解释提示最便宜，但无法保存无动作对象、观察后续补全。独立实体链接模型或完整知识图谱需要新增训练、消歧及维护机制，当前难例不足以支持这些成本。本轮采用已有模型与存储，新增轻量账本和明确的待确认出口。

## 实现契约

`context-v1`：按最多 8 个原文段落一个检查点读取累积原文 → 实体/指代关系/需求线索账本 → 全文解释 → 独立全文核验 → 原有任务规则与待确认列表。

- 账本保存实体 ID、原话提及、实体关系；需求线索保存稳定 ID、关联实体及按顺序追加的更新。每条更新绑定当时已出现的原话。每个检查点只提供截至该点的文本；旧更新不覆盖，纠正另加更新。
- 解释阶段输出完整事件与需求记录。工作描述允许恢复连续分工省略，保留目的、范围、约束；禁止把合理推测伪装成明确命令。需求记录类别为 `work`、`implicit_need`、`ambiguous`、`entity_only`。只有实体也可保留。
- 每个事件必须关联一条需求记录；隐式、模糊、实体类不能自动创建或更新任务。明确工作仍使用既有承接、身份、权限和旧任务关系规则。
- 核验分别检查事件字段和每条需求记录的依据、完整性、类别；不接受“前一步已删掉”作为理由。遗漏或核验不足进入待确认，核验不会自行编出新任务。
- 待确认记录保存原话、可能含义、缺口、确认问题及建议询问的提出方；明确标记推测。纯实体保存在 trace，不默认形成确认问题。
- CLI 展示并支持有权用户 `add_task` 或 `dismiss`；添加必须提供最终描述与已映射负责人，单独记录人工决策。该决策不伪装成会议中的承诺。支持 `ask_issuer` 生成待询问记录，不发送消息。使用原有意图、权限、回执恢复和幂等机制。源版本改变后阻止旧确认。
- 默认策略、旧实验原件和标签不变。新配置、代码及输出独立保存。

## 评测口径

旧 v2 任务标签照常评分，不因 C09 转待确认而改旧分数。另冻结“工作含义与处置”契约：C03 界面工作可为未承接分工；C09 至少保留用户看法/使用问题并提出确认；C20 文稿保留未知动作但不得创造整理/发送；C26 建议不自动建任务。此契约是根据用户产品方向新增的代理标注，不称为人工金标准。

先运行已有六例和连续分工视图各三轮，检查全部输出、遗漏、误报、调用和 token；另用事先冻结的中文合成对话验证实体同名但不同对象、后文补充/纠正/取消、跨检查点承接、无动作实体。合成检查只验证机制，不称为新系列盲测。

工程验证覆盖保存/恢复、权限、手动决定、重复确认与原有双会议回放。若仍有漏项或成本不合理，如实保留失败，不切默认策略。

## 实施顺序

1. 冻结本设计和检查契约，保留修改前代码快照。
2. 新增账本与分类/路由回归测试；实现 `context_state.py` 与 `context_pipeline.py`，接入 Extractor 和评测代码。
3. 实现待确认展示及人工决定 CLI，测试权限、版本、幂等和恢复。
4. 全量单元测试通过后，冻结代码与提示，运行三轮难例/上下文及合成补全检查；填写独立于核验输出的语义复核。
5. 汇报失败例、改法、实际输出、指标与成本，更新 HANDOVER。

重点检查：隐式需求不会因模型标为 accepted 而自动写入；词相近不会自动合并任务；被撤回的工作不创建；未获支持的推测只能以待确认形式展示；迟来的补充不能改写旧检查点的历史记录。
