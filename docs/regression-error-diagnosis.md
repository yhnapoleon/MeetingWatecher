# 六个难例的错误变化与前置能力缺口

2026-11-15。本次复查原话、阶段输出、冻结标签及程序路径，并做离线字段干预。没有重新调用模型或修改生产逻辑。比较对象是前置能力阶段的 `guarded-regression` 与旧任务更新阶段的 `regression`，不是默认 split-v3。

## 先纠正上一轮概括

“市场工作被核验否掉”不够准确。新输出认可该工作的内容、负责人、时间与状态，只有承接核验不通过。程序因此不输出任务候选，但待确认列表仍保存完整工作及承接问题。所以它是从任务清单退到待确认列表，不是信息被彻底删除。

市场工作后的“Okay”是否接受分工，冻结标签本就标有 `short_acknowledgment_acceptance` 不确定性。标签主判定为已接受，不代表这个判断是无争议的人类金标准。可确定的缺口是：即便承接有疑问，明确的分派也应能保留为待承接工作，而不是只能在两种输出结构间跳转。

## 错误具体怎样变化

六例输入、增量实体账本完全相同，冻结标签也相同；解释与核验重新生成。六例前后均有五条任务输出，其中四条内容完整正确，因此内容 F1 都为72.7%。这并不表示错误稳定或整体改善。

| 工作 | 前一版 | 当前版 | 变化所在 |
| --- | --- | --- | --- |
| C02 工业设计 | 正确提取 | 正确提取 | 核心结果不变 |
| C03 用户界面/技术功能 | 解释为模糊领域，无事件；核验指出应恢复分工但没有补回 | 恢复为明确分派，生成待承接候选 | 解释阶段改善 |
| C03 市场需求梳理 | 将营销人员的 Okay 判为接受，输出创建提议 | 解释仍判接受，核验判承接不足；不输出任务，保留确认卡 | 承接判断翻转，程序阻断任务输出 |
| C09 说明书研究 | 输出“看看说明书＋很少有人使用”的创建提议，缺少研究目的 | 描述仍不完整，又因缺具体日期不输出任务；确认卡询问下次会议日期 | 原内容问题保留，新增时间缺口阻断 |
| C20 视频剪辑 | 正确候选 | 正确候选 | 核心结果不变 |
| C21 整理意见 | 正确候选 | 正确候选 | 核心结果不变 |
| C26 会后细化场景 | 判 suggested，无任务输出，保留待确认 | 判 self_committed，形成团队候选，只问个人负责人 | 建议被提升为承诺 |

前一版正确的是工业设计、市场工作、视频、整理意见；当前正确的是工业设计、UI、视频、整理意见。前一版不合格的第五条是说明书研究，当前变成了会后细化场景。漏掉的目标从 UI＋研究目的，变成市场工作＋研究目的。两版都保存待确认记录，现有任务 F1 不衡量这些记录是否完整、有用，不能据此声称信息完全丢失。

## 第一类错误的三条实际路径

### 省略分工未恢复，核验发现也不能修正

C03 前一版原话是逐角色安排中的“for user interface, technical functions … what it'll actually do”。账本把它标为 ambiguous，解释沿用了这个结论，没有产生工作事件。核验反而指出它应恢复为用户界面/技术功能相关分工，但输出协议仅允许 verdict/issues，不能提供修正后的事件；程序也没有根据核验意见重新解释的步骤。最终只留下“具体要做什么”的问题。

这是两层问题：省略结构没有稳定恢复；发现错误后缺少有证据的修正通道。仅放宽核验不能凭空补出事件。完整分工窗口中有前面的工作句式，当前三项都提取正确，支持上下文有帮助，但不证明所有短片段都能唯一恢复。

### 内容已明确，承接疑点阻断整项输出

C03 当前版中，解释产生 UI、市场两个事件。市场事件的 work/owner/time/state/relation 五个核验均 supported，只有 commitment=accepted 被判 insufficient，理由是“Okay”不足以证明承接。

`task_events.py` 对新工作先要求 commitment 核验 supported；不通过就立即进入 pending，尚未走到 candidate 分支。反之，如果解释直接输出 assigned 且核验 supported，同一项工作就会成为候选。因此“确定尚未接受”和“不确定是否已经接受”得到不同结构，虽然两者都不足以自动创建。

离线干预保留原内容与负责人，只将有争议的 accepted 改为有依据的 assigned，任务输出从一条增为两条，均是 candidate。该检查验证了程序路径，不能证明模型能可靠做这个修正，也不能用于提高原实验分数。修复时应保留“明确分派、承接待核对”，不能直接把核验不通过改成通过。

### 一个非必要字段缺口阻断整项输出

C09 当前版六个事件字段全部核验 supported，但解释 record 自带 missing_fields=[time]。`context_state.py` 在进入事件处理前排除了有 time 缺口的记录；核验虽说相对期限有依据，却不会清除解释留下的缺口。

离线只移除这个日期缺口，保留原期限文字和 date=null，原程序即可输出工作。因此这里不是没找到任务或没认出期限，而是把“日期尚未换算”提升成了“整项工作不能保留”。说明书研究目的仍不完整，这个干预不是完整修复。

## 第二类问题还依赖哪些能力

| 前置能力 | 本次看到的缺口 | 应区分的结果 |
| --- | --- | --- |
| 明确动作、对象与目的之间的关系 | C09 保存了说明书与少人使用的背景，但没有明确判断它是否改变研究方向 | 已明确工作范围与待确认的研究目的 |
| 判断发言是建议、分派还是承诺 | C26 同一句“我们可以……”在两版变成不同类别；核验也跟随变化 | 提议存在与决定执行分别保存，不用“可以”单字硬判 |
| 将回应指向具体工作及当时范围 | C03 的 Okay 可回应分工，也可能只是确认接收邮件安排 | 谁回应、回应哪项内容、回应的是哪个版本；不确定就保留待承接 |
| 按对话时间补完范围 | C09 的 Okay 在“说明书”刚被提出、负面背景尚未讲完时出现 | 同意查看说明书不自动等于同意随后推导的完整研究目的 |
| 按真正缺口生成问题 | C26 当前只问谁做，实际还没确认是否决定做；CP06 问“是否推进、具体做什么、谁负责”，方向仍过宽 | 先确认是否需要、研究哪一方面，再补负责人 |
| 核验后维持字段一致 | C03 记录核验通过但事件承接不通过；C09 时间核验通过但记录仍缺 time | 已确认内容持续保留，疑点只约束对应字段和执行 |

当前账本有实体、同一/相关/不同关系及工作历史，但目的、回应对象、承诺范围主要存在于自由文本和证据片段中，没有可直接检查的独立绑定。这意味着实体保存是基础，却不足以单独解决“同意了哪件事、同意到什么范围”。

C09 可尝试问“这项研究重点是了解用户为什么不看说明书，还是改进说明书内容？”但这两个方向只能作为待选择的假设，不能倒写成会议已经明确的任务。原标签“研究使用者对说明书的看法”来自语料摘要；当前产品口径又要求推断目的先确认，需要同时报告任务指标和澄清质量，不能为追分强行自动创建。

## 第三类：指代与日期换算需要分开定位

“下次会前”确实依赖上下文中的会议事件，完整能力需要把它关联到下一场会议；若已有授权日程，应据此解析。当前模型输入只有当前会议日期/原话/人员和旧任务，没有下一场会议的日程字段或检索步骤，缺少这条能力。

但该失败样例中，模型已提取 time.kind=deadline、text=before the next meeting、date=null，核验也明确支持该期限。它并没有把“下次”指到另一场会议。直接新增的追问来自解释记录；新提示写着“set 时……date 不可确定时……询问具体日期”，同时又要求新任务期限用 set。这与原有“未知截止时间不必一律追问”相冲突，把旧任务改期要求扩散到了新任务。

离线移除日期缺口后工作恢复，验证了阻断位置。提示冲突与输出吻合，是有依据的解释；尚未做仅改该行、冻结其他模型输出的因果试验，所以不能声称已证明全部模型变化由这句话导致。

本次还检索了本地 AMI 原始 ES2004b 对话中 next meeting/thirty minutes/half an hour 及相邻句，只找到本段“下次会议”提问，没有找到可直接换算的时间锚点。这是有限关键词检查，不证明完整语料不存在其他表达；更不能用另一场 ES2002a 的“三十分钟”补这里的日期。现有输入本身没有下一场会议的具体时刻。

应分别记录：相对约束已明确、所指会议待绑定、日历日期待解析。没有日历日期不应自动使整个工作变为模糊任务；只有用户要精确提醒或平台写入确实要求日期时，才需要进一步确认。

## 归因边界与下一步检验

本次已确定三个程序边界：没有事件时核验不能补回；承接核验不通过会阻断候选；record 的 time 缺口会在事件核验通过时继续阻断。模型为何翻转 UI、Okay 和“可以”的判断，还不能分离提示变化与生成波动，因为解释和核验都重新调用过。不能把同分的两个结果解释成定向修复稳定有效。

后续实验应分别固定解释只换核验、固定核验只检查字段处理，再比较上下文长短；回应测试覆盖同人/他人、分工后/通知后、明确承接/仅表示听到。时间测试覆盖下一场会议已知、未知、多个候选及无需精确日期；目的测试区分明说、背景暗示和后续明确接受。候选保留、实际写入和确认问题分别评分，避免一个总分掩盖错误转移。
