# context-v2 残留错误的系统溯因

2026-11-15。针对 C19、HT04、C23、CP01 追踪原文、保存的模型请求/响应、确定性校验、修正计划和最终输出，完成 25 项离线诊断断言及一次恢复请求比对。新增模型调用为 0，生产源码、提示及原始实验产物未改。

**四例能定位到不同的系统边界，不能归结为同一种“模型不稳定”。** C19/HT04 有可确定复现的协议和状态路由问题；C23 是解释阶段内容遗漏且核验放过；CP01 是背景与潜在需求的政策边界没有在各阶段形成一致判据。严格校验避免了错误执行，但部分错误会在进入修正前结束整条行动项流程。

## 1. 从用户结果定位错误产生位置

| 样例 | 原本应得到什么 | 错误最早出现的位置 | 后续为何没有解决 |
| --- | --- | --- | --- |
| C19 | 保留会后整理问题、请老师解答、整理问答稿并发布的工作 | 首次解释用同段重复的“会后”作时间证据，未标出现次数；恢复后又产生多余对象确认 | 第一次在引文定位退出；第二次核验已否定确认，但少填派生的 question issue，再次退出，均未进入语义修正 |

## 2. C19：引文定位负担、协议重复表达与无反馈恢复叠加

原文同一段包含两次“会后”。首次解释已经生成完整的工作含义，只有 event.time.evidence 使用 `quote="会后"` 且没有 occurrence。`align_spans` 无法选择位置，因此拒绝整个解释结果。

保持其余响应完全不变，仅分别补 occurrence=1 和 occurrence=2，解释校验均通过，得到原有 2 条记录、1 个工作事件。这个实验证明首次失败的直接原因是证据定位协议，不是模型没有理解工作；它不表示可以在生产中任意选择出现位置。[定位代码](../meeting_eval/task_events.py)、[诊断结果](../runs/2026-11-15-context-v2-diagnosis/summary.json)

证据接口没有统一：核验阶段已经使用程序提供的 Q 编号，解释与修正仍要求模型自行复制逐字引文，并判断短语重复次数。证据必须精确是必要约束，但查找、引用与语义判断目前捆在同一次生成中，一个时间字段的定位错误会丢掉该阶段全部工作输出。

实际恢复没有定点补这个字段。原请求与 retry 请求逐字相同，没有把校验错误回传给模型；整个解释被重新生成，从 1 个工作事件变为 4 个，还为“两位老师”新增 reference 问题。该变化只能证明重抽样会改变任务粒度，尚未重新评判这 4 项是否应拆分，不能把结构通过当作语义正确。[恢复请求核对](../runs/2026-11-15-context-v2-diagnosis/resume-audit.json)

之后核验已经指出“两位老师”不构成需要追问的对象歧义，输出 `issues=["reference"]`、gap unsupported 和 clarification not_needed。代码还要求撤回问句必须另填 `question` issue。只追加这一标签就通过核验校验，并正确将 R2 列为修正目标。这是同一纠正意图在多个字段上重复编码后发生的脱节。[一致性校验](../meeting_eval/context_coverage.py)

**系统问题已确认：**恢复只重发请求，未区分传输恢复与结构纠正；协议中可由变更推导的 issue 仍要求模型重复填写；初次核验异常发生在 plan_repair 之前，导致修正机制无法接管它。该诊断没有生成后续修正答案，故不能声称 C19 已修复。

## 3. HT04：真实的用户待决定事项，被混入系统解释失败

该例有两条旧任务，摘要、负责人和期限完全相同，GUID 分别为 H-HT04 和 H-HT04-other。原文只说“上周说的那项……我已经做完并发群了”。解释阶段正确输出 relation=ambiguous，保留这两个选项的具体问题，没有猜选一个任务。

核验阶段的四种表述却不一致：

- gap verdict=supported：确实存在关联缺口。
- gap blocking_for=none：声称这个缺口不阻断。
- clarification=needed，fields=[relation]：又要求用户选择。
- record verdict=insufficient，event.relation verdict=insufficient：把无法唯一执行关联同时作为核验不足。

第一处矛盾由 `validate_clarification` 正确拒绝。离线仅把 blocking_for 改成 operation 后，结构校验通过，但仍会把 R1 列为修正目标；将该核验状态直接送入 reducer，得到的是 interpretation_unresolved，而不是原有的具体关联问题。实际重新运行仍可能通过模型修正改变此状态，离线实验没有预测那份新答案。

再做两个诊断干预：让 record verdict 表示“准确记录了歧义”，改为 supported，具体关联问题恢复且禁止添加任务；event.relation 仍为 insufficient 时，修正计划仍会启动。进一步让 event 核验支持“ambiguous 是忠实的状态”，才不再无故修正，执行仍被 relation=ambiguous 阻断。这里的 supported 变更是人工设置的诊断状态，不是可以无条件应用的归一化规则。

**系统问题已确认：**“原文理解是否忠实”和“是否具备唯一执行条件”没有在 verdict、修正触发和 reducer 中形成一致定义。提示已允许 supported + needed，但事件核验的 relation 说明仍强调唯一关联，计划又以全部事件字段 supported 为成功标准。`record_content_supported` 对 relation issue 的处理还会把关联不确定升级为整体解释争议。[修正触发与路由](../meeting_eval/context_v2.py)、[内容支持判定](../meeting_eval/context_state.py)

解决方向应是让关联状态承载“需用户选择”，让核验判断该状态是否忠实，执行器继续阻止非唯一更新；不能简单忽略 relation 失败或自动选择第一条旧任务。

## 4. C23：两份工作描述发生内容漂移，支持性检查未发现不完整

原文：“还有其他几个问题，会后我们单独再联系刚才袁校长，那个讲的过程中，你这个信号也没有太听清。……所以稍后会单独联系。”

同一次解释输出了两份描述：

- record：会后联系袁校长，沟通其他问题，括号中还保留“讲解过程中信号不太清楚”。
- event.work：会后联系袁校长，就其他几个问题继续沟通。没有未听清内容。

最终 item 原样取 event.work.description。仅把 record 描述补完整，item 完全不变；仅替换 event 描述，item 随之改变。由此排除 SQLite 或纪要渲染在最后截断内容：缺失已发生在解释生成事件时，reducer 只是选用了它应使用的字段。[item 生成](../meeting_eval/task_events.py)

核验把两份描述都判 supported，甚至写“联系对象、目的和时段已明确”，coverage_findings 为空。提示本来就要求目的范围完整，因此这不是“完全没有写完整性要求”；实际缺口是完整性只存在于长提示中的文字要求，没有单独留下“原文哪些必要内容必须在最终任务保留”的可审计判断。record、event 各自看起来有依据，并不保证 event 表达充分，也不保证两者含义一致。

**已确认：**两份描述有差异；最终任务取较短版本；内容核验和遗漏核验均未拦住。**仍属机制假设：**模型可能把“信号不清”仅当背景，或者核验受到已有简化描述影响。没有独立输入对照，不能宣称已证明锚定效应，也不能断言换模型或增加推理预算就能解决。

解决方向是确定最终任务内容的权威表示，保留有证据的动作、对象、必要目的和范围，并让完整性核验直接面对即将生成 item 的内容。不能只美化 record 或纪要，也不能要求把所有背景都塞入任务。

## 5. CP01：背景与潜在需求的判据不一致，修正没有形成有效关闭

跟踪器先将“设置页有一些开关名称还没统一”记录成潜在统一命名需求。解释输出 R4 implicit_need，并询问是否安排统一命名。第一次核验明确要求改成 context_only；修正阶段却只删去 owner 缺口、保留 scope 和 implicit_need；再核验重复否定这个分类。最终没有虚构新任务，但多留了一条系统解释未解决项。

生成方并非毫无依据地违反全部提示：跟踪提示写“当前问题背景与讨论目标有关时仍保留 implicit_need”；解释提示写“仅从孤立抱怨设想一项从未安排的行动时，才用 implicit_need/inferred 并提问”。核验提示也保留了相近规则，却在本例以“没有提出后续动作”否定潜在需求。**有无显式动作不足以区分背景与 implicit_need，否则隐式需求这个类别本身无法成立。**[跟踪规则](../prompts/track-context-context-v1.txt)、[解释规则](../prompts/interpret-work-context-v2.txt)、[核验规则](../prompts/check-work-context-v2.txt)

对照 CP06 能看到更有用的分界：它不只说用户不看指南，还明确说该现象关联“减少重复咨询”的目标，并把“尚未确定要做什么”留作讨论事项。CP01 则围绕功能清单补范围，命名现状没有被明确提升为另一个希望处理的目标。这个差异支持“是否把问题带入共同待处理目标”作为候选判据，但还需要更多对照验证，不能仅凭这两例写成关键词规则。

离线提供一份人工确认的 R4 context_only 修正和相应通过核验后，既有身份检查、合并和 reducer 可以正常关闭它，主任务完全不变。因此排除了“覆盖每个 thread 的约束必然迫使它留作需求”以及“合并代码不能降为背景”这两种解释。当前 proposed_kind 是建议；已有记录必须经过实际重写和再核验才能关闭，第一次和第二次核验同意背景并不会直接覆盖仍为 implicit_need 的修正记录。

**系统问题定位：**分类依据在各阶段存在未消除的解释空间；修正再次使用同一套宽泛规则，容易重复最初解释；单次预算后的保守处理会将这类政策争议暴露给用户。不能直接采用 proposed_kind 或隐藏待审项充当修复。优先需要统一潜在需求资格，再验证有限修正能否按这一资格收敛。

## 6. 修复顺序与检验边界

建议先处理协议和状态语义，再调任务分类提示，避免继续用更多提示条款补偿程序边界。

1. **精简核验协议并区分失败类型。** 确立缺口判定的唯一来源，可推导的字段由程序生成；保留真正矛盾的拒绝。区分证据定位错误、结构不完整、语义争议和真实用户选择。结构纠正需要保留原语义并带具体错误反馈，不能仅原请求重抽样。是否允许记录级隔离应按记录依赖设计，不能让互相依赖的更新部分执行。
2. **分开忠实性、用户待决定状态和执行资格。** 用 HT04 检查：两条同名旧任务时输出具体选项、不自动更新、不将正确歧义反复修正；同时保留错误关联被拒绝的反例。
3. **统一最终工作内容并检验完整性。** 用 C23 检查目的是否真正进入 item；同时验证普通背景不会被扩写成新的行动。保留两套原标签和旧结果，不能通过改评分对象让 trace 抵消 item 的缺失。
4. **明确背景与隐式需求的共同判据。** CP01 应关闭额外需求，CP06 的目标相关需求必须保留；再覆盖具体合作邀约、孤立抱怨和真实工作建议，防止简单收紧边界导致漏项。
5. **减少解释阶段的自由引文定位。** 比较程序生成的稳定证据编号或更明确的引用选取约束。需要保留精确证据能力，且重新检验引用粒度是否足以支持 owner、time 等字段；仅把引文放宽为模糊匹配不解决问题。

本轮完成的是根因定位和机制验证，没有实施上述修复，也没有新增真实模型结果。不能从离线人工干预推导未来通过率。原始跨会 M2 两轮通过的结论保持不变；本轮确认的是其他残留需要在协议、状态和语义表示层面继续处理。
