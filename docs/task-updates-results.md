# 旧任务更新：改期落地、保留历史字段和减少多余确认

实验目录日期为 2026-11-14，文档于 2026-11-15 完成。`context-v1` 现在可以把会上确认的新期限更新到原任务，明确取消期限时同时清除日期与日期原文；只汇报进度时保留汇报，不再要求重新承接。默认策略仍为 `split-v3`。当前是本地 CLI、SQLite 与任务模拟器，真实飞书读写尚未验收。

## 从一个失败看问题

HT07 中负责人说：“三个登录失败案例还没整理完，截止时间改到2026年11月20日，我会在那天下班前发到研发群。”旧流程识别到修改，却没有真正修改任务日期，只留下通用确认。另一个场景 HT08 只是汇报进度，也被问是否承接已经负责的任务。

这里有两个不同原因。解释阶段混用了历史属性和本次修改，旧日期没有本次引文就可能阻断完成更新；执行阶段只支持完成与重开，识别出改期也无法落地。与此同时，旧任务沿用了新任务的承接要求，产生多余追问。上一轮隔离的历史日期提示实验解决了第一部分，本轮把它合入并补齐字段更新。

## 调研与实现

[SOM-DST](https://aclanthology.org/2020.acl-main.53/)先判断槽位操作，再生成变更值；[RFC 7396](https://www.rfc-editor.org/info/rfc7396/)区分字段省略与删除；[Clarify When Necessary](https://aclanthology.org/2025.findings-naacl.306/)研究何时澄清才有收益。本项目据此选择显式字段操作，并按缺少的信息生成问题，具体设计见[方案](task-updates-design.md)。这些来源支持设计方向，不构成本项目效果的实验证据。

时间字段现在区分四种操作：没有变化则保留，明确改期则设置，明确取消则清除，尚未决定则待确认。未出现的字段不改写，未知日期也不等于取消日期。完成/重开仍更新状态，普通进度单独进入纪要。

每项状态或日期修改都有自己的原文证据。改期单独检查负责人是否在对应证据中确认，不能借相邻的进度发言冒充改期承诺；执行前继续检查唯一目标、身份、权限、受众和预期旧值。旧值已改变则阻止覆盖，写入后回执丢失则先回读。

内容修改、换负责人等暂未支持的操作单独列为“执行受阻”，显示原因。该类记录只能忽略，不能借人工入口另建一条任务，也不让用户重复解释已经清楚的要求。混合“改内容＋改日期”时可以只执行符合条件的改期，同时保留内容修改未执行的提示。

独立代码审查发现：初版会把解释后的工作描述同步到任务标题，从而在改期时暗中执行内容修改。补失败测试后移除了标题更新，限制允许字段为状态、日期及日期原文。代价是旧标题可能仍含历史期限；当前期限以结构化日期字段和纪要中的更新为准。

## 实验如何比较

冻结历史日期八例，增加试探改期、取消期限、无人承接改期、非日期修改四例；代码审查后另加混合修改 TU13，并在其模型调用前冻结。前后共用相同十三例契约，要求真正检查任务存储中的日期和状态、确认入口、创建数及拒绝原因。TU13 是追加的审查反例，不是盲测。

旧八例基线复用上一轮原始模型输出，五个新增例在旧代码上运行。修复版复用跟踪、事实和决策输出，重新调用解释与核验，从正常 Service 入口进入新数据库。最后一版只修改程序判断，复用修复版全部模型响应重新执行。因此最终十三例说明同一批模型输出经修复后满足定向契约，不能称为十三次全新独立模型成功。

| 阶段 | 十三例通过数 | 失败与恢复 |
| --- | ---: | --- |
| 旧代码、新契约基线 | 3/13 | 原有日期证据失败、引用失败、改期未执行与多余确认 |
| 初版修复首次 | 11/13 | HT06 继承原引用结构失败；TU11 缺少可操作的改期确认卡 |
| 初版一次结构恢复后 | 12/13 | HT06 恢复成功；TU11 保留失败，未重采样 |
| 最终程序重放相同响应 | 13/13 | 零新增模型调用；含 HT06 恢复后的响应 |

TU11 中模型误借负责人对进度的确认，把主持人提出的改期判为承诺。执行层已经阻止写入，但初版没有给出后续确认入口。最终在生成更新前增加同样的字段证据检查，保留具体问题“负责人是否确认将这项任务的截止日期改为2026-11-20？”。

| 代表场景 | 最终可观察结果 |
| --- | --- |
| 完成旧任务 | 更新原任务状态，保留历史期限，不重复创建 |
| HT07 明确改期 | 日期实际写为 2026-11-20，原任务身份不变 |
| HT08 普通进度 | 留下汇报，无多余承接确认 |
| TU09 试探改期 | 不改日期，询问是否确定采用已提出的日期 |
| TU10 明确取消期限 | 日期与日期原文同时清空 |
| TU11 无负责人确认 | 不改日期，保留明确确认问题 |
| TU12/TU13 不支持的内容修改 | 原标题不变，显示未执行原因；TU13 的明确改期独立落地 |

完整 M1/M2 回放另做两次。初版首次在 M1 核验 JSON 解析失败，尚未生成验收结果；保留首次响应并恢复一次后为 12/12。最终代码使用全新模型调用，首次 12/12，无恢复。两次不能合称首次全过。

## 回归表现及局限

六个既有难例首次均完成结构处理，内容 F1 为 72.7%，完全正确召回 4/6；连续分工完整窗口三项工作均正确。这里同样冻结了上游输出，只重新调用解释与核验，不能据此声称独立全流程稳定性提高。语义由代理复核，旧标签未改，不是人工金标准。

六例的总分与上一版局部对照相同，但错例发生了变化：短片段 UI 恢复了，市场工作却被核验拒绝；C09 研究目的仍未补出，对“下次会前”还多问了绝对日期；C26 把“我们可以……”提升为团队承诺并形成候选，冻结标签不将其列为行动项。候选没有写成真实平台任务，但仍属于误报。完整窗口成功也不能抵消短片段的遗漏。

本轮未解决同一任务收到多个相互矛盾的最终更新：目前第一项可能执行，第二项被旧值检查拦住；尚无统一裁决契约。未确认需求仍不自动跨会议继承。结构生成仍出现过引用和 JSON 失败，实际飞书的原子更新也尚未验证。以上限制及标题保留历史日期的问题，使本轮结果不足以切换默认策略。
