# 自然会议上下文跟踪恢复

2026-11-17。跟踪恢复修复已实施：4 个既往失败样例均完成全文跟踪，3 个整场处理完成；GN29 仍被后续解释阶段的预算/证据引用错误阻断。本次只处理自然会议评测的原因1：跟踪输出的编号、引用或增量结构出错后，整场任务提取被阻断。任务分类、承诺判断和标注保持不变。当前实现为可选 context-v5 的 version 14，默认策略仍为 split-v3。

## 为什么旧机制容易中断

GN25 只有约 1,733 个参考 token，却有 93 段短发言。旧方案每 8 段检查一次，预定 12 个节点；每个节点都携带此前全文和累计状态。一次响应把原文发言尾号当作 Q 证据别名，重试后又更新了不存在的 T6/T7，整场未能进入任务解释。GN26 的严格工具响应仍把要求的 entity_ids 数组写成 entity_id 单值，本地校验正确拒绝了它。

这些失败既涉及模型生成格式，也涉及系统把新增编号、证据别名、线程挂接和历史追加同时交给模型维护。短回应越密集，固定段数分块产生的节点越多。仅增加重试次数或切换严格工具输出，不能消除这种负担。旧失败原件保留在 [诊断索引](../runs/2026-11-17-generalization-v1/failure-diagnosis.json)。

## 调研及移植选择

| 官方项目 | 相关处理方式 | 本项目采用方式 |
|---|---|---|
| [LangGraph Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers) | 保存步骤状态，恢复时复用成功节点 | 复用现有 accepted.json 和节点锁；每个检查点原子保存进度、最后有效状态与未处理尾部 |
| [LangGraph Fault tolerance](https://docs.langchain.com/oss/python/langgraph/fault-tolerance) | 按异常类型配置有限重试；节点重放仍须考虑外部副作用 | 内容失败才允许缩小窗口；支付、权限和限流不触发二分；沿用 Service 幂等任务写入 |
| [Pydantic AI Retries](https://pydantic.dev/docs/ai/core-concepts/retries/) / [Output](https://pydantic.dev/docs/ai/core-concepts/output/) | 验证错误反馈模型，限制输出重试次数 | 保留本地强校验和已有预算，进一步减少需要模型生成的结构字段 |
| [LlamaIndex SentenceSplitter](https://developers.llamaindex.ai/python/framework-api-reference/node_parsers/sentence_splitter/) | 根据内容长度、句段边界分块 | 借鉴完整文本边界分块；使用原始发言边界和 UTF-8 文本字节数，未照搬其 token 分词器 |

本项目已有持久化阶段执行器，整体迁移框架不能直接解决上述协议错误。因此移植执行原则并复用现有机制，没有增加框架依赖。

## 实际改动

模型只提供对象标签、语义更新、原始 segment_id 证据，以及要更新的既有线程。新增 N/T 编号、逐字证据和更新位置由程序生成；去掉跟踪阶段的 Q 别名。新线程必须含有更新，更新必须引用当前窗口至少一段原文，不能重写历史。每次提交仍经过完整校验。

检查点从每 8 段改为最多 6000 个 UTF-8 **文本字节**、最多 128 段。完整原始发言不截断；单段过长则独占窗口。这是新增文本量的控制，不是整个请求的 token 硬上限，累计全文与 ledger 仍会增长。

节点耗尽原有内容预算后，仅 schema、语法或输出预算错误允许按发言边界二分一次。一个根窗口最多产生父、左、右三个节点，各自遵守原有请求预算。左侧接受后再处理右侧；右侧仍失败则保留已完成前缀、待处理尾部和失败节点。不能跳段，也不会把尚未读完后文的前缀任务发布出去。

恢复时按同一计划重放成功缓存；只有失败节点需要追加请求。Service 的显式授权续跑和任务写入幂等机制保留。跟踪参数、协议版本和新增模块代码哈希都进入缓存身份。

## 验证与证据

离线定向 89 项测试通过，新增协议/恢复测试先观察失败再通过。覆盖原文 ID、程序编号、只读历史与取消更新、密集短发言、超长单段、有界二分、叶失败保留前缀、显式续跑、支付/传输错误不二分、未完成跟踪阻断解释，以及 Service 重复续跑不重复建任务。见 [测试日志](../runs/2026-11-17-tracking-recovery-v2/targeted-tests.txt)。独立上下文只读审阅未发现阻断问题，范围和未验证项见 [复核记录](../runs/2026-11-17-tracking-recovery-v2/code-review.md)。

真实测试仅取旧冻结输入 GN25、GN26、GN29、GN38，沿用原模型、推理配置和正常 Service 入口，SQLite Simulator 写入；标签不进入请求。原 60/115 例均未重跑。初轮出现 HTTP 402：GN25/GN26 跟踪完成，GN29/GN38 分别停在 228/398、99/126 段。用户授权补充余额后续测。

402 在生产执行器中是终止状态，不会自动恢复。实验续测在新副本中归档经 HTTP 元数据核实的 402 节点，随后调用相同配置的 Service.process；成功节点缓存不清除。原初轮、归档错误、续测新增调用分别保留。这个维护入口不能描述成生产系统自动检测充值并续跑。

20 个成功跟踪节点全部通过，无内容类跟踪失败。二分恢复本轮没有实际触发，其有效性来自离线故障注入，不能将 4 例成功说成真实二分恢复已验证。连续覆盖与输入/标签/源码一致性见 [覆盖审计](../runs/2026-11-17-tracking-recovery-v2/payment-resume/coverage-audit.json)。续测前已接受节点对应的 26 份 metadata 哈希全部保持不变，确认成功节点没有重发模型请求；GN29、GN38 从原有前缀继续完成尾部。

最终还逐个核对成功节点内请求文件集合没有增加，当前仅GN29解释节点等待恢复；检查结果见 [最终验证](../runs/2026-11-17-tracking-recovery-v2/final-verification.json)。

GN29 的阻塞已越过跟踪阶段，发生在 interpret_work：首次达到输出长度上限，原有预算恢复后的响应引用 Q587 等不存在的证据；该请求目录仅有 395 个 Q 别名。解释阶段仍使用原来的 Q 协议，本次没有替换它。这表明同类编号混用在另一阶段仍然存在，不能把跟踪通过写成端到端可靠性已经解决。两次失败响应保留于 payment-resume/natural/GN29/model 内。

任务级复核按原冻结规则：10 TP、6 FP、10 FN，P=62.5%、R=50.0%、F1=55.6%。这些是 **4 个已知失败回归样例** 的识别结果，不是 40 场自然会议的新成绩。旧 4 例全部无任务输出；本次没有重算或替换旧正式成绩。GN25 一条输出同时完整包含首版分析和组内讨论，按两个目标匹配；其条件性支付目标也保留，但负责人字段不能据此声称正确。

剩余 10 个 FN 中，8 个来自 GN29 的后续技术中断；GN26 将电子反馈只保留为 proposal；GN38 没有收录会后发送文字记录。6 个 FP 均在 GN38，主要来自把政策延续/执行安排收为确定工作，其中考试沟通和维持 8 月放榜节奏按两个目标拆开。政策/任务边界存在标注选择，尤其“学院下周细化支持安排”按非与会者承接排除，与允许组织具体工作计划的规范存在疑点。保留冻结计数及争议，没有追改标签。逐目标理由见 [匹配记录](../runs/2026-11-17-tracking-recovery-v2/payment-resume/task-matches.json)、[指标](../runs/2026-11-17-tracking-recovery-v2/payment-resume/task-metrics.json)。这部分只计任务识别，不作完整字段准确率结论。

初轮 33 次请求、976,893 个已知 token；用户授权续测新增 18 次、1,958,757 个已知 token，合计 **51 次、2,935,650 个已知 token**。其中 7 次 402 响应没有 usage，不能按已确认零计费描述；没有请求缺最终 metadata。累计账目保留的 7 个 terminal 节点均为归档支付失败，当前活动节点只有 GN29 一个 recovery_required，没有活动支付错误。GN38 解释阶段的长度耗尽已由原有恢复机制处理成功。

跟踪单独累计 22 次请求（20 个成功节点及 2 次支付失败），1,281,920 个已知 token。旧 4 例在失败前用了 62 次跟踪请求、2,339,935 个已知 token，但旧流程未完成全文，两者不能当作同等完成量的严格成本对照。GN29 新方案已处理到结尾，因此不能用它旧失败时的低用量证明新方案一定更省。协议简化与分块同时变化，本轮未做消融，不能分别量化各自贡献。
