# 行动项抽取退化诊断

2026-11-14。完整抽取器在同一开发集上的行动项 F1 从 72.0% 降到 70.0%。逐条核对显示，新增漏项是 C20 的剪辑视频承诺和 C21 的整理意见承诺；两条均被完整抽取器写入 facts，却没有进入 items。小规模控制实验支持提示词变更是这两条漏项的主要因素。另发现导入与校验的确定性名册错误，会拒绝片段中未发言参会者的合法负责人 ID。

## 分数差异来自哪些实例

| 指标 | 行动项基线 | 完整抽取器 |
| --- | ---: | ---: |
| 参考行动项 | 12 | 12 |
| 真阳性 TP | 9 | 7 |
| 误报 FP | 4 | 1 |
| 漏项 FN | 3 | 5 |
| 精确率 | 69.2% | 87.5% |
| 召回率 | 75.0% | 58.3% |
| F1 | 72.0% | 70.0% |

C03 删除了基线误报的说明邮件项，但原有两项分工仍未检出。C09 从不完整的行动项变为空；基线本来因核心句不符被记为一个 FP 和一个 FN，新版去掉 FP，却没有修复实际工作理解。C20 去掉了额外臆测的文稿任务，同时也去掉了正确的视频任务；C21 丢掉正确的整理意见任务。因此总体是少 2 个 TP、少 3 个 FP，没有新增命中的参考任务。精确率提高主要来自输出减少。

这两条新增漏项与核心证据选择无关，因为 items 整体为空。C09 则仍受严格核心句匹配口径影响，不能把它从有预测变为空解释成业务改善。

## 提示词与输出类别

C21 原话是“对，然后意见都非常宝贵，我们会整理出来。”基线将它识别为团队候选任务；完整抽取器只输出事实“发言者表示会整理会上提出的意见”。C20 的“后面的话我们会把这个视频剪辑，然后给大家确认”同样被写进事实。模型读到了承诺，却未把它列入可跟进清单。

基线专门提取行动项，逐项说明团队承诺、未承接指派、身份未知和简短回应。完整提示词将这些规则压缩，同时要求生成 items、facts、unresolved、decisions、updates 五类结果，但没有明确说明：一项承诺写进 facts 后仍必须出现在 items，缺账号或暂不可执行也不能取消候选任务。实际输出与类别间漏分配一致。

为区分输入与提示词，选择出现变化的 C02、C07、C20、C21，共发起 13 次诊断请求。所有请求使用原完整抽取器的模型参数：deepseek-flash、temperature=0、thinking disabled、max_tokens=6000、JSON object；均正常停止，返回模型及服务指纹相同。每次请求与响应保存在 [诊断目录](../runs/2026-11-14-extraction-diagnosis/)。

| 条件 | C02 | C07 | C20 | C21 |
| --- | --- | --- | --- | --- |
| 原完整抽取请求重跑 | 0 项 | 3 项，ID 正确，工作时段误作期限 | 0 项 | 0 项 |
| 只换回行动项基线提示词 | 1 项 create | 3 项，ID 正确，期限为空 | 2 项：恢复视频任务，也恢复文稿误报 | 1 项候选 |
| 只换回原始公开输入 | 1 项 create | 0 项 | 0 项 | 0 项 |
| 只补齐完整名册 | 未运行 | 3 项，ID 正确，工作时段仍误作期限 | 未运行 | 未运行 |

前三组各请求 4 个片段，最后一组只请求 C07；未使用答案构造请求，未改动业务提示词或应用代码。结果见 [results.json](../runs/2026-11-14-extraction-diagnosis/results.json)。

对 C20/C21，提示词替换恢复检出，而原始输入替换未恢复，支持优先处理提示设计。实验同时改回了任务目标、规则详细程度与输出格式，尚不能单独量化“多任务输出”和“规则压缩”各自的贡献。每个条件只做一次，不作为新版本整体分数。

## 确定性名册错误

C07 的原始 participants 包含四个参会人，但 normalize 只从实际发言段填充 roster，因此 roster 仅剩项目经理 FEE005 和营销 MEE008，漏掉未在片段发言的工业设计师 MEE006、界面设计师 MEE007。模型输入同时出现完整 participants 与不完整 roster，身份信息不一致。

更直接的问题在 validate：合法负责人集合只取 roster。将原基线 C07 的三条正确负责人预测装入完整抽取格式，校验直接报 `Unknown person reference`。[可复现记录](../runs/2026-11-14-extraction-diagnosis/boundary-reproduction.json)

本次重跑完整请求时，模型恰好生成了正确的 MEE006/MEE007；这些结果也会被当前业务校验器拒绝。故该问题不限于模型偶尔漏填字段，是必须修复的输入契约错误。它没有造成原先两条新增中文漏项，也不能单独解释 C07 的三条 ID 都为空；其中营销 ID 本来就在 roster，说明模型提示及单次输出波动也参与了字段错误。

## 其他变化与结论边界

C02 从已承接的 create 退为 candidate，原话中的“Yep”未被稳定用于判断承接。C07 把午饭后的工作时段填进 due_text，而基线三项均为空。这些字段退化不会改变核心证据检出 F1，所以只看 72.0% 与 70.0% 会遗漏实际行为变化。

所有原始完整抽取响应均有效、无截断，评分拿到的 items 与模型原始响应一致，未见任务在 SQLite 写入或权限后处理阶段被删除。开发片段的 history 为空。模型名称和服务指纹相同，没有证据支持把差异归因于换模型、历史检索干扰或输出 token 不足。

重跑完全相同的完整请求，C02 从 1 项变成 0 项，C07 从负责人为空变成正确 ID；本环境下 temperature=0 没有得到逐次一致的结果。因此 2 个百分点只是这两次运行的观察，不足以证明稳定总体退化。C20/C21 在原始运行、完整请求重跑和原始输入对照中都漏项，诊断证据比单次总分更明确。

## 修复顺序

1. 从完整 participants 建立统一人员表，保留未发言参会者，校验与模型输入使用一致的已知人员集合。用 C07 正确 ID 可被接受作为回归。
2. 把行动项检出作为明确的独立步骤，保留基线的完整候选规则。纪要可以复用行动项结果；不能因已写成事实、缺账号或缺期限而漏掉可跟进承诺。若仍用单次完整输出，先针对这些类别边界补规则验证，不能仅恢复文稿误报换取召回。
3. 固定其他条件，检查 C02 承接、C07 人员与期限、C20/C21 团队承诺，再完整复跑 21 个 dev 片段，分别报告检出与字段结果。保留原预测，不动 holdout，不改评分口径掩盖回退。

本轮只进行了诊断与实验留档，应用中的名册错误及提示词尚未修改。
