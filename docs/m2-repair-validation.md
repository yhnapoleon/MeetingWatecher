# 跨会 M2 修复方案：实验结果与实施设计

2026-11-15。当前结论：**优先修正现有核验与遗漏处置协议；不接入额外分类器。M2 尚未达到修复验收标准。** 本轮完成了三个真实模型实验和一个记录级程序原型，生产源码与提示未修改。局部核验方案能改善冻结输入上的 M2，但仍有指代误判和输出协议冲突，不能据此宣称完整跨会流程已通过。

## 1. 为什么先修核验与状态流

原始 M2 中，陈可汇报三个登录失败案例已发研发群，王宁随后说：“登录改版第一批的范围今天改一下，内部员工和试点客户都开放。”场景要求前一句完成同一旧任务、保留原期限，后一句替代旧范围决定；原文没有另派人改配置等实施动作，因此不应多出任务或负责人确认。

本轮 `merge/M2-blind-r1` 提供了完整的失败链：独立分类将范围句判为 context_only，合并解释也保留该判断；核验却以“今天改一下”为理由改判工作，同时把同句列为遗漏。一次修正后，最终仍有 R2 分类争议和 U 遗漏两张确认。`merge/M2-visible-r1` 的最终 R2 已恢复为受支持的 context_only，却仍留着 U 确认。前者说明上游分类正确不能保证最终正确，后者证明遗漏状态需要独立关闭机制。

| 类别 | 系统原因与证据 | 修复位置 |
| --- | --- | --- |
| 决定被改判为工作 | 核验将改变范围值理解为另有落实动作；冻结核验对照中，旧提示两次均把正确 context_only 否定 | 明确决定与实施动作的核验依据；修正后仍按原文复核 |
| 已失效遗漏持续存在 | 首次 uncovered 只有整段引用，没有工作身份与处置结果；repair 不重新核验它 | 用 finding 身份、对应关系和处置核验替代永久保留的裸引用 |
| 系统解释争议变成用户问题 | R2 没有得到可靠解释，却问用户“这项工作”由谁执行，预设了任务存在 | 分开核验“内容成立”和“确有用户待决定缺口”；系统争议保留 unresolved |
| 普通省略被误当阻断缺口 | P07b 的安排与本人接受已明确，仍因“这个场景”未展开而被阻断 | 逐字段核验缺口是否成立、阻断内容还是平台操作 |
| 核验字段相互矛盾 | 新核验 P07b-r1 将 reference 判 unsupported，却将原来带 reference 的记录判 supported | 在程序边界拒绝矛盾结果，要求修正原记录，不能直接相信 verdict |
| 输出契约不统一 | 新旧遗漏协议叠加后，同段真实遗漏两次均未输出兼容字段 uncovered_spans | 采用单一版本协议、单一完整示例；旧协议只在版本边界转换 |

最后一项是本轮实验提示新增的协议冲突，不能算作原生产实现已有的新失败。原生产另有 time.change/other_changes 示例缺字段、重复短引文和 speaker 元数据被当正文的独立问题，详见[前轮系统调查](m2-system-diagnosis.md)。本轮没有重测这些结构方案。

## 2. 调研如何影响设计

会议行动项研究将任务描述、时间和承担者放回对话上下文分析，支持这里把“发生了范围决定”与“有人承担实施动作”分开检查；它并不能替本项目的 M2 标签提供正确率保证。[Purver 等，SIGDIAL 2007](https://aclanthology.org/2007.sigdial-1.4/)

Chain-of-Verification 在事实核验中使用独立回答核验问题的方法，减少先前回答对核验的影响。这为本轮 visible/blind 对照提供了假设，但论文测试的任务不是会议工作提取，所以本项目仍需检验后续合并会不会重新引入错误。[Dhuliawala 等，ACL 2024](https://aclanthology.org/2024.findings-acl.212/)

DeepSeek 的 JSON Output 负责合法 JSON 输出，官方仍要求提供 JSON 示例并设置合理输出预算。合法 JSON 不意味着必填字段齐全、引用正确或分类正确，因此结构校验与语义验收分开；本轮沿用当前端点与 json_object，没有混入 strict API 或模型迁移。[DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)

## 3. 本轮怎样检验

全部运行位于 [2026-11-15-m2-repair-study](../runs/2026-11-15-m2-repair-study/)。[执行计划](superpowers/plans/2026-11-15-m2-repair-validation.md)、输入、提示、配置、首次请求/响应、源码快照及用量均保留。使用当前 deepseek-flash，分类与核验 thinking=disabled、temperature=0、max_tokens=16384；合并解释及修正沿用 compact-check 的原配置。所有首次失败计入，没有结构恢复或追加抽样挑结果。

### 3.1 前序解释是否影响分类：16 次调用

冻结失败 M2、明确改灰度配置的正例、C20、P07b，各做两轮 visible/blind。两组原文、名册、tasks 历史、证据目录、提示及参数相同；visible 额外收到冻结的 ledger/records/events，blind 没有这些输入。实际 request 的八组比较确认，差异只有 upstream 字段。

| 分类阶段整例通过 | visible | blind |
| --- | ---: | ---: |
| M2 | 0/2 | 2/2 |
| 明确落实正例 | 2/2 | 2/2 |
| C20 | 0/2 | 0/2 |
| P07b | 0/2 | 0/2 |

visible 的 M2 两次都把范围决定当工作；blind 两次正确。C20-visible 保留文稿 unresolved，blind 则虚构“整理文稿并给大家确认”；两者都判失败。P07b 两组都保留了不必要的对象缺口。该小样本支持“前序解释输入会影响此处判断”，不能泛化为去掉前序解释总是更好。

按实验前门槛，blind 的 M2/正例两轮通过、各轮总分更高，且 C20 视频工作和 P07b 承接没有丢失，因此进入同下游合并实验。这里的晋级仅是允许继续检验；C20 幻觉没有被当成改善。

### 3.2 分类结果经过相同合并、核验和一次修正：43 次调用

两组都将原文、冻结的首次解释及各自分类建议交给同一合并提示，再走现有 ContextPipeline 的真实核验、最多一次 repair/recheck 和 reduce_context。跟踪结果使用已验证的冻结 ledger，未重跑 tracker；没有调用 facts/decisions、Service 或写入跨会数据库。这是任务处理阶段的集成实验。

| 最终任务处理阶段整例通过 | visible | blind |
| --- | ---: | ---: |
| M2 | 1/2 | 1/2 |
| 明确落实正例 | 2/2 | 2/2 |
| C20 | 1/2 | 2/2 |
| P07b | 2/2 | 1/2 |
| 合计 | 6/8 | 6/8 |

M2 的四次均生成了同一旧 GUID 的完成更新，未生成改期限指令，但第一轮两组都留不当确认。落实正例四次均保留唯一灰度配置/发测试工作，负责人陈可，期限“今天下班前”、2026-11-16。C20-visible-r1 的修正输出了错误 case_id，程序保留首次结果，文稿错误提问也随之保留；该例按失败计。P07b-blind-r1 的核验理由甚至写明“指代省略不构成必须补齐的缺口”，但 verdict 支持原记录，程序仍被 reference 阻断。

因此，**C3 不接入生产**。它在分类阶段的优势没有转成稳定的最终结果，还要额外增加分类和合并两次调用。两组的后续合并也会自行改变分类建议，不能把最终收益全部归因于分类器。

### 3.3 直接调整现有核验协议：28 次调用

在相同冻结首次解释上，对照当前核验与增量协议，各两轮。除四个原样例外加入三个保护输入：明确未决定选登录还是支付场景、明确“文稿也发给大家确认”、范围决定同段另安排陈可发测试结果给客服。保护输入在调用前冻结；同段任务故意不放入原 records，用于检查真正遗漏。

| 检查对象 | 当前核验 | 新核验协议 |
| --- | --- | --- |
| 原始 M2 | 两次均否定正确范围分类并重复标遗漏 | 两次支持 context_only，无范围缺口、无遗漏 |
| 明确落实正例 | 两次支持真实工作 | 两次仍支持真实工作，无额外范围任务 |
| C20 文稿 | 两次要求改原模糊记录，但一轮理由仍推断文稿继承确认动作 | 两次明确建议 entity_only，不为文稿补动作或问负责人 |
| P07b 普通省略 | 两次支持原错误 reference 缺口 | 第一轮 gap 判对但与 verdict 矛盾；第二轮仍认为缺口成立，均未通过完整契约 |
| 真实对象竞争 | 原带 reference 记录仍被支持；一轮理由却称其非必要缺口 | 两次明确 content 阻断，只问登录还是支付 |
| 明确文稿发送 | 两次保留视频与文稿工作 | 两次保留视频与文稿工作 |
| 同段另一项工作 | 两次返回整段 Q2 遗漏 | 两次给出正确独立工作 description/new_work，但漏 required uncovered_spans，首次结构校验失败 |

该实验同时改变语义说明与输出协议，因此只能说明组合方案改善了冻结 M2；不能归因到其中某一句提示或某个新增字段。新协议需要单一结构定义，不能继续在旧示例后叠加相互冲突的要求。P07b 的两次结果进一步说明：给模型增加判断字段有诊断价值，但不会自动使判断正确。

新协议首次校验为 12/14 通过，2 次失败均为同段遗漏的缺字段。随后追加无模型调用的一致性审计，又检出 P07b-r1 的 verdict/gap 矛盾；原始结果未改写，见 [alignment-audit.json](../runs/2026-11-15-m2-repair-study/alignment-audit.json)。**本批未达到七例两轮全部通过的接入门槛。**

## 4. 可实施的修复方案

推荐沿用现有流水线，不增加常驻分类阶段。先将协议变为可验证的单一契约，再检验含义正确率。

### 第一部分：统一核验结果与澄清资格

record check 保留 verdict/issues，增加 proposed_kind、gap_checks 和 clarification。proposed_kind 只提出建议；实际 records/events 必须经过一次修正和再核验。gap_checks 表示缺口是否有依据、阻断内容还是平台操作，不能仅因转写没有展开对象名称就阻断。

程序在消费前校验：原 missing_fields 每项都有结果；原缺口被判 unsupported 或不再阻断、原问句被撤回，或 proposed_kind 改变原分类时，原 record 不能同时 supported，必须有对应修正 issue。这样 P07b-r1 会成为明确的协议失败，而不是继续保留旧 reference。protocol failure 不自动应用建议。原文确有两个未选定场景时，保留 content 问题；内容明确但缺个人账号时，沿用候选及具体负责人确认规则。

若修正后仍存在分类争议，阻止该项自动操作，显示原话和解释未解决的事实，不预设“这项任务”的负责人；该例仍算失败，不能因错误问句减少而通过。其他已核验工作和旧任务更新继续独立保留。

### 第二部分：给遗漏工作建立身份和处置结果

首次核验输出 coverage_findings：description、evidence、relation、related_record_ids。服务端按源版本和首次核验快照固定 O1/O2；身份为 `(scope, finding_id)`，不能只用段号、描述 hash 或裸 O1 跨会议合并。

一次修正的目标为失败 records 与 finding 关联 records 的并集；即使没有失败 record，只要有 finding 也应进入修正。允许在预分配命名空间 R_O1_1 等新增记录；同段第二任务保留独立身份。未选择记录保持原值，原记录线程和事件身份保持。

每个 finding 必须有 covered/added/rejected/unresolved 处置。再核验既验证对应关系，也验证最终记录；只有两者通过才关闭。已有受支持记录被修改坏时保留原记录，依赖它的 finding 仍未解决。无效新增不成为工作，结构失败保留首次有效快照。待确认区与纪要共用 finding 身份，只呈现一份残留。

### 第三部分：一次性替换新版本输出协议

新版本只向模型要求 coverage_findings，不再同时要求旧 uncovered_spans=[]；兼容旧结果应放在版本明确的程序边界。用一份机器可验证的 schema 生成完整输出示例。time.change、other_changes、case_id 与引用字段纳入同一验证顺序；先检查结构，再进行精确证据定位。

引用改为服务端生成的证据 ID 是独立实验，不与当前语义改动捆绑。正文位置与 speaker 人物元数据必须分开，重复短语由确定性位置区分。当前客户端的 strict API 支持尚未实测，不能作为已验证方案写入发布条件。

### 第四部分：接入顺序与验收

| 顺序 | 改动 | 必须看到的结果 |
| --- | --- | --- |
| 1 | 独立版本 schema、完整示例、核验字段一致性校验 | 缺字段与 verdict/gap 矛盾被明确拒绝；真实字段未丢失 |
| 2 | 新 checker → 一次 repair/recheck → 原 reducer 的实验适配 | M2、落实正例、C20、P07b、三个保护例各两轮首次通过；结构失败和 unresolved 均计失败 |
| 3 | findings 的固定目标、新增命名空间和处置再核验 | 纯遗漏可补回；同段真任务不被去重；错误遗漏可关闭；失败处置保留一次残留 |
| 4 | Service 入口的 M1→M2 与落实正例 | 同 GUID 完成、due_date/due_text 保留、决定替代、权限隔离、重复与重启幂等；零范围候选/错误确认/U残留 |
| 5 | 受影响的全体 context 回归 | 30 段语料、33 例对照及旧任务/条件/长上下文等路径无新增退化，保留原与审计口径 |

下一批实验先改统一 schema，保留本批全部失败；P07b 要在同一批同时测试普通省略与明确竞争对象。不能清空 reference 列表，也不能只修提示让 M2 一次通过。后续任何提示调整都使用新批次、同预算两轮首次结果。

## 5. 程序原型已验证到哪里

[repair_contract.py](../experiments/task-boundary/repair_contract.py) 是记录级契约原型，覆盖 plan_repair、apply_repair、route_record 与 validate_check_alignment。[26 项测试](../experiments/task-boundary/test_repair_contract.py)全部通过，包含遗漏单独触发计划、同段第二任务、有效新增/拒绝/覆盖、失败新增、受支持目标退化、未选记录保持、真实对象缺口、负责人缺口及解释争议路由。

测试实际发现过两类程序问题并修正：关联记录退化时，rejected 处置仍误关 finding；原记录被 supported 的同时又建议移除其缺口或改变 kind。独立审查进一步发现“缺口仍 supported 但不阻断、原问句已撤回”的同类漏洞，也已补失败测试并修正。失败与通过日志均在实验目录。另有 134 项现有程序回归通过。

原型验证的是**已得到核验结果之后的记录状态规则**。它不判断模型给出的对应关系是否语义正确，也未接入事件身份分配、平台写入、恢复、确认卡或纪要；`needs_repair` 证明修正计划应触发，不等于生产流水线已经调用了新增分支。本轮没有重新验证 Service 跨会验收，现有生产实现也尚未获得这些原型能力。
