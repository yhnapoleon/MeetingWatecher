这些语料已在前期调优中被查看，本次是回归测试，不能当作盲测。190 是执行次数，只有 95 个场景，且部分专项与服务链复用基础输入。原文复核由助手完成，独立代理抽查评测代码和证据，不是独立人工标注集。

## 五项修改在全量数据中的表现

1. **已决定的范围变更保留为任务。** M2、同段混合任务及完整服务链均保留内部员工、试点客户和“今天”，缺个人时只问负责人。明确陈可接受修改灰度配置并发测试时，范围变更与落实步骤合为一项任务。两轮完整服务流程共 4/4，通过旧任务完成、决定替代、重复处理和重启无重复写入检查。个别“今天”留在描述而非日期字段，符合运行前冻结的时间可见标准，不能声称日期字段全部完整。
2. **程序绑定新增记录身份。** 本轮没有观察到 introduced_by 缺失引发的合并失败；这只说明本批未复现该故障。仍有模型在再次检查时返回不属于目标记录的字段，属于另一处输出契约问题。
3. **待定事项仅收集。** 两轮专项补充 12/12。明确暂缓的监控面板没有生成任务或即时追问；同会后文决定推进后转为工作；没有日期的已承诺工作继续保留。跨会议自动激活不在已实现范围内。
4. **固定检查槽位仍有协议失败。** 三次 check_repair 返回只读记录的检查字段，严格校验拒绝，未静默放过。固定 schema 尚未保证模型总能遵守目标边界；此外追踪阶段还发现两次引文错误和一次线程更新乱序。本轮未进行同口径版本对照，不能量化该改动的改善幅度。
5. **C23 放宽推断目的要求后通过。** 原 C23、明确补问目的正例、无关背景反例，两轮共 6/6。明确说“补问没听清的问题”时保留该动作；报名问题反例没有添加补问义务。普通 C23 不再因为缺少推断目的而失败。

## 22 次失败的具体来源

以下按首先阻断结果的原因互斥分组；同一例可能还伴随其他语义问题，详见逐例记录。

| 主要原因 | 次数 | 场景 |
|---|---:|---|
| 超时或连接失败 | 11 | 第一轮 C15、C17、P05b；第二轮 C11、PF02、TU09、TU11、P03b、P05b、P06b、R03 |
| 再检查越出目标记录范围 | 3 | 第一轮 CP02、HT06；第二轮 HT06 |
| 追踪阶段证据或顺序不合法 | 3 | 第一轮 PF02；第二轮 C14、CP07 |
| 任务／汇报语义错误 | 5 | 第一轮 C03、HT05；第二轮 C17、HT05、P11a |

**完成汇报被当成普通背景，是最应优先修正的共同原因。** HT06 的原话同时包含“上周三个登录失败案例我已经发到研发群了”和新的支付案例任务。两轮都正确创建了新任务，但检查器认为前半句“没有新的跟进动作”，把旧任务完成报告判为 context_only，触发修正；再次检查又多返回只读记录字段，最终旧任务没有更新。HT05 的第三方完成报告两轮分别丢失确认入口、退成 interpretation_unresolved。C17 和 P11a 第二轮也把“已发纪要／正在放共享文件夹”合并为背景，reports 为空。它们共同混淆了“没有新任务”和“没有可追踪的完成或进展信息”。

**再检查输出越界有直接原始证据。** 第一轮 CP02 只需重查 R2，却返回 R1；第一轮 HT06 多返回 R2，第二轮 HT06 多返回 R1，均报 Unexpected proposal fields。CP02 的任务本身已正确保留，但留下解释失败条目，仍计失败。该问题不能归因于新增记录缺 introduced_by，也不能把接口收到响应当作通过。

**三次追踪错误并不相同。** 第一轮 PF02 把“今天分别安排春季展会和秋季展会的准备工作”改写成引文“春季展会的准备工作”，该连续字符串在原句中不存在，匹配次数为零；此前“重复引文”的初步诊断已更正。第二轮 CP07 在第二窗口复述旧 ledger 时，删掉引文中的“怎么”，却保留 start=4、end=20，导致引文与原文切片不一致。第二轮 C14 的线程更新位置依次为 0、3、5、4，最后一项倒退，违反顺序契约。三者都在追踪校验处中断，尚不能据其空任务结果判断语义能力。

**C03 是一次可观察的漏提。** 第一轮保留 Marketing 需求思考任务，却把 UI 技术功能安排当背景；第二轮两项均保留。完整角色上下文 CTX 两轮也均保留 UI 任务，说明上下文和生成波动与该现象有关；仅凭两轮不能确定单一因果。

**网络失败独立计入总分。** 11 次场景执行涉及 12 次请求失败，TU09 同时发生 facts 超时和 track_context 连接断开。其余包含读取超时及 SSL EOF，不能归为漏任务，也未用重跑成功替换首轮失败。仅移除这 11 次网络失败后为 168/179（93.9%），该数只帮助区分故障来源，不替代 88.4% 的整体结果。

## 终审另发现的服务写入缺陷

独立审查发现 service.py 的独立事件分支列出了 context-v1 至 v4，却遗漏 context-v5。因此同一段中，同一个人完成旧任务并接受另一项新任务时，v5 会回落到“负责人相同且共享证据即冲突”的旧规则。即使提取正确，也会同时阻止创建和更新。

离线固定正确抽取结果，经正常 Service.process 和临时 SQLite 复现：输入“上周的登录案例我已经发到研发群了。另外我来整理支付案例并发到客服群。”，v4 将旧任务改为 done 并创建新任务；v5 返回 processed、无提取错误，却留下 create_update_conflict，旧任务仍 open，且未创建新任务。此检查不调用模型，也没有修改生产代码。

本轮 190 次结果中没有进入该冲突分支：HT06 更早被完成汇报分类错误阻断；S-same-segment 中旧任务更新位于另一段，所以也未覆盖这条路径。该缺陷单独报告，不混入已冻结的 190 次评分。建议后续先补上 v5 的策略接入与同段创建／更新写入回归，再继续修正模型分类。复现脚本及输出见 [服务冲突复现](../runs/2026-11-16-context-v5-full/review/reproduce_shared_evidence_conflict.py)。

## 重复稳定性与运行证据

95 个场景中，78 个两轮均通过，12 个一轮通过一轮失败，5 个两轮均失败。重复失败的是 C17、PF02、HT05、HT06、P05b；其中 C17、PF02 两轮的失败原因不同，不能直接称为五个稳定语义缺陷。HT05/HT06 的汇报分类问题两轮均出现，P05b 两轮均受网络影响。

模型调用共 983 次，971 次收到响应，已记录用量 4,186,590 tokens。两轮模型运行用时 2,015.232 秒（约 33.6 分钟），单场景耗时中位数 30.0 秒；该时长不含随后原文复核和报告整理。未进行实际飞书写入，任务操作均在独立 SQLite 模拟器中验证。

运行结束后重新执行 205 项项目测试、33 项实验测试，全部通过。运行前 source.zip 中的 54 份生产代码及提示与当前工作区逐字节一致，各输出保存的流水线代码摘要也与快照匹配。评测适配与汇总脚本不改变被测算法。

建议下一步先修复上述确定性的服务策略接入遗漏，并统一各阶段对旧任务完成／进展汇报的分类，再处理再次检查的目标记录边界，以及追踪状态复述导致的引文和顺序错误。网络失败需要另做受控复测以判断持续性；本轮证据不足以断言由并发数或服务限流导致。后续验证应使用新目录，保留本轮所有失败和评分。
