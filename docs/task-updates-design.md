# 旧任务的字段更新与必要澄清

2026-11-14。用户授权调研、方案、实验并修复。沿用 Python/SQLite 的 context-v1，默认 split-v3 不变，真实飞书不在本轮范围。

## 依据和选择

[SOM-DST](https://aclanthology.org/2020.acl-main.53/)先预测槽位操作，再生成需要改写的值；本项目借鉴逐字段操作，不引入训练模型。[RFC 7396](https://www.rfc-editor.org/info/rfc7396/)区分省略字段与 null 删除；本项目采用显式 keep/set/clear/uncertain，避免模型的未知值触发删除。[Clarify When Necessary](https://aclanthology.org/2025.findings-naacl.306/)强调澄清的收益和交互成本；本轮以实际缺口决定是否追问，不将执行能力限制伪装为用户表达不清。

已有 HT07 明确改期但只得到通用确认，HT08 汇报旧任务进度却被追加承接缺口。共同原因是旧任务继续走新任务承接逻辑，且执行层仅支持状态更新。仅补提示无法支持改期；任意字段补丁会扩大权限和模型出错范围。本轮选择 context-v1 专用的日期操作，加现有完成/重开状态；暂不支持换负责人、泛化任务内容修改。

## 数据和行为

合入已验证的 current-time 提示。在 context-v1 事件 time 中增加 change=keep/set/clear/uncertain：未提出变化 keep；明确新期限 set；明确取消期限 clear；试探、条件或多种日期未确定 uncertain。set 必须有当前 deadline 原文和可解析日期；clear 必须有取消期限原文，不能从 null 推断。核验 time 同时判断 change 是否忠实、是否已决定。

旧任务关系唯一且内容/状态/时间受支持时：

- progress 或普通继续执行且 keep：保留汇报，无新写入、不询问承接。
- completed/reopened：生成状态修改，历史期限保留。
- set/clear：已明确承接/本人决定且各字段通过核验，生成日期修改；未决定则具体问是否改期/改到哪天。
- revised 但没有支持的日期操作：保留为 execution_blocked，说明当前不支持该类变更，不问笼统问题，不允许转成新任务。

日期写入包含 due_date 与 due_text，清除时一起清除。独立审查发现同步摘要会放行混合内容修改，因此最终不修改 summary。当前日期以结构化字段为准，纪要明确展示新日期；旧摘要可能保留历史日期，是本轮限制。other_changes 显式保存 content/owner/other 等未支持修改，即使与改期同句出现也显示未执行原因。每个修改字段保留当前证据。任务状态与日期可一次共同变更，未出现字段不写入。

Service 继续检查唯一目标、负责人本人汇报、账号映射、任务/来源写权限、受众范围。新日期变更单独检查其证据中的负责人，不能借旁边的进度发言冒充改期承接。记录预期旧值和新值；发送前旧值或负责人已变则阻止覆盖。回执恢复仍先回读，重复处理不重复写入。旧 evidence-v1 reducer 不变。

结构更新验证入口严格检查允许字段、日期组合和字段证据，禁止未知字段。context 协议升级，旧缓存不会绕过新解析。

## 检验方案

先写失败测试再实现：进度不多问；set/clear 正确落地；keep 不改日期；uncertain/缺日期不写；组合状态日期；未知字段、无证据及矛盾字段拒绝；同名目标、代报、权限和受众限制；已有值变化与回执恢复；暂不支持操作明确显示且不可新建。

实际模型：冻结沿用历史日期八例并增加含糊改期、取消期限、无负责人支持的改期、非日期修改四例。新预期要求 HT07 真正改日期、HT08 无确认。保留旧八例原评分，另算新契约基线。当前代码重放固定旧解释作机制对照，再从正常 Service 入口跑新协议；保留首次失败，至多一次结构恢复。原有六难例和连续分工做回归，完整 M1/M2 回放验证生命周期。合成数据和既有样例不称盲测。

独立代码审查关注字段权限、状态/日期互不污染、旧流程兼容与重试；修复所有重要发现。使用 before/final 源码快照替代 Git。结果如实报告；未达到质量门槛不切默认。
