# 统一复评与独立工作发现实验

> 后续用户裁定：M2 范围调整可以是有时间约束的执行工作；C23 推断目的不再作为单独不通过项。本文分数保留原实验口径，不代表新标准下的总通过率。当前定义和具体溯源见 [用户裁定后的修订](review-feedback-diagnosis.md)。两次 Incomplete event checks 经原始响应复查，实际是多生成 E2，而非漏 E1。

2026-11-16。本轮要确定后续从哪个版本继续，并验证独立读取原文能否补回上游漏掉的任务。结论是：**历史 v2/v3/v4 按相同新增标准复评后为 4/4、3/4、2/4；新增来源清单未改善最终产物，A 的正常入口也仅通过 2/4。A 与新增方案均不晋级，不扩大实验。**

## 1. 先看一项已发现却没有补回的工作

原文在范围决定后追加：“另外，陈可今天下班前把测试结果发给客服。”冻结输入故意不提供这条任务记录，预期产物应是一条负责人陈可、期限为当天的发送候选，只确认承接，同时完成原有案例整理任务。

本轮 A 第一轮已经正确发现这项遗漏。修正也生成了正确的新工作，再核验支持其动作、负责人和期限；最后却在合并时因缺少 `introduced_by` 失败，最终用户仍看不到发送候选。第二轮 A 同样发现遗漏，但再核验多输出了只读记录，报 `Incomplete record checks`。证据见 [A-r1/G-omitted](../runs/2026-11-16-baseline-reassessment/small-v1/A-r1/G-omitted/) 和 [A-r2/G-omitted](../runs/2026-11-16-baseline-reassessment/small-v1/A-r2/G-omitted/)。

这改变了本轮的诊断重点：历史三轮 A 没发现遗漏，本批两轮发现了，却无法完成修正。后续需要分别统计“发现”“生成补充”“再核验”“最终可用”，不能把最终没任务都归为来源发现失败。

随后用已记录的 A-r1 修正与再核验输出做零调用检查：原样经过现有 `check`、`apply_repair` 为 invalid；仅给 `R_O1_1` 补上与处置对应的 `introduced_by="O1"` 后，合并变为 checked，遗漏清零。这只定位了确定性合并的阻断点，未执行新的模型修正或完整 Service，也未改原评分。见 [离线字段干预](../runs/2026-11-16-baseline-reassessment/binding-counterfactual.json)。

## 2. 统一历史 M1/M2 标准

离线读取 v2/v3/v4 各四次已有 Service 回放，保留记录中的任务更新、决定替代、权限、历史、幂等与重启检查，再按同一 `full_flow_checks` 补查 M1/M2 是否有解释未解决、修正失败或提取错误。本步骤没有重跑模型或历史数据库；各来源文件 SHA-256 已保存。

| 历史版本 | 去掉新增六项后的旧契约 | 加入 M1/M2 完整检查 | 新检出的失败 |
| --- | ---: | ---: | --- |
| context-v2 | 4/4 | **4/4** | 无 |
| context-v3 | 4/4 | **3/4** | positive-r1 的 M1 再核验漏/多记录，`Incomplete record checks` |
| context-v4 | 4/4 | **2/4** | positive-r1 修正缺必要问题；cross-r2 再核验出现非法 gap field |

三份新增失败都留下 M1 `interpretation_unresolved` 和失败修正。v4 原 summary 已包含新增检查，因此表中的“旧契约”是明确移除这六项后的复算结果，不是将原文件的 2/4 改写为 4/4。完整证据见 [离线复评](../runs/2026-11-16-baseline-reassessment/offline/summary.json)。

该表只统一了已有四次回放的验收范围。v2 的 C19、HT04、CP01、C23 等扩大回归问题仍存在；它不是所有场景的综合冠军。v3 在其中部分样例上已有改进，所以仍可作为继续开发的代码基础，但须保留 v2 作为历史跨会强对照。

## 3. A 与来源清单 D 的同批对照

A 是原实验中的 `PromptOnly(ContextV3Pipeline)`。D 在 A 首次核验前增加一份独立来源清单，输入只有原文、授权历史任务和 Q 证据目录，不看 ledger、records、events 或标签。首次核验将清单与已有记录对齐；后续修正、再核验和归约仍走 A。清单无权直接生成任务或覆盖分类。

四例各两轮，双方使用相同冻结上游和推理配置。每轮“已有第二工作”和“故意遗漏第二工作”的原文及历史相同，共用一份来源清单，以控制来源阶段波动。D 同时增加了清单和对齐提示，因此结论针对整个增量机制，不能单独归因于多一次调用。

| 最终产物，四例各两轮 | A | D |
| --- | ---: | ---: |
| M2 范围决定，零额外工作或问题 | 1/2 | 0/2 |
| 明确改灰度配置并发测试 | 2/2 | 2/2 |
| 上游已有同段第二工作 | 2/2 | 2/2 |
| 上游故意遗漏同段第二工作 | 0/2 | 0/2 |
| 合计 | **5/8** | **4/8** |

自动契约后逐份复核最终正文、负责人、日期、承接状态、旧任务 GUID、实际更新字段及额外问题；独立来源审查得到相同分数。原自动评分只检查数量和部分操作，无法独立验证这些语义条件，不能将其布尔值当完整质量证明。见 [逐份来源复核](../runs/2026-11-16-baseline-reassessment/small-v1/source-review.json) 和 [独立审查](../runs/2026-11-16-baseline-reassessment/independent-review.md)。

六份来源清单全部把范围决定放入 works，两个 G 清单都发现了发送测试结果的工作。按本次实验当时的标准，D 最终仍在 M2 上把范围当工作；G-omitted 第一轮修正输出了只读记录，第二轮首次核验多输出输入中不存在的 E2，触发事件集合校验失败。新增来源阶段未解决已发现工作的落地问题。范围工作是否成立的业务评价以后续用户裁定为准。

本批 A 的八份首次核验请求，与历史 A 对应例的请求内容、推理参数完全一致；返回的模型标识与 fingerprint 也一致，结果仍发生变化。见 [请求一致性比较](../runs/2026-11-16-baseline-reassessment/a-request-comparison.json)。这支持保留多轮结果和失败分母，但不能据此断言模型服务发生版本变更。历史 A 的 18/24 与本批 5/8 的样例范围和轮数不同，也不能直接比较百分比。

## 4. A 的正常 Service 入口

本轮以实验适配将 Extractor 实际导入的 context-v3 Pipeline 替换成 A，继续经过真实跟踪、解释、核验、facts/decisions 分支、Service 与新 SQLite 模拟库。运行目录的 `adapter.json` 记录适配方式，M1/M2 trace 的 protocol 必须实际为 `context-v3-coverage-prompt-control`；不会把 `--arms A` 错用到旧 runner 固定的 v4 回放入口。

| A 正常入口 | 完整检查 | 具体结果 |
| --- | --- | --- |
| cross-r1 | 失败 | M2 完成原任务并替代决定；M1 再核验本应只检查 R2，却同时输出只读 R1/R3，留下解释未解决 |
| cross-r2 | 失败 | M1 同上；M2 首次核验 `Incomplete event checks`，提取 partial，原任务未完成 |
| positive-r1 | 通过 | 保留唯一陈可改灰度配置并发测试任务、2026-11-16 期限，原任务完成、决定替代及完整检查通过 |
| positive-r2 | 通过 | 同上；M1 曾修正，但修正和再核验成功，无解释残留 |
| 合计 | **2/4** | 普通跨会 0/2，明确落实正例 2/2 |

四次 trace 均证实 A 适配生效。普通跨会第一轮及两次正例的旧任务期限日期和 `due_text` 保留；cross-r2 因未完成更新而仍是原 open 任务，不能把期限没改当作完成成功。通过的正例也经过权限、历史、重复处理、重启、决定替代等检查。见 [总汇总](../runs/2026-11-16-baseline-reassessment/summary.json) 与各运行目录。

这四次是本日的新调用，历史表是对昨日记录的离线复评。共同验收标准有助于找出失败位置，但四次小样本、运行时间及上游输出差异不足以给出全版本统计排名。所有首次失败保留，无恢复、无追加抽样。

## 5. C23 的标签边界

独立审查先只看到原话，没有读取旧标签和报告，随后才查看明确目的及无关背景对照。盲审认为，原话明确承诺“会后单独联系袁校长”；联系很可能也为处理刚才未听清的内容，但把“补问未听清内容”强制作为任务必需义务，存在解释边界。

| 来源 | 本轮复核后的边界说明 |
| --- | --- |
| C23 原文 | 联系、其他几个问题、听辨不佳是明确内容；其目的关系有合理语用推断，但不宜未经共识当成唯一解释 |
| C23-paraphrase | 同样依赖语用推断，旧计划已标记 source ambiguity |
| C23-explicit | 明确说“把没听清的问题补问清楚”，该目的必须保留 |
| C23-unrelated | 明确已听清，联系是谈报名问题，不能增加补问目的 |

本轮没有修改标签或重新记分，旧 C23 失败仍保留。该复核说明需要先明确评测对合理推断的要求，不能证明模型已经修好 C23。后续应将“明确要求必须保留”与“语用关系是否准确理解”分开评估，保持明确目的和无关背景对照。

## 6. 本轮产物与下一步

新增内容限于实验脚本、实验提示、边界测试和文档。49 个生产源码/提示文件与 v4 的 `final-source.zip` 字节一致，默认仍为 `split-v3`，没有注册 A 或 D 为生产策略。现有 198 项回归与新增 4 项实验边界检查通过。独立审查发现的 Service 早期异常漏记分已加包装，并保留先失败、后通过日志；来源异常捕获也已补齐。实际批次没有触发该早期退出，不改变本轮模型请求或分数。

本轮共 **80 次真实调用、454,426 tokens**，80 次均收到响应，无传输失败或恢复调用。小集含来源阶段共 32 次/190,076 tokens；四次 A Service 合计 48 次/264,350 tokens。独立来源阶段自身为 6 次/7,379 tokens。离线复评、语义审查和字段干预均未额外调用项目模型 API。上述 token 统计来自项目模型 meta，不含 Codex 会话及审查子任务自身用量。

下一步应优先处理已定位的修正契约：新增记录的 finding 绑定、只读上下文与待核验对象的边界、record/event 检查集合的完整性。将“模型已经给出正确工作，却因为确定性身份字段丢掉”的输入先固定为离线复现，再单独检验修正方案。决定与实施分类仍需语义对照，程序契约改善不能替它得分。本轮 D 未过门槛，停止扩大到完整 30 语料及其他回归集。
