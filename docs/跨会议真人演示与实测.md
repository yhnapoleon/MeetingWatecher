# ES2002b → ES2002c 跨会议演示与实测

已接入同一团队连续两场真人会议，前端默认提供 13:02 的节选演示，包含跨会导航、前后决定对照、原任务进展和可定位的原话。后端另用两场完整人工逐字稿完成真实模型试验，第二场经一次失败阶段恢复后为 processed。**旧决定能正确重申，但新供电方案没有更新有效决策；本场纪要任务还被误关联到上场纪要任务，跨会语义正确性尚未通过。** 在独立的“已确认历史任务”对照中，三位成员的汇报均关联到正确任务，未重复新建，但其中一项完成判定需复核。

这份报告分别记录预设演示、完整模型试验和带模拟确认的定位对照。演示中正确出现的事件不计入模型成绩。

## 失败阶段恢复与新增发现

在首轮数据库副本上调用现有 `Service.retry_extraction`，沿用相同配置及冻结上下文，仅增加一次 `check_work` 请求，151.71 秒、239,349 token，结果 **processed，errors=[]**。其他阶段复用已保存结果；首轮数据库、结果和前两次截断响应不改写。首轮加恢复共 58 次请求、6,130,738 token。恢复结果、正常重复提交和数据库重开一致，重复提交没有模型调用。

恢复后保存 3 项任务：原有项目经理的 2 项任务，以及 David 新增的“核实材料组合”。三位成员的研究汇报均识别出来，但历史中没有已确认的对应任务，因此 `target_guid` 均为空；这些汇报没有触发重复新建。决定分支保持原结果，新供电方案仍只见于事实摘要。

核查同时发现两个需要区分会议阶段的关联问题：

| 实际关联 | 原话与交付物差异 | 判断 |
| --- | --- | --- |
| c 场“尽快整理本场纪要”作为 report 关联到 b 场纪要任务 `SIM-e5576747c90f` | b 场 `B.303` 指 b 场纪要；c 场收尾 `B.318` 指 c 场纪要，是不同会议的文档 | 误关联，且未为本场纪要形成独立任务 |
| c 场展示下一阶段工作，将 b 场“提供下一阶段指示”任务 `SIM-ba8a673c3c24` 标为 done | b 场 `B.304–308` 对应概念研究；c 场 `B.313–315` 指下一次 Play-Doh 设计阶段 | 阶段不同，当前完成依据不足，需复核 |

这说明仅按负责人和相似动作匹配不够，会议纪要、周期性汇报和“下一阶段安排”需要保留各自的会议或交付物范围。上述问题是实际保存输出的核查结论，本轮没有修改提取提示词来重新跑出更好的分数。

## 展示与实测分开

前端沿用已授权的纯展示方式，增加双场时间轴和跨会追踪页。第一场沿用 29:35–36:05；第二场按原顺序展示 00:15–01:25、03:06–04:37、11:04–12:23、15:57–17:12、31:56–33:13 五段。播放时显示会议编号、原始时间及“节选”，不将剪辑包装为两场完整录音。事件仍由人工编排，字幕由真实 STT 生成。

后端使用两场**完整**逐字稿，在一个全新的 SQLite 中依次调用正常 Service；context-v5 v19＋DecisionReview，使用现有配置。四位人物显式映射至本地模拟账号，第二场由 Service 自动读取第一场保存的任务和决定。禁止手工灌入预期历史、替换模型结果或把演示事件算作识别成功。源文本、运行前预期、实际上下文、原始响应与数据库均留存。实验导入时间仅用于确定处理顺序，不冒充录制时间。

## 确认后的任务关联定位对照

第一场完整真实模型输出把三位成员的分工设为候选任务，缺口为 commitment（是否承接）；原始双场试验不干预这些结果。另建 `runs/2026-11-18-ami-bc-confirmed-probe/`，重放第一场实际提取输出，通过正常 Service 入库，显式加入本地模拟参与者权限，再调用 `resolve_requirement(add_task)` 模拟确认三项分工。没有直接插入任务或改写模型输出。

此对照的第二场只输入三段真实汇报，使用保留原 ID 的完整 dialogue-act 段：186–277、664–743、957–1032 秒相交的原文。它不属于第二次完整会议成绩，也不代表真人实际按下了确认。第一场输出哈希、模拟确认输入、上下文、实际第二场响应均保存。

对照已 processed：8 次请求，179,113 token，194.21 秒。三段汇报分别关联到正确的历史任务，0 项新建，前后均为 5 项本地任务；重开及重复提交一致，重复提交没有新增模型调用。其中 David、Craig 保存为关联原任务的阶段汇报，任务仍 open；Andrew 触发 done 更新。后者的原话主要是研究方法与发现，未明确声明整项工作完成，完成判定标为需复核，不能把“3/3 关联”写成“3/3 状态全对”。对应原件见对照目录的 `audit.json`、`result.json`、`context-before.json`、`simulated-confirmations.json`。

## 使用与复现

前端启动：在 `demo/` 执行 `npm ci`，然后 `npm run dev -- --host 127.0.0.1 --port 4173 --strictPort`，打开页面点击“开始演示”。默认 STT 词轴由 small.en 实际识别剪辑音频得到，共 2,152 词；中文纪要与自动交互仍为人工预设。前端经过 14 项测试、类型检查、生产构建及完整自然播放验收，细节见 [前端说明](../demo/README.md) 和 [界面验收](../demo/design-qa.md)。

下面命令在项目根目录执行，要求已有 AMI 原始标注包与本机模型配置。真实调用会产生模型费用；每个新试验使用未存在的输出目录。读取报告和已保存结果不调用模型。

```powershell
$env:PYTHONUTF8='1'
python experiments/full-meeting/cross_meeting_pair.py --out runs/ami-bc-new
python experiments/full-meeting/cross_meeting_pair.py --out runs/ami-bc-new --live
python experiments/full-meeting/cross_meeting_confirmed_probe.py --source runs/ami-bc-new --out runs/ami-bc-confirmed-new
# 仅当第二场为 partial 且需要一次现有阶段恢复时：
python experiments/full-meeting/cross_meeting_retry.py --out runs/ami-bc-new
```

本次证据保存在：

- `runs/2026-11-18-ami-bc-continuity/`：首轮两场完整输入、运行前参考、实际上下文、原始模型输出、结果与数据库；`summary.json` 是首轮统计。
- 同目录 `recovery/`：首轮数据库副本上的一次恢复结果；新增模型请求保存在共用 `model/` 的新 attempt 中，原始响应不改写。
- `runs/2026-11-18-ami-bc-confirmed-probe/`：独立模拟确认对照、71 段原文输入、真实响应和关联核查。
- `demo/public/scenario-cross.json`、`asr-cross-result.json`：预设展示事件与实际 STT 输出。

完整后端试验使用 AMI 人工逐字稿，当前尚未验证“在线 STT → 会议提取 → UI 更新”的一体化链路。两场为同项目、已有素材上的连续关系案例分析；71 段对照是定位试验，均不作为未见会议泛化成绩。所有任务操作进入本地模拟器，没有写入真实飞书。
