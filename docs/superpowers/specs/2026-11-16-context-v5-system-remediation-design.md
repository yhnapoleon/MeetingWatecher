# Context-v5：语义判断、推理预算与失败恢复设计

2026-11-16。状态：研究完成，本文为建议方案，尚未实施或运行新的模型实验。

用户需要会议纪要保留真实待决问题，让任务系统只为原话成立的工作生成确认或更新，并让截断、格式错误能够有界恢复。本设计基于最终 95 场景×2 轮中的 18 次失败，重新审计标注、追踪系统数据流，并核对模型接口官方文档。历史结果保持 172/190，默认策略保持 split-v3，后续候选仍从可选 context-v5 验证。

## 二、系统原因：三个没有被表达清楚的区别

### 1. 有证据的句子，不一定有它所声称的会中状态

facts/unresolved 只有 `statement + evidence_ids`。程序能检查证据编号存在，却不能从编号推出“这件事本场待决”。引用一条旧问句，只能支持“有人问过”；引用未实现的产品功能，只能支持“未实现”。本场是否采纳该问题、后文是否已回答、未实现是否仍待决定，是另外的命题。

当前 `extract.py:evidence_extract` 并行执行 facts、decisions 和工作流水线。工作检查没有 unresolved 输入，最终 `validate` 也只核对字符串、证据编号等结构。这里既缺少最终核验，也缺少核验所需的明确判断对象。给每条输出再问一次笼统的“是否正确”，容易重演原检查器认可错误描述的问题。

十次可进一步分为：**问答状态更新错误（2）、本场议题资格错误（5）、结果状态与决策状态混淆（1）、命题角色与对象漂移（2）**。P05a r1 表明，本场议题资格不完全等于引用识别；它识别了培训背景，但仍把“未展示答复”当成“会议留下的问题”。

### 2. 工作是否成立，与工作是否已承接不是同一个判断

当前 kind、commitment、missing_fields 和 question 之间存在互相支撑的解释：先假设文稿是一项工作，就能说其动作缺失；先把产品选项当成工作，就能说采纳缺失。这些“缺口”在各字段内部看似合理，前提却未经充分验证。

`need_basis` 已要求潜在需求有来源目标，这是可复用的先例；但 work、ambiguous 和工作问题尚无同等明确的资格依据。已有提示正确描述了引用、对象提及、产品选项的边界，但模型给出分类后，程序无法检查它是否回应了这个前提。

### 3. 修正后检查，没有保留原异议的处理责任

C11 第一轮的原 record 与修正 record **逐字段完全相等**。首检因 classification 判 insufficient；复检改为 supported。复检输入有原文和修正结果，但没有首检的 record_checks、event_checks 或分类异议，coverage_findings 又为空。程序只核验新输出是否获得支持，没有要求解释为何首检异议已解决或为何应推翻首检。

对最终六条已完成的修正流水线做只读比较，C11 是唯一记录完全不变却重新获得通过的目标。它不证明所有“不改文本”的修正都有错——首检也可能误判——但证明现有流程允许无须回应原异议便完成反转。[比较记录](../../../runs/2026-11-16-context-v5-system-design/unchanged-repair-audit.json)及[C11 请求证据](../../../runs/2026-11-16-context-v5-system-design/c11-review-objection-loss.json)保存了断言。

## 三、方案选择

| 方案 | 收益 | 代价与不足 |
|---|---|---|
| 仅增补各阶段提示、扩大预算 | 改动少，预算可直接针对 CP01 | 不能保证首检异议被处理，不能约束最终问题与缺口一致；也未建立纪要语义评分 |
| 合并后加一个总评审模型 | 接入集中，可看跨分支矛盾 | 把分类、改写、覆盖和裁决再次塞入一次判断；总评审失误仍可能整批放行，且难归因 |
| **统一判断标准，保留分支，在既有检查和最终纪要核验处分别执行** | 复用工作 repair 与证据协议；对不同错误给出可审计理由；能分别验证 | 增加纪要检查调用和少量结构字段，需要衡量保留率、成本与延迟 |

建议第三种。“统一”指共同检查命题、归属、最终状态和用户用途，并由程序维护身份与状态一致性；不要求所有内容共用一个大模型调用，也不把任务输出当作纪要真值。

细粒度核验比单个总分更适合定位混合错误：FActScore 将输出拆成可分别支持的事实；QAFactEval 强调问题生成和可回答性判断，并发现问答与蕴含信号可互补。本设计借用检查粒度，不引入其整套模型或声称能复现其论文指标。[FActScore](https://aclanthology.org/2023.emnlp-main.741/)、[QAFactEval](https://aclanthology.org/2022.naacl-main.187/)。对话领域的 TofuEval 也发现通用 LLM 二元事实评审有明显局限，因此新增检查器仍须用本项目正反例衡量，不能作为新的金标。[TofuEval](https://aclanthology.org/2024.naacl-long.251/)

## 四、共同判断标准及输出去向

### 4.1 先确定四件事

| 判断 | 必须表达的内容 | 此次对应 |
|---|---|---|
| 命题 | 谁做什么、涉及什么对象、查询什么内容；条件和不确定性修饰什么 | P08b 调查者/支持对象/查询信息分开，缺失对象不补写 |
| 归属 | 当前发言是在提出、报告、转述、举例，还是回顾；引用是否在本场被采用 | P05/P06/C24 保留外层语境和本场采用依据 |
| 最终状态 | 对同一命题，后来是回答、决定、撤回、暂缓，还是仍开放 | C09 回答研究对象；C13 接受产品结果；调研已承接不等于问题已有答案 |
| 用途 | 事实/选项记录、当前未决、执行工作、任务必要缺口，或系统尚未解释可靠 | C11 可记产品选项而无工作追问；C20 只保留文稿对象 |

这些判断由模型依据原话完成，程序能保证的是：身份完整、证据合法、字段组合不冲突、未解决的系统异议不被当作通过、未决状态与输出去向一致。不能用枚举、关键词或证据非空冒充语义理解。

时间上的“过去”与话语上的“历史引用”必须分开。“我上周已经发了材料”是本场工作状态汇报，仍保留 work/completed；“我举一个上周培训里的例子”是引用。两者不能按过去时一起过滤。

### 4.2 unresolved 的纳入条件

一条问题进入“本场未决”，需要同时满足：

1. 输出所说的命题与原文一致，没有添加提供支持的人、录像文件等对象。
2. 本场确实把它提出为问题/选择，或明确采用了被引用的问题。仅仅材料未展示答案不够。
3. 在可见输入的最后，它仍未被回答、决定、撤回；若部分回答，只保留未回答的部分。
4. 没有被明确暂缓到“只记录、不立即推进”的状态。暂缓不进入立即待答的未决栏，但纪要分支必须以事实保留议题和暂缓安排；不能仅依赖工作分支的 deferred_topic。

“已经有人答应去调查”只关闭负责人/承接问题，不关闭调查对象本身的未知。比如 P08b 可保留“是否支持录像尚待了解”，并记录小林尝试查询信息；不能说支持能力已解决，也不能改成由小林提供支持。

产品备选方案可以作为事实中的选项记录。是否必须另列本场未决，要看当前是否仍需作出选择；`context_only` 本身既不要求保留，也不要求删除 unresolved。C11 第二轮现有结果就是“无工作追问，但记录成本与方案选项”的对照。

### 4.3 纪要核验的最小接入

在候选合并后、Service 规划写入和生成用户纪要之前，增加仅对 facts/unresolved 生效的 `minutes_review`：

- 程序给原候选分配 F/U ID；输入完整、授权后的模型原文，事实和未决候选，工作及决策结果作为只读解释。其他模型结果不能代替原文。
- 检查分别输出内容支持度、本场议题资格、最终状态、相关证据和发现的问题。新增遗漏作为 coverage finding 返回，不直接修改现有任务或决策。
- 原候选正确则原样保留。候选含义正确但栏目不合适，可建议移入事实；角色或对象错可建议改写；已关闭或仅作例子的问句退出未决栏。
- 需要改写、转为事实或补回遗漏时，沿用一次“局部修正→复检”的有界模式，目标 ID 和待处理异议由程序固定。新文本必须被复检，不能让检查器一边改写一边直接批准自己的新句子。
- 只有通过复检的替换才进入用户输出；检查或修正失败时保留原始候选供诊断，将相关结果标为未完成。不能把未核验的候选包装成已确认未决，也不能把系统没理解变成用户需要回答的问题。

首版按整个 facts/unresolved 依赖组提交，避免同一命题同时以“已答”和“未决”部分落入纪要。工作与决策仍按现有独立分支提交。新增 `check_minutes/repair_minutes/check_minutes_repair` 使用非思考配置作为对照起点，输出上限先设 6,000，记录实际用量；只有修正时产生后两次调用。检查覆盖原文中应保留但候选遗漏的重要问题，避免以删除全部 unresolved 换取低误报。

**暂缓信息由纪要分支保证可见。** 对“方案先放着，下周再议”，纪要保留“方案已暂缓，将于下周再议”等有依据的事实，不询问负责人或是否立即执行。即使工作分支失败或漏提 deferred_topic，也必须保留。若工作分支同时产出同一议题，核验可将该事实 ID 与对应 deferred record ID 显式关联；Service 仅对同版本、通过核验的关联合并展示，保留纪要事实而不重复展示工作侧暂缓条目。无已核验关联时不凭同一段证据或关键词删除记录。该映射只是展示去重，事实的提交和保留不依赖工作分支；新的工作结果使映射失效时也不能隐藏事实。

新模块建议为 `meeting_eval/minutes_review.py`，接入 `extract.py:evidence_extract`，`service.py:minutes` 处理已核验暂缓关联的展示去重；输入输出验证仍使用现有 Q 证据、绑定 ID、严格 schema 的做法。不要强行把纪要问题塞成 work event，也不为两个调用方先搭通用工作流框架。

## 五、给工作和追问增加资格判断

### 5.1 在已有检查器内增加，不再独立加一个工作模型

为 `check_work/check_repair` 的每条 record_check 增加简短 `qualification`：

- `speech_scope`：current / quoted / historical / uncertain；表示当前话语用途，不表示动作发生日期。
- `work_basis`：action / work_report / goal_need / option / entity_mention / none / uncertain。
- `evidence`：支撑动作、工作报告或目标的 Q 引用；若引用在本场被采用，另给 `adoption_evidence`。
- `reason`：只解释该工作为何成立或不成立，不重复描述整件任务。

这组判断用于核验 kind 和追问前提，不替代原有 owner、commitment、time、state、relation 核验。明确本场工作建议也属于 action，即使尚未采纳；产品属性选项则属于 option。对当前目标下的真实需求复用 need_basis，不能仅靠缺少明确动作将它删除。

程序根据已核验的资格约束路由：

| 原话支持的资格 | 合法处理 |
|---|---|
| 当前 action，或引用内容被本场采用 | 保留 work；再判断是否已承接、是否缺必要对象或负责人 |
| 当前 work_report | 保留 completed/progress 及关联；不因 unknown commitment 要求重新承接 |
| 有来源目标的 goal_need | 保留 implicit_need，询问确实未定的落实方向 |
| option / entity_mention，且没有另行建立工作 | 事实/背景或对象记录，不预设任务后补问动作、执行者 |
| 模型无法可靠判断工作是否成立 | 系统解释未完成；不能伪装成“用户没决定做什么” |
| 原话确实建立工作，但存在两个对象/范围待选 | 合法 ambiguous/reference/scope 缺口，问题只问这个实际选择 |

C20 的关键变化是先判断“文稿工作是否存在”，而不是看到 missing work 就追问。C24 要核对内层动作的外层归属。C11 要区分“选哨子作为产品方案”和“安排某人评估或实施哨子方案”。判断依据仍需原话，不能只用有无动词、未来时或负责人字段。

### 5.2 修正必须处置原异议

扩展 `plan_repair`，将首检的 classification、内容错误、真实缺口冲突和事件字段异议绑定为稳定 issue ID。复检同时收到原异议、修正前后差异与原文，并逐项返回：

- `resolved`：修正如何消除了异议，引用修正内容与原文。
- `overturned`：首检为何不成立，提供原文依据；允许原记录不变。
- `unresolved`：当前仍无法可靠判断，不通过该目标。

每个 issue 必须被处置；漏项、未知 ID、仅重复“supported”而无对应处置不能提交。检查器先基于原文核对候选，再回应异议；首检不是权威，不要求模型机械服从它。程序只能保证异议被处理，理由是否成立仍由正反例和源文本复核验证。

原 coverage_findings 处置机制继续用于遗漏，它不能代替分类异议。`context_coverage.py` 负责固定 issue 身份和原子合并，`context_v2.py`/v5 适配负责传递，`context_protocol_v5.py` 固定复检输出键。初版保持一次语义修正上限，不通过多次重抽样寻找满意结论。

### 5.3 最后一次性生成问题，修复 HT04

在归约过程中先收集已证实的语义缺口和执行所需选择，再生成问题；不允许生成后只修改 missing_fields。

- completed/progress/reopened 的真实工作报告不会因为 commitment=unknown 新增承接缺口。
- 已核验 relation=ambiguous 且至少两个授权候选，必须保留 relation 选择；选择前不创建新任务或更新任一候选。
- 问题的字段由最终缺口决定。没有真实缺口时 question=null；系统解释失败单独显示处理状态，不以工作问题表示。
- HT04 最终只问对应哪条旧任务，并列出候选。期限、负责人、承接等已无问题的字段不连带追问。

可复用 `context_v2.reduce_v2`、`context_state.reduce_context` 和 `context_v3.reduce_v3`，集中完成最终缺口和问题组装，不新增一套执行策略。

P08b 还暴露条件修饰范围问题：“如果能查到”可能是结果可得性的保留，不一定是开始调查前需确认的条件。原 expectation 已冻结 conditional，本次不改旧分；新测试要区分“先开始、结果不保证”和“条件成立才启动”，再决定是否扩展条件字段和追问规则。

## 六、推理预算与调用失败机制

### 6.1 预算先针对长尾扩容

全部 992 请求与 5,206,653 tokens 已重新对齐。210 次追踪的输出 P95=7,808、P99=12,123；只有 CP01 两次触及 16,384。其他 208 次均 stop，但其中包括 C14 非法 JSON，不能说全部有效。解释阶段最高 14,830，来自仍有语义错误的 C24；更长推理不保证理解正确。[预算及缓存研究](../../research/2026-11-16-budget-recovery-research.md)

[独立复算统计](../../../runs/2026-11-16-context-v5-system-design/request-statistics.json)保存各阶段请求数、分位数、结束原因、推理用量及 992 份元数据哈希；分位数采用 nearest-rank，包含失败请求。

建议先固定 CP01 第一检查点，对比 high/16,384 与 high/32,768，其他输入与参数完全相同。32K 通过后继续运行后两段和下游，核对最终范围与承接。首批各三次只用于筛查明显不稳定方案，不作为稳定性证明。若 32K 仍耗尽，单独比较 low/32K 或删减重复协议表示，不同时改变检查点大小、思考档位和提示。

后续恢复策略先采用：追踪/解释首发 16K，遇 length 一次升到 32K；32K length 后停止。若实验证明追踪首发直接 32K 更合算，再调整首发配置，此时不再自动升 64K。其他阶段保持现有预算。预算是最大输出容量，不是固定消耗。

官方现行 API 支持超过 32K 的输出，thinking 有 low/high/max；本地仅接受 high/max。预算扩容和 low 档位是两项不同变更。CP01 16K 已耗时约 95 秒，32K 实验还需明确阶段总截止时间，建议初始 300 秒并记录读等待与总耗时。`urlopen(timeout=90)` 不是整个阶段的墙钟上限，不能直接复用它声称已限制总耗时。[Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)、[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)

### 6.2 按失败类型恢复一次

现状是所有非 stop 被归为 Incomplete，JSON 解析失败和截断都可进入“修复结构”反馈；预算不变。普通缓存会重新读到已收到的坏响应，只有 partial 的 resume 路径才触发 fresh。应区分：

| 类型 | 一次技术恢复 | 验收 |
|---|---|---|
| budget_exhausted：length | 保持语义输入、high 和协议不变，16K→32K 完整重生成 | 完整响应＋解析＋schema/证据/顺序验证，然后进入正常语义检查 |
| syntax_invalid：stop 但 JSON 不合法/空内容 | 原预算，附精确解析错误，一次格式重生成 | 所有本地校验重做，后续语义检查不省略 |
| schema_or_evidence_invalid | 原预算，反馈具体字段/证据错误 | 未知引用、未来引用、旧身份替换仍拒绝 |
| retryable_transport | 依据已记录的连接错误/状态码，有限等待后一次新请求 | 完整收到并校验；无最终 usage 记 unknown |
| 非重试参数/认证错误或其他明确终止原因 | 直接终止并暴露原因 | 不靠增预算或修改内容绕过 |
| 结构正确但语义不可靠 | 工作或纪要的有界语义修正 | 原异议被逐项处理，修正内容通过复检 |

不采用补一个括号就直接放行 C14 的策略。该离线操作证明故障位置；线上新响应仍可能改变字段含义，必须走同等校验。

### 6.3 逻辑节点与请求尝试分开

每个检查点/阶段保留一个逻辑节点：源输入、前一个 accepted 产物、prompt/schema/校验器版本固定。一次实际请求是该节点下的 attempt，另存预算、请求哈希、finish_reason、解析结果、用量和时间。预算升级属于同节点的一次恢复，不重置整条流水线。

每个节点最多首发＋一次技术恢复，计数持久化，Service 重入不清零。语义修正是现有的一次 repair/check_repair 流程，不允许以技术重试绕过语义拒绝。请求已启动却无最终 usage 的中断也占一次尝试，并单列未知消耗。

成功 checkpoint 原子提交，失败 raw response 永久保留但不可当作 accepted。恢复 C14 时复用成功的首 checkpoint，只恢复第二个，再运行下游；CP01 从首 checkpoint 恢复。只有依赖的 accepted 产物或语义协议改变时才失效后代；改变某次恢复预算不能清掉所有成功祖先。现有配置整体进入管线缓存键，直接改 inference config 不具备这一保证，必须改缓存边界。

`received`、`parsed`、`validated`、`exhausted` 分开记录。所有失败请求的已知 usage 纳入成本，缓存命中不重复计费。用户再次处理同一会议仍使用冻结 context 和原 source identity，经既有 intent ID 与回读机制避免重复写任务。工作分支失败时继续保留独立 facts/decisions；不得把整场重建作为恢复手段。

repair 子阶段异常目前可能只写 trace.repair.failed，外层 errors 为空，Service 不保证进入 partial。需要显式暴露“语义修正未完成”，保留已核验的其他记录，阻止未通过目标的副作用；这类状态不应仅依赖解析错误来触发恢复。

### 6.4 strict 输出是独立选项

官方 Beta strict 约束工具参数，需要 schema 转换及 tool_calls 读取，并非替换当前 response_format 的一个值。thinking 下不能使用 required/指定函数强制调用，因此不能直接把现有 high 追踪改成“必定返回 strict 工具”。先用 json_object＋分型恢复解决当前故障，再独立验证 strict 的接口兼容性、调用完整性和成本；本地引用、身份、顺序校验仍保留。[官方 Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)、[tool_choice 限制](https://api-docs.deepseek.com/api/create-chat-completion/)

## 七、落地顺序与可判定的验收

| 阶段 | 主要文件/产物 | 验收结果 |
|---|---|---|
| 0：冻结纪要标注 | 新语义标签版本；保留旧 manifest 和预测 | 每条标注包含命题、本场资格、最终状态、发起/关闭证据、必须保留/允许省略/禁止添加；P05a 政策边界写清。旧预测按新旧口径分开评分 |
| 1：确定性一致性 | context_state.py、context_v2.py、context_v3.py、context_coverage.py 及协议适配 | HT04 只问关联且不更新；C11 未改记录不能无处置地洗掉原异议；首检误判可有据推翻 |
| 2：预算与恢复 | model_client.py、阶段缓存、extract.py、Service partial 状态 | CP01 与 C14 分类不同；最多一次恢复；成功祖先不重跑；失败费用可核算；重复 process 不重复执行 |
| 3：工作资格 | v5 check/repair 提示和 context_protocol_v5.py | C11/C20/C24 不造任务问题；真实提议、被本场采用的引用、工作报告、目标需求继续保留 |
| 4：纪要核验 | minutes_review.py、extract.py、service.py、事实提示与独立检查提示 | 删除已关闭/非本场未决，P08b 修主宾语而保留未知；P06b、部分回答、暂缓事实不得丢失；修正失败可见 |
| 5：受控验证 | 新实验目录、固定源输出与未见对照 | 分别报告首发有效率、一次恢复率、语义正确率、真实未决保留率、错误追问、任务状态及成本；不只报最终通过数 |

最小语义对照集在看新输出前冻结，至少覆盖以下成对变化：

1. 引用问题只举例／引用后明确要求本场决定。
2. 研究对象已回答、研究结果待查／研究对象本身仍未定。
3. 两个问题只回答一个／全部回答。
4. 产品结果回顾／明确重新开放该选择。
5. 只提到文稿／明确说文稿也要编辑并发出。
6. 产品备选选项／明确安排评估或实施该选项。
7. 过去工作完成报告／过去培训里的工作示例。
8. 结果不保证的调查承诺／条件成立才启动的任务。
9. 首检正确、修正原样返回／首检误判、原文支持推翻。
10. 两条同名旧任务／唯一可关联旧任务。
11. 明确暂缓且工作分支成功／工作分支失败或漏提：纪要事实均保留，未决和即时追问均不出现；已核验关联不重复展示，关联过期也不丢事实。

离线先用保存响应验证异常分类、issue 传递、缺口/问题一致性、缓存与副作用；真实模型实验再验证语义判断和预算。每次只改变一个机制，使用新目录保存全部尝试。已有 95 场景参与过调优，最后还需要冻结未见的上述变体；不能只让当前十八条“过关”。

本设计的成功标准是用户看到的纪要、问题和实际任务状态都正确：全部删除未决、把所有不确定性变成用户追问、或重试到某次偶然通过，均不满足验收。
