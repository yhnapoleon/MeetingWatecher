# 跨会 M2 复测：任务更新正确，范围决定分类仍有波动

2026-11-15。用户可以通过 M1→M2 流程完成上一场会议的原任务、保留原期限，并查询被新范围替代的历史决定；但原始 M2 仍可能多出范围调整候选和确认。本轮完整跨会两次首次运行中一次通过附加语义验收，单独 M2 两次均失败，不能认定问题解决。

“登录改版第一批的范围今天改一下，内部员工和试点客户都开放。”在当前场景中表达范围决定，没有另派实施工作。第一轮跨会的首次解释正确将它保留为 `context_only`，核验却认为“今天改一下”意味着分派任务。随后的一次定向修正生成范围候选，并把“今天”设成截止日期；首次核验留下的遗漏标记也继续显示，最终有两张确认。这是本轮最能暴露问题的失败样例。

## 输入与比较条件

使用当前 `context-v1`，生产源码、提示和默认策略均未改。模型为 `deepseek-flash`，沿用 `compact-check.json`：跟踪和解释开启 high 推理、temperature=1，核验关闭推理、temperature=0；输出预算均为16384。沿用最多一次定向修正。所有写入均落在本地模拟器。

预先固定三组、每组两次首次运行：

- **原始跨会**：从 `examples/m1.json` 提取任务和决定，再处理原始 `examples/m2.json`。历史任务不是预置答案。
- **单独 M2**：复用旧全量实验的 M2 输入和预置旧任务，用于检查任务解释；它没有 M1 的历史决定，不能替代跨会验收。
- **跨会落实正例**：M1 和原始 M2.1/M2.2 不变，仅追加王宁“陈可今天下班前改好灰度配置并发测试。”以及陈可“好，我来。”。沿用原参与者和权限，避免新加入人员改变授权历史。预期只新增一项配置及发测试任务。

同组原文、模型和配置一致，端到端跨会每次重新生成 M1，因此旧任务摘要和 GUID 会变化。本轮衡量同一流程的运行波动，不能把跨会与单独 M2 的差异归因为某一个历史字段。检查输入时确认：任务分支只收到授权任务投影；历史决定传给决定分支，跟踪器不接收 history。旧 C1 确实向解释/核验加入了授权历史决定，但使用的是前一版提示，不能与本轮作单变量比较。

旧单独 M2 fixture 的 `meaning` 仍写“范围调整待负责人”，预期包含 `pending=true`。本轮保留旧文件，采用交接规定的零额外候选、零错误确认标准，另存 `m2-validation.json`。预期及人工结论不进入模型请求。

表中“候选”指错误的范围调整候选；确认数来自最终 `review_records`，未把纪要“待核对工作”对同一遗漏的重复展示再算一张。

| cross-r2 | 是 | 不适用 | 0 / 0 | 无 | 通过 | 10 / 43,986 |
| isolated-r1 | 是 | 不适用 | 1 / 1 | 无 | 失败 | 5 / 20,685 |

| positive-r2 | 是 | 1项，陈可，当天下班前 | 0 / 0 | 无 | 通过 | 10 / 47,528 |

六次首次运行共52次调用、231,412 tokens；一次恢复新增3次、23,980 tokens，合计55次、255,392 tokens。跨会行含 M1 和 M2，单独 M2 行只含 M2，不能直接用行间差值估算某一机制成本。恢复目录包含复制的原调用记录，总用量只计新增部分。

positive-r1 的错误发生在跟踪阶段：模型输出 `{"segment_id":"M2.1","quote":"陈可"}`，但 M2.1 正文是“上周说的三个登录失败案例，今天早上我已经发到研发群了。”，“陈可”仅在发言人字段。校验返回 `Missing or ambiguous exact quote; provide occurrence`，实际原因是引文不在正文，增加 occurrence 不能修好这条输出。首次结果和数据库保持原件，在独立目录按相同配置恢复一次后通过。

两次原始跨会的旧12项检查均通过。新增验收进一步检查实际 `items`、确认、遗漏、纪要已决事项、原 GUID 与期限；对成功处理的 M2，在数据库副本上重复处理并重启，再核对任务、决定、intent及审计记录均不增长。跨会决定替代、历史查询和访客隔离通过。正例产生的第二项持久化任务是预期的配置工作，因此旧 `m2_no_duplicate_task` 的“只能有一项任务”不适用于正例，新验收要求恰好原任务加配置任务。

## 阶段证据说明了什么

**范围误判首先出现在跟踪解释中，但最终成败还取决于后续核验。** 旧 `cross-v2` 与本轮两个 isolated 运行把范围标为 `work` 后一路支持；本轮 cross-r1 的解释曾纠正为 `context_only`，核验又以“今天改一下”为由推翻，修正遂生成错误候选。cross-r2 的跟踪同样标为 `work`，但解释和核验接受范围决定，最终通过。因此，已观察到“核验把正确解释改坏”的路径；尚未通过受控实验确认这是前序解释影响，还是核验自身的语义边界判断。

**重复遗漏确认来自修正前后的状态合并。** cross-r1 首次核验同时将 R2 判为分类错误并把 M2.2 放入 `uncovered_spans`。`context_pipeline.py` 的局部修正只替换目标 records/events 及其 checks；修正核验被明确要求 `uncovered_spans=[]`，且不重新评估首次遗漏。最后仍使用首次遗漏列表。`context_state.py` 又为列表中的每个 span 生成独立 U 记录，因而 R2 确认和 U 确认同时出现。旧单独 M2 也有同一路径。这里的空列表是局部核验协议要求，不能解释为模型已经撤销首次遗漏。

**明确实施工作可以与范围决定共存。** positive-r2 首次和 positive-r1 恢复后都只创建灰度配置及发测试任务，陈可、2026-11-16及“今天下班前”均保留；原任务完成，新范围替代旧范围，零额外确认。真实工作会引用 M2.2 的范围证据，恢复结果甚至把 M2.2 作为 action_anchor，因此不能用“与决定共享证据”或“锚点是范围段”直接删除任务。两次可用输出包含一次结构恢复，不能写成正例两次首次都通过。

## 后续实验边界

下一步可按既有 C3 设计冻结同一份授权原文、名册和历史，仅改变分类器是否能看到 ledger/records/events，并使用相同合并核验过程，比较原始 M2 和本轮落实正例。两个等调用版本的差异才能检验前序解释的影响；本轮未实现 C3。

遗漏确认应另行验证其生命周期：修正后某条首次遗漏是否已被已有记录覆盖、是否仍有另一项未表示的工作。验收至少同时覆盖“同一工作被重复标遗漏”和“同段确有第二项遗漏”，避免仅凭证据相同抹掉真实工作。与任务分类实验分开，才能看清各自收益。

本轮是固定合成场景复测；没有新会议泛化结论。C20、P07b和完整证据协议仍按原交接留待后续。
