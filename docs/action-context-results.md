# 上下文补全与待确认需求：实施和验证

2026-11-14。本轮为离线会议助手增加了实体和需求线索记录，以及人工确认入口。用户可以保留暂时说不清的工作，随后明确内容和负责人再加入任务。但实验策略 `context-v1` 的综合提取质量未超过上一版，默认仍为 `split-v3`。

一个实际回退是 C20：“后面的话我们会把这个视频剪辑，然后给大家确认，然后还有这个文稿可以吧。”视频已有明确动作，文稿只有对象。新方案第一轮把两者合为同一条待补全工作，因文稿动作不明，连视频也没有形成任务。这说明持续补全需要先分清是哪项工作；多保存上下文，并不会自动解决这个判断。

## 1. 四项建议如何落地

| 建议 | 判断与采用方式 | 需要区分的情况 |
| --- | --- | --- |
| 联系上下文、保存无动作实体 | 合理。新增实体、原话提及、实体关系与工作线索账本；每 8 段检查一次新增信息 | “界面功能”和“用户界面”可以相关，不能仅因词相近判为同一对象；同一对象上的设计、测试也不是同一任务 |
| 隐藏需求单独列出 | 合理，类型使用 `implicit_need`。保留推测内容与原话，允许人工加入或忽略 | “用户不用说明书”可能是研究动机，也可能只是背景；不能直接推成“重写说明书”。若后文明确安排调查，应转为明确工作 |
| 要求持续补完 | 合理，保存按时间追加的更新，允许补充、纠正、否定和撤回 | 补全不等于一直增加要求；后文“不是 Web，是移动端”必须替换当前理解，并保留修改依据 |
| 模糊工作持续跟踪、最终确认 | 合理，类型使用 `ambiguous`，记录具体缺口和询问对象 | 只有负责人没答应，与根本不知道做什么是不同问题；缺少可选截止日期不应阻止已明确的任务 |

实体、隐式需求、模糊工作与明确工作有各自出口。隐式/模糊内容不自动执行；人工加入时必须填写最终描述和已映射负责人。`ask_issuer` 保存待询问状态，不发送消息。详细命令见[使用说明](context-workflow.md)。

本轮实现的是同一场会议内的离线分段更新。已创建任务沿用原有跨会议机制；尚未确认的需求线索暂不跨会议继承。

## 2. 调研依据与方案

[Purver 等的行动项研究](https://aclanthology.org/2007.sigdial-1.4/)将行动项放在提出、讨论、分派和承诺的对话中判断，适合解释为什么单句找动作会漏掉连续分工。[CREAD](https://aclanthology.org/2021.naacl-main.265/)联合处理指代和省略；[逐轮关键短语跟踪](https://aclanthology.org/2024.findings-acl.127/)提供保存上下文对象的思路。[增量对话状态推理](https://aclanthology.org/2021.tacl-1.34/)支持随新增对话更新需求状态；[必要时澄清](https://aclanthology.org/2025.findings-naacl.306/)则提醒澄清本身也有用户负担。这些研究支持设计方向，不证明本项目采用后一定有效。

本轮复用已有模型、SQLite 和任务执行规则，没有引入新的训练系统。流程为：累积原文和旧账本 → 追加实体/需求线索 → 全文解释 → 独立全文核验 → 生成任务或待确认记录。各检查点只能看到截至当时的原文，后来的补充不能改写旧记录。

实现分工如下：

- [context_state.py](../meeting_eval/context_state.py)：校验实体、关系、更新历史、原话证据及需求类型，按具体缺口决定是否允许生成任务。
- [context_pipeline.py](../meeting_eval/context_pipeline.py)：分检查点读取、调用缓存与失败恢复；核验采用简短证据编号，避免反复生成长引文。
- [requirement_review.py](../meeting_eval/requirement_review.py) 与 [service.py](../meeting_eval/service.py)：待确认列表、人工决定、权限、来源版本、意图回执及幂等。

人工决定与会议承诺分开记录。重复提交同一记录的相同决定复用结果；来源更新后不能继续确认旧记录；已有任务关系不清时不能绕过检查新建。

## 3. 标注和检验口径

旧 `action-semantics-v2` 标签保持不变，继续检查任务内容、负责人、承接、时间和操作。另在运行前冻结[行为契约](../experiments/action-context/behavior-contract.json)，单独判断“是否保留了含义、是否提出具体问题、是否避免无依据执行”。例如 C09 从任务改成待确认，不会因此在旧任务指标中获得额外分数。

这两类分数回答不同问题：任务指标检查最后留下的任务是否完整正确；行为契约检查暂时不能执行的内容是否得到合适处理。C02 第一轮保留了工作和负责人，但因 `it` 未命名而不产出任务，因此某些保留准则通过，任务召回仍扣分。

数据包括六个既有难例各三轮、C02+C03 连续分工窗口各三轮，以及预先冻结的 8 个中文合成样例。后者含 6 条参考任务、21 条行为准则，覆盖跨检查点补全、改对象、撤回、同名不同对象、纯实体、隐式需求及明确化。合成样例只检查机制，不能代表真实会议泛化。

复核由独立代理读取原文和全部输出完成，不使用流程自身核验结果作为真值。输入、输出、标签和契约通过哈希绑定；首次失败保留在分母。所有标注仍是代理复核，不是人工金标准；新系列盲测尚未建立。

## 4. 迭代结果

初版让跟踪、解释和核验都开启推理。除了语义错误，还出现引文结构不合规、推理耗尽预算而没有最终答案等失败。第二版明确结构并让核验引用证据编号，但仍有截断。冻结一份 C03 核验请求、只关闭核验推理后，该步骤约 7.6 秒返回了可用结果；这是单次诊断，不能证明稳定性。

最终候选保留跟踪和解释推理，关闭核验推理，并澄清“对象未命名”与“存在竞争指代”、“背景约束”与“必须执行的范围”的区别。配置为 [compact-check.json](../experiments/action-context/compact-check.json)，代码与提示快照为 `frozen-v3.zip`。这些变化同时涉及提示、表示与推理模式，不能把分数变化单独归因于某项架构。

以下是同样六个难例、每轮 6 条参考任务的三轮均值：

| 方案 | 内容 F1 | 完全正确任务召回 | 每轮任务 token | 每轮六例累计处理时间 |
| --- | ---: | ---: | ---: | ---: |
| 上一版 evidence-v1，含一次失败恢复 | 75.2% | 55.6% | 62,206 | 224.1 秒 |
| 本轮初版，未恢复失败 | 46.3% | 33.3% | 142,038 | 583.5 秒 |
| 本轮最终候选，六例均首次处理成功 | 71.1% | 50.0% | 100,884 | 361.8 秒 |

最终候选的内容 F1 分轮为 66.7%、66.7%、80.0%；完全正确召回三轮均为 50.0%。任务 token 比上一版增加约 62%，质量没有超过上一版。token 仅含任务阶段，排除事实与决定分支；耗时来自各例记录的累计处理时间，受服务负载影响，不能当作生产延迟保证。

最终六例行为准则分别通过 12/17、11/17、13/17，合计 36/51；初版为 37/51。内容分数回升不意味着待确认行为也改善。最终 10 条任务预测均未被复核为含无依据陈述，也没有错误创建提议，但仍有内容、承接及操作错误；“没有编造”不等于“全部正确”。

| 其他验证 | 首次结果 | 同配置恢复失败步骤一次后 |
| --- | --- | --- |
| 连续分工窗口，三轮 | 首轮结构失败；另外两轮内容 F1 80%、完全正确召回 2/3 | 三轮均为 80% 和 2/3；每轮行为准则 2/4，UI 分工仍未正确保留 |
| 8 个中文合成样例 | 7/8 处理成功，任务命中 5/6，内容 F1 90.9%，行为准则 17/21 | 8/8 处理成功，任务命中 6/6，内容 F1 100%，行为准则 19/21；6/8 例全部准则通过 |
| 三轮双会议回放 | 12/12、11/12、11/12 | 各 12/12；后两轮恢复了原任务更新步骤的结构错误 |

恢复没有重采样成功的语义判断，只重新运行失败步骤。原始失败、恢复输出和费用都保留。最终连续窗口平均任务 token 35,725，累计处理 119.8 秒；中文合成整组任务 token 181,991，累计处理 596.6 秒，均包含实际恢复费用。

## 5. 哪些有效，哪些仍明显不达预期

**持续补全的机制能够工作。** 中文样例中，前段提出工作、后段补范围和承接可以汇成任务；Web 改为移动端能更新对象；隐式建议明确安排后能转成工作。检查点历史保留了当时可知的信息，没有发现把后文提前放进旧检查点。

**核心语义仍有以下失败：**

| 样例与预期 | 实际表现 | 对使用者的影响 |
| --- | --- | --- |
| C03：连续给工业、UI、市场人员分工，应从前句恢复 UI 的省略动作；未承接可以待确认 | 短片段仅第一轮保留为候选；完整窗口三轮都被核验降为未核实假设 | 明明分配过的工作仍不能稳定进入正确候选；增加上下文没有解决 |
| C09：说明书使用问题至少应形成具体研究含义和确认 | 三轮都未形成合格确认；前两轮附带问题背景但问题泛泛，第三轮只问“说明书还是全部问题”，没有保留用户看法/使用目的 | 用户仍需回看逐字稿、重新解释为什么要做这项工作 |
| C20：视频明确，文稿动作未知，两者分别处理 | 第一轮把文稿缺口并入视频工作，阻止视频任务 | 一个模糊片段拖住了旁边已明确的任务 |
| C21：已承诺整理意见，“内容可能很长”是背景 | 第二轮把篇幅背景当作必须确认的范围 | 凭空多一道确认，漏掉本可执行的工作 |
| CP03：活动取消，相关工作撤回 | 没有创建已取消的任务，但仍问是否继续活动、是否核对安排 | 用户被已解决的问题打扰 |
| CP05：只提到两个实体，没有动作也要进入账本 | 最终有两个 `entity_only` 记录，但实体账本为空 | 无法认为实体已按设计保存到供后续指代使用的位置 |

此外，CP02 重问已经完成的对象核对；CP04 把“结果分别保留、不要合并”拆成独立模糊工作，再追问负责人。连续 UI 分工有输出同时生成一张需求卡和三张遗漏原话卡，增加重复确认。幂等目前只保护同一记录 ID，不保证语义相同的不同卡片不会被人工加入为重复任务。这些噪声在冻结契约中没有单列，未事后改分，详见[合成复核说明](../runs/2026-11-14-context-v3/synthetic-r1/review-notes.md)。

结构可靠性也未解决：中文明确任务 CP08 首次把只出现在说话人字段的“小林”当成正文引文，校验失败；回放后两轮分别因日期缺证据和无效引文失败。核验已改成证据编号，但跟踪/解释仍需生成精确引文，依然可能失败。

## 6. 工程验收与采用决定

[最终测试日志](../runs/2026-11-14-context-implementation/final-tests.log)记录 94 项测试通过，覆盖历史不可改写、证据/时间边界、隐式需求不执行、任务关系、人工决定权限、账号映射、版本变化、重复提交、回执丢失和恢复。CLI、Service 与本地任务模拟器的正常入口均有覆盖。旧证据实验也重新汇总，37 份成功阶段记录经原规则重算，任务提议未变化。

**保留实验实现，不切换默认策略。** 当前能验证保存、更新和人工决定的程序机制，但尚不能认定模型稳定理解并分类了真实会议需求。中文合成的高分不能抵消原难例未改善、确认噪声和成本增加。

后续优先做更小的修复：

1. 保留实体/证据记录和人工确认入口；先明确工作边界，把同一句里的已知视频动作与未知文稿动作分开，不因共享原话合并任务。
2. 分别判断工作含义、指代、负责人、承接和当前状态。未承接不应删除已经说清的分工；可选信息缺失不应阻断任务。核验应指出具体缺口，不能把所有不确定性都转成“整项工作不可信”。
3. 针对 C03/C09 做冻结输入、单变量对照，检查解释正确后究竟在哪一步被删或压缩。先让完整工作含义稳定留下，再检验持续补全带来的额外收益。
4. 将无效澄清、取消后残留问题、同一工作重复卡片列入下一版预先冻结的准则。工作身份明确后才能合并卡片，不能仅凭共用引文去重。通过现有难例后，再建立新会议系列盲测。

这四项是后续方案，尚未实现或验证。
