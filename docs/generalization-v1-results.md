# 新增会议任务数据集与冻结方案评测

2026-11-17。本轮已采集、标注72例并完成60例正式测试。自然会议任务识别P=50.0%、R=13.9%、F1=21.8%；20个控制样例P/R/F1均为100%。**当前context-v5未通过新自然会议上的普适性验证。** 主要损失是14场英文会议的上下文跟踪恢复失败，造成59个必需任务没有产出；其余9个漏项来自分类、状态与事项收录。

主结果按预测前冻结参考计算。4处参考边界/可能漏标和1处合并匹配存在争议；全部采用有利于系统的另一种解释时，自然召回率仍只有19.3%，不改变优先修复失败传播的判断。

## 数据规模与覆盖

## 标注与计分

52个自然片段先用独立整段提示进行模型预标注，执行助手再核对证据与任务边界；20个控制例由助手编写和标注。预标注不读被测Service预测。最终[labels.json](../data/generalization-v1/labels.json)及[标注规范](../data/generalization-v1/annotation-guide.md)在预测前冻结；原始预标注和修订记录均保留。

这是模型辅助标注与助手审计，**不是独立人工金标**。预标注与被测系统使用同服务模型，可能有相关盲点；助手复核也不等于52篇逐词双人独立盲读。公共材料是否进入基础模型预训练未知，只能称为项目未见样本。

主指标按任务动作、对象和必要范围的一对一匹配计算Precision、Recall、F1。items和独立的真实工作待确认/条件卡按record_id去重；负责人缺失不丢掉真实工作。完整字段指标再要求负责人、承诺/条件、语义时间正确。一个输出含多个独立目标时逐目标计数，额外编造目标单计FP，重复提取只能命中一次。

required构成召回分母；正确的optional匹配不奖不罚，未输出optional不算漏召回。全部60例包括partial都入分母，没有产出的必需任务计FN。纯提议、潜在需求等辅助卡单列，不混作已确定工作；本轮并未对全部辅助卡建立独立完整金标，因此不提供其总体准确率。

自然会议和控制样例分别计分。置信区间按自然会议重采样2,000次，而不是把同一会议里的任务当成独立样本。中文只有9个必需任务，尤其不能把其召回率看成稳定估计。

## 执行条件

被测策略为context-v5，模型deepseek-flash，正常请求使用high推理、16,384输出上限及既有节点恢复机制。生产代码、提示和配置与旧115例preflight的61个生产文件逐字节一致；没有针对新集修改生产逻辑。标签不进入被测请求。

仅通过既有Service入口执行新增正式60例，4个worker，无外层重跑，无失败样例替换，所有内置恢复调用计入成本。测试在本地SQLite Simulator进行，不执行真实飞书任务写入。冻结记录、执行配置和代码快照分别见[freeze.json](../data/generalization-v1/freeze.json)、[manifest.json](../runs/2026-11-17-generalization-v1/manifest.json)、[source.zip](../runs/2026-11-17-generalization-v1/source.zip)。

标注API单独消耗54次、1,116,041个已知token：52份成功预标注及2次初始预算耗尽；只对耗尽的两个pilot增加预算恢复。正式测试不会使用标注阶段的32,768输出上限替换原Service预算。

### 技术完成与用量

自然会议491次调用、18,308,369 token；控制123次、565,160 token。标注另计54次、1,116,041 token。调用日志与账目已逐文件核对，不能把本轮耗尽案例当成零成本。中间正常化19个节点单独记录，不与重试混算。

### 已定位的共同故障

**跟踪检查点失败会阻断整场任务产出。** GN25只有约1,733个参考token，却因93段短发言需要12个跟踪检查点；GN30约7,566 token、406段，预定51个检查点。生产逻辑固定每8段发言检查一次，每次携带此前全文及累计ledger。短回应密集时，检查次数和状态维护负担明显增加。检查点异常在`context_v2.run`的外层被捕获，后续`interpret_work`不再执行；此前已成功的ledger留在trace中，却不会形成最终任务。这是代码与日志确认的传播路径，尚不能隔离归因于英文语言本身。

GN25首次把原始发言尾号误当作Q证据别名；重试改正别名，却向T6/T7追加更新，而previous只有T1至T5、new_threads为空。GN26重试请求的严格工具schema要求`entity_ids`数组，原始接口响应仍返回`entity_id`单值；本地校验正确拦截。当前提示已经明确禁止按原编号拼接Q，也要求新线程有更新，因此仅重复这两条提示不足以证明问题得到解决。详细请求和响应路径保存在failure-diagnosis.json。

**未来工作与已有进展共用一个状态，工作内容保留了，任务入口却没有收录。** GN18把“慕课正在做，后期也要发表”整体标成progress；GN20把后续收集案例和评估与前期项目进展合并；GN28将已下载软件和“我的工作是在Swede及本机运行系统”合并。对应工作都留在报告区，未进入items或真实工作确认卡，因此按本轮任务入口定义计漏召回。GN13则将后续上线产品与既有产品一起归入context_only。

**具体承接、建议和愿景的边界仍不稳。** GN28双方约定的特征讨论以及明确条件性初版工作被降成proposal；中文论坛里“持续努力”“余生帮助”等长期承诺又被提升为待办。前者需要在原文回应链中保留承接，后者需要可追踪的具体行动边界。GN28还有执行者与分派者混淆：Grad B对“the two of you”布置工作，结果把他自己列入执行小组；这些字段错误与任务目标漏提取分别统计。

## 后续修正的优先顺序

1. 先处理跟踪阶段的失败传播：减少让模型维护的编号与增量状态，按内容量控制检查点，并用实际失败响应验证引用与线程契约。恢复应从已接受检查点继续；仍无法完成时明确保留待恢复状态，不能把未经后文核验的部分工作直接执行。严格工具输出仍须本地验证。
2. 再处理任务落袋：同一发言的“已经完成/正在做”和“之后要做”应分别保留状态；发送纪要、核对文字记录等行政跟进也要进入任务审查。已明确承接的工作不应仅以proposal等待再次采纳。
3. 在上述机制有定向证据后，再用授权的中文业务会议做下一轮外推。本次自然来源的退化不能靠控制对的高分抵消，也不宜用逐条补丁修饰成普适性通过。

这些是由本轮证据提出的后续方向，尚未实施验证；本轮结果对应原冻结方案。

## 复现与后续使用

从项目根目录离线复核现有结果：

```powershell
python experiments/generalization-v1/validate.py
python experiments/generalization-v1/score.py --out runs/2026-11-17-generalization-v1
```

评分依据是冻结参考、原始result哈希和task-matches.json内逐目标审计，不会调用模型。首次运行代码为`python experiments/generalization-v1/run.py --workers 4`；已有运行目录禁止覆盖，本次已执行，不需要为阅读结果重新调用接口。新增数据/评分合同的10项离线检查在冻结前通过。结束后再次核对冻结文件、52场原文还原、60份结果哈希和一对一匹配；独立计算任务计数与评分器一致，614份模型metadata用量和54份标注metadata用量均与账目一致，见[最终核对记录](../runs/2026-11-17-generalization-v1/final-verification.json)。

本批公开自然数据中的任务数量高度不均：中文24场只有9个必需任务，英文16场有70个。它能够揭示新输入上的故障，却不足以验证中文企业工作会议的任务召回普适性。下一次采集应优先取得授权的中文任务密集会议，并保留自然存在的无任务会议；不要按当前模型输出来挑选样例。之后若用本批失败调优，应把本批改称回归材料，另留新会议作独立验证。
