# 减少多余任务与确认：方案和对照设计

2026-11-15，研究设计草案。依据[逐例根因调查](task-boundary-diagnosis.md)，效果待实验验证。

用户应能从会议中得到真实的后续工作、现有任务变更和可供判断的潜在需求，同时在纪要里看到产品决定、活动安排和状态汇报。“不生成任务”仍需保存有用内容；“不能执行”也不自动意味着要向用户提问。

第一阶段目标是消除六类非任务/语境误报，纠正C26的承诺判断和C17的确认路由，保留目前17项正确任务及上下文能力。C14的条件性候选属于独立规则改动，单列验证。当前审计口径17/18召回、7项多余任务，30段中另有22张确认卡；新增审查标出9张不当追问，C26一张提问前提不当。

## 1. 三种可比较方案

| 方案 | 具体改动 | 收益假设和代价 |
| --- | --- | --- |
| A：现有结构，只改边界提示 | 在track/interpret/check中明确当前工作、产品约束、会内流程、告知和转述的区别；沿用entity_only保存无需后续行动的内容。 | 无新增调用，容易形成对照。现有entity_only已承载过通知，可能足够；但其“纯实体”语义与保存整项决定/安排不一致，规则仍可能泛化追问。 |
| B：明确上下文类型，加上输出路由（主方案建议） | 在原三阶段中增加context_only；加强分类/问题核验；对状态汇报、提议和真实缺口分别输出。 | 不增加模型阶段，覆盖分类及规则两个根因。要同步协议、验证、修正、展示和缓存版本；新类型的实际增益须和A比较。 |
| C：独立分类或分支协调 | 在A/B基础上，分别试授权历史决策、本场决策输入，或一次只看原文的任务边界分类。 | 能检验跨分支缺信息及前序解释影响。新增输入/调用和依赖，未必比B有效；只在对照支持时接入。 |

建议先比较A和B的语义部分，再独立验证B的规则路由；C拆成消融实验，不同时加入。这里是设计建议，尚未将方案写入生产流程。

## 2. 先判断这段话在做什么，再处理工作字段

对每个语义单元，解释器在同一模型调用内依次判断：

1. **归属与用途**：当前说话人是在安排或提出工作，还是转述别人的话、介绍既有活动、管理发言顺序、作产品选择、汇报状态？结合说话人、指代、前后问答和会议目的判断，不靠某个词。
2. **是否存在可独立跟进的工作或有用的潜在需求**：若存在，保留原来的工作领域恢复、上下文补全、隐式需求机制。C07的“思考组件概念”不必补交付物；C09的“说明书”可以继承研究问答。
3. **工作状态和承接**：suggested、assigned、accepted、self_committed、conditional仍分别判断。工作成立不代表已承诺；缺承诺不否定工作内容。
4. **输出用途**：新任务提议、候选、待采纳提议、潜在需求、事实/决定/安排、状态汇报、真实澄清或执行限制。

这不是要求每句话证明自己“会后”“有明确交付物”或“可单独验收”。正在会议中提出的实际跟进工作仍可保留，未知日期和执行细节不是自动排除条件。C01依据的是现场练习语境；C30依据的是面向听众的节目告知。相同“我们会/稍后”出现在真实后续整理、联系工作中，应继续保留。

一句话可以含两种功能。例如“只支持电视，小林据此改规格并发评审”：范围决定与修改规格各有记录，不能因同段、共享实体或证据交叠而删掉工作。

## 3. B方案的最小数据契约

### 3.1 增加context_only，不一次扩展整套对话标签

`kind=context_only`表示有用但不构成本场独立跟进工作的内容，包括产品决定/约束、现场活动、既有安排告知、引用说明和主持流程。现有description写清其功能及归属，evidence同时引用必要语境；不新增一组大而全的speech-act标签。

- entity_only继续保存纯实体；implicit_need保存与当前讨论目标有关的潜在需求；ambiguous只用于真实工作线索中尚未确定的内容。
- context_only的missing_fields=[]、question=null，没有task event。分类核验通过后不进入任务和确认卡。
- `context_only`不是永久关闭状态。账本后文可追加work更新，例如先介绍展览安排，后来另派人调整导览路线；初次内容仍保留。已取消/已解决继续使用原生命周期语义。
- 解释阶段必须能把旧账本的work改为context_only；新发现的record也适用同一判断，覆盖C29的thread_ids=[]路径。
- 修正可删除错误event并把record改成context_only，仍保持记录ID、thread关联及非目标记录不变。不能借修正重新改写全场。

证据要求是保存原文已经提供的语境，不是要求额外证明：C24需保留“我都会听到老师们这么说”的外层话语及后续引语；C29联系前面的主持环节；C04保留产品属性决定。之后出现本场采用或重新分派的证据时，生成新的工作解释，不能被先前“引用”分类压住。

### 3.2 核验明确检查分类和问题前提

复用现有record check及classification/question issues，在字段核验前检查：描述虽然符合原话，它是否把产品属性、节目介绍、历史/引用或交接发言转换成了当前任务？状态future_work只说明模型所理解活动未完成，不能单独证明它该进入任务列表。

分类错误指出具体语境差异，触发已有的一次定向修正。无需另造“怀疑所有省略”的规则；C02/C03正常短回应继续supported。对C26核对整段的提议/自愿承担含义，不能用“可以”一词作承诺证据，也不能要求所有自我承诺都有第二个人接受。

首轮只确定性排除“核验支持的context_only”和下文明确条件内的状态汇报。修正后仍未解决的分类争议，保留现有确认路径并单独评审，不能仅按classification issue、空missing_fields或模型已有question判断该不该隐藏。现有verdict/issues/reason不足以可靠区分“真工作含糊”与“任务前提有误”；若这些残留仍是主要干扰，再设计单独的确认资格判断并做正反例验证。不能通过隐藏争议记录提高表面分数。

### 3.3 输出与确认规则

| 语义结果 | 任务/更新 | 用户可见内容 |
| --- | --- | --- |
| context_only且分类支持 | 无新任务 | 事实、决定、活动安排或上下文记录；无执行确认。 |
| 新工作已承接，身份可执行 | 沿用create提议和Service校验 | 工作内容与已有字段。 |
| 新工作assigned或执行者不完整 | 沿用candidate | 只问真实承接或执行者缺口，不补问未知日期。 |
| work + suggested，如C26 | 不放入已承诺任务列表 | 保留待采纳提议。若显示问题，问是否采纳；不预设已决定只欠负责人。 |
| implicit_need | 无自动创建 | 保留推测依据，供用户判断是否采纳；保留CP06/C25等真实潜在需求。 |
| ambiguous且确有本场工作线索 | 无自动创建 | 问会改变执行内容的具体缺口；保留真正的未知材料/指代。 |
| completed/progress且无可关联旧任务，如C17 | 无新建、无更新 | 记录当前汇报，不让“没有可执行操作”触发确认。 |
| existing + completed/reopened/改期/进度 | 沿用旧任务契约 | 更新、进度报告或真实字段确认；不重新要求承接已有任务。 |
| 指令明确但系统不支持该字段操作 | 不假装执行成功 | 沿用execution_blocked及具体能力限制，不改写成需求不清楚。 |

对C17先做窄修复：`relation=new`、`state=completed/progress`，内容/状态/关系得到支持且没有实际待定字段时，返回reports而非no_supported_state_change。可以复用reports结构，target_guid=null；纪要标题从“旧任务进度汇报”调整为能包含此类记录的“工作进展与完成汇报”。这不等于自动把任何progress/new都加进任务清单；若原话另有待做动作，单独保留对应记录。

首轮给确认卡路由增加明确的终止分支：核验支持的context_only，以及上述内容/状态/关系支持且无实际缺口的new+completed/progress，不因pending生成确认。C26的suggested保留待采纳含义；真实字段缺口继续使用具体问题，能力限制沿用独立展示。其他未知字段、分类冲突及uncovered_spans先保留现有处理并逐类审查，不把missing_fields=[]设为全局删卡条件。长期目标是让确认对应真实用户选择，但不以未经验证的隐藏规则完成这一目标。

工作、决定和原话继续保存在账本及trace中。B首轮将核验支持的context_only确定性投影到`context_records`（record_id、description、evidence_ids），并在纪要单独显示“会议上下文”，不附执行确认。facts/decisions照常保留，允许同一内容跨区重复；重复数作为展示观察项单列。这样无需隐含的语义去重模型调用。若重复成为实际干扰，再在C2或独立的纪要合并实验中处理，不能用相同证据直接删除，也不能把合并步骤的收益归给B的分类契约。

### 3.4 C14作为独立改动

条件性工作已明确动作、对象、执行者时，可作为candidate保存，显示原条件，禁止自动create。与suggested分别路由；不能为了修C14而将所有conditional事件纳入候选，例如C24引用里的条件性提问仍应在前面的语境分类被排除。

现有events仅保存conditional类别及引文，标题未必保留条件。候选展示必须带条件证据或忠实条件描述；不将条件改写成泛化“是否承接”。若实现时需要新增字段，优先在提议/展示投影中保存承接类别和条件引文，不重写会议原文。此项实验和主要误报修复分开出分。

## 4. C方案怎样做独立对照

**C1：只增加授权历史decisions。** 复用Service已按参与者权限过滤的context，不扩大读取范围。将history由tasks扩展为tasks+decisions，供解释和核验理解M2的属性修订。无需等待本场decisions分支，也不增加调用。当前任务的新增/旧任务关联仍以任务身份判断。

**C2：再增加本场decisions结果。** 和C1分别比较。跟踪可以继续并行；解释若等待决策结果，会改变依赖和延迟。决策只是有证据的辅助解释，不能覆盖原文，不能用“存在决策”直接禁止任务；决策分支失败时如何处理也必须纳入实验。只在C1仍不足时投入。

**C3：分类是否看到前序解释。** 固定同一份完整授权原文、名册、历史、模型、分类提示和推理/输出预算，比较两个等调用版本：C3-visible的分类调用可以看到已有ledger/records/events，C3-blind看不到；二者均输出当前工作、提议、潜在需求、上下文或状态汇报及证据，再使用相同的合并核验过程。两组输入token因是否含预测而不同，要单列实际用量，不通过裁掉原文配平。另与不加分类调用的版本比较整体收益。visible与blind的差异才用于判断前序解释的影响；新增调用版本与基线的差异不能单独归因为去除前序影响。在现有check开头多写一句“独立判断”不算盲核验。标签和人工答案始终不进入输入。

C1/C2检验输入信息，C3检验核验上下文。不要把三项合成一个版本后宣称某一机制有效。若增加一个调用，应报告额外token、耗时、结构失败、正确任务损失，以及错误支持是否减少。

## 5. 成组对照：只改会改变工作含义的部分

以下是待运行的合成诊断样例；真实语料原文保持不变。每组均从正常Service入口验最终任务、确认和上下文，不只看中间分类。姓名均为合成，执行测试用固定模拟账号。

| 组 | 无新增任务/待决定输入 | 应保留工作输入 | 关键验收 |
| --- | --- | --- | --- |
| P01 现场练习/后续交付 | 主持：“现在在白板画喜欢的动物。”小林：“我先来。” | 主持：“会后请把白板上的动物图整理后发给大家。”小林：“好。” | 左侧保存活动、零确认；右侧一项工作并接受。 |
| P02 产品属性/落实动作 | “遥控器只控制电视，不支持DVD。” | “遥控器只控制电视，不支持DVD。小林，请据此修改规格并发评审。”小林：“好。” | 两侧保存范围；右侧增加且仅增加修改规格工作。 |
| P03 同句多功能 | “今天决定取消图文电视功能。” | “取消图文电视功能，小林把这一项从规格表移除。”小林：“好。” | 决定与行动可共享一句，不能按同句引用相同而过滤。 |
| P04 笼统时段/领域分工 | “接下来有30分钟做下一阶段工作。我会上传纪要。” | “接下来30分钟，小林看组件概念，小周看界面功能。我会上传纪要。” | 左侧仅纪要；右侧三项工作，前两项assigned，时段不是deadline。 |
| P05 转述/本场采用 | “培训时老师常问：‘人事要我们核对孩子信息，能发群里吗？’” | 前句相同，续：“说回本园这次核对，小林请核对名单。”小林：“好。” | 左侧无本场任务/执行确认；右侧只建立当前核对任务。 |
| P06 引述问题/当前隐式需求 | “我在举一个老师们过去常问的问题：怎么恢复出厂设置？” | “客服反馈用户常问怎么恢复出厂设置，这影响我们减少重复咨询的目标，尚未决定怎么做。” | 左侧保存例子；右侧保留潜在需求，零已承诺任务，不能按“客服说/常问”全部过滤。 |
| P07 提议/承诺 | “我们可以会后细化这个场景，先作为一个建议。” | “小林，这个场景会后细化一下可以吗？”小林：“可以，我来。” | 左侧待采纳提议；右侧接受。两侧都有“可以”，不能词语过滤。另保留原C26作为未消歧压力例。 |
| P08 能力/条件工作 | “这类遥控器可以支持录像功能。” | “能否支持录像我去了解一下，如果我能查到的话。” | 左侧能力事实；右侧条件性候选，保留条件，零自动创建。 |
| P09 节目告知/新增筹备 | “感谢参加，稍后导览员带大家参观，请在入口集合。” | “导览路线还没排。小林请在活动开始前排好路线并发给导览员。”小林：“好。” | 左侧活动安排；右侧筹备任务及相对期限，日期可空。 |
| P10 主持交接/工作交接 | “上一位老师的环节结束，下面交给安老师。” | “这个客户投诉交给安老师跟进。”安老师：“好。” | 左侧零任务零确认；右侧真实工作。 |
| P11 状态汇报/新任务 | “纪要我已经发了，现在正放入共享文件夹。”无历史任务。 | “我会把纪要发给大家，再放进共享文件夹。” | 左侧状态汇报、零兜底确认；右侧保留未来工作。再给左侧提供唯一旧任务，检查按原契约更新。 |
| P12 决策变更/实施变更 | 带旧范围决策：“第一批范围改为员工和试点客户。” | 同上，续：“小林今天下班前改好灰度配置并发测试。”小林：“好。” | 两侧保存决定；仅右侧出现实施工作和真实期限。原M2另测，不能靠改写后的清晰负例代替。 |
| P13 可选交流/明确后续联系 | “有需要可以会后找老师交流。” | “还有两个问题，我会后单独联系袁老师。” | 左侧可选安排；右侧联系工作，保护C23。 |
| P14 当场澄清/新增跟进 | “核对的是哪个页面？”“移动端登录页。”“好，清楚了。” | “核对的是哪个页面？”“移动端登录页。”“好，我来检查这个页面的按钮文案。” | 左侧resolved；右侧保留检查任务；不因核对已解决关闭后续工作。 |

另作两类扰动：人名/实体同义替换后保持结论；将本人“好”换成另一人回应、明确拒绝或限定时，改变承接而保留工作内容。跨8段检查点的用例使用CP01/CP02/CP07及补充“先引用，后重新分派”变体，防止context_only成为无法重新打开的状态。

## 6. 实验顺序、归因和验收

### 阶段一：定位语义收益

冻结本轮原文、账本、首次records/events、配置，建立新的实验目录。先比较旧解释/核验、仅换核验、仅换解释、解释+核验；使用相同输入做配对比较。对于B的类型变化，保留A能表达相同语义的entity_only对照，标明这是类型表达方式比较。冻结上游实验衡量局部收益，不能替代从原文重新跑跟踪器。

局部集合包含七项误报、C29、C17、C11、两个M2条件，以及C02/C03/C07/C09/C19—C23和成组样例。C14单列结构恢复样例和conditional路由。语义初筛后再重新跑完整track→interpret→check→repair，观察前序分类影响及结构失败。

### 阶段二：分别验证规则与信息输入

C17用冻结解释验证新的报告路由；C14用冻结conditional解释验证候选保留和不自动创建。随后从Service正常入口以真实模型输出确认同一行为。C1/C2/C3按需做独立消融，固定比较时的其他提示、模型、repair开关和调用参数。

对C26/M2等已观察到歧义或波动的样例，预先固定至少两轮配对试验；保存每次首次输出，不挑最好结果。结构恢复另目录、另计分。若结果未优于A，保留A即可，不因B更结构化就默认接入。

### 阶段三：完整回归

候选方案冻结后重新跑30段真实语料、连续分工、10个上下文/取消场景、13项旧任务场景、M1/M2跨会和必要程序检查。原标签与审计标签同时计分，新的确认卡判定作为单独审查文件，不能重写旧MATCHES后冒充模型改进。

| 指标 | 观察方式与最低验收 |
| --- | --- |
| 正确任务、额外任务、漏项 | 原17项正确工作逐项保留；针对的7项额外任务减少，逐项交代残留；C14候选修复单列。若新样例或全回归仍有关键误报，继续按类别定位。 |
| 确认质量 | 9张已定位不当追问消除；C26改为待采纳含义；C11保留方案但不预设已分派。实际任务的承接/账号缺口和CP06等潜在需求不被隐藏。 |
| M2可见结果 | 旧任务完成、范围决定正确，额外items和错误范围确认均为零；不能只检查平台实际任务数。 |
| 上下文保存 | 原有实体、隐式需求、范围纠正、取消和后续补全仍可读；非任务信息有合适记录，未变成空输出。 |
| 程序行为 | 一次定向修正、未选中记录保持、失败恢复、已有权限和幂等契约不退化。 |
| 成本及失败 | 首次完整率、结构失败、恢复数、模型调用、token及耗时分开报告。新增阶段的收益需与成本同时呈现。 |

17/18召回与7项误报来自已使用过的回归集；合成对照也用于方案开发。它们能验证当前目标和机制，不能代表新会议上的泛化率。方案稳定后再增加新会议系列，不把已有30段改称盲测。
