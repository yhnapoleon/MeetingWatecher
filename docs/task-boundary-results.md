# 任务边界修复与测试结果

2026-11-15。当前实现位于 `context-v1` 路径。用户可在纪要中分别看到真实任务、待采纳提议、条件性工作、状态汇报和非任务上下文。实验调用真实模型，写入使用本地模拟器。

“我都会听到老师们这么说……我把孩子的信息发到群里，让家长核对可以吗？”原先被解释成当前参与者的任务。新完整流程保留外层转述，将两段教师提问放入会议上下文，不再向本场参会者分派工作。类似修复覆盖现场练习、产品范围、笼统工作时段、主持交接和活动介绍。

30段语料首次输出17项正确任务、0项多余任务；一项引文结构失败经一次恢复补回。但M2的范围决定仍会形成任务或错误确认，C20也残留一张文稿确认。因此，本轮降低了语料误报，尚未达到设计中全部语义验收标准。

## 1. 实现改变了什么

| 位置 | 实现与可见结果 |
| --- | --- |
| 跟踪、解释和核验提示 | 先判断当前话语用途及行动归属，再处理负责人、承接和期限；区分决定与落实工作、引用与本场采用、提议与本人接受。 |
| `context_state.py` | 新增 `context_only`；核验支持时保存至 `context_records`，无任务或确认。分类仍有争议时保留确认，允许后文追加工作。 |
| `context_new_work.py` | 无旧任务可关联、内容/时间/状态/关系受支持且无实际缺口的完成/进行中汇报，进入 reports；条件性工作保留为 candidate。 |
| 确认展示 | suggested 显示“待采纳提议”；conditional 显示原条件，禁止自动创建。局部日期疑问不吞掉工作和条件。 |
| `context_pipeline.py` | 条件性工作必须提供条件引文；保留一次定向修正及非目标记录不变的约束。协议版本升至7。 |
| `extract.py`、`service.py` | 增加上下文投影和纪要段落，显示完成/进展汇报；验证版本升至7。 |

独立审查发现“条件工作遇到局部时间疑问会丢候选”和“条件引文允许为空”两处契约缺口，已用失败测试复现并修复。程序测试从123项增至134项，全部通过。旧策略的条件性规则保持原契约；本轮没有增加生产模型阶段。
后续独立代码复核确认两项问题已关闭，未发现新增Important。最终语义评分由本轮主执行者对照原文完成，不是双人独立标注；[审查记录](../runs/2026-11-15-task-boundary/reviewer-findings.json)单列了审查范围和测试限制。

## 2. 如何比较

基线为 `runs/2026-11-15-full-validation`。原文、原标签和既有审计标签均保持原版本；新预测重新逐项审查并绑定输出hash，没有沿用旧预测的MATCHES。完整新结果在 `runs/2026-11-15-task-boundary/full-v2`，首次失败和恢复结果分别保存。

先固定旧账本，比较A（使用现有entity_only保存上下文）和B（显式context_only），再从原文运行完整流程。两者共用新的规则路由，比较的是语义表达方式。`a-frozen`初稿存在重复类型定义，因此只保存为预实验；正式A对照是`a-clean-frozen`。关键样例另做第二轮配对，未挑选最好的一次输出。

| 样例 | A第一/第二轮任务数 | B第一/第二轮任务数 | 观察 |
| --- | --- | --- | --- |
| C24 转述 | 2 / 2 | 2 / 0 | 固定旧账本时B也会沿用错误解释，存在波动。 |
| C26 提议 | 0 / 0 | 0 / 0 | 两者均保留待采纳提议。 |
| M2 范围变化 | 0 / 1 | 1 / 1 | A首轮修正成功，后续未稳定；B也未解决。 |

冻结旧解释、只替换核验提示的5例实验中，C24、C26和M2的错误仍通过。重新跟踪原文后，C24在两次完整运行中均无任务/确认。这个差异支持继续研究前序解释对核验的影响，但小规模对照不足以证明context_only这个类型本身稳定优于A。本轮保留B作为后续实验实现，同时使用其明确的上下文展示和路由契约；收益不能全部归因于新增类型。

C1只向任务分支补入Service已授权的历史decisions，提示不变，未增加调用。跨会M2仍产生范围调整候选和“今天”期限，故没有把该改动接入生产。当前事实、决策和任务分支仍按原并行方式运行。C2/C3尚未实施。

首次召回相同并不意味着逐项结果相同：新版本补回了C14条件候选，但C19解释阶段因重复引文未提供occurrence而失败。C19一次同配置恢复后，问题整理、老师解答、文字稿和公众号发布链条全部保留；这时原17项正确工作均在，加上C14共18项。恢复没有替换首次成绩。

按未审计的原标签，最终首次完全正确14/17，精确率82.4%、召回率77.8%、F1为80.0%；恢复后15/18，三项指标均83.3%。差异仍是C09的具体研究目标及C22/C23“会后”的时间口径，未为新结果调整标签。

第一轮完整B运行（`full`）曾出现C19/C20引文结构失败、C23因议题未细列被scope缺口挡住、C25合作需求降为背景。最终版补充了“执行前必要信息”和“开展时可细化信息”的区分，并保留具体合作目标下的潜在需求，重新跑了全部54例。最终C23恢复候选，C25保留两项潜在合作需求；C19仍需结构恢复。

## 4. 确认质量与上下文

基线语料共22张确认卡，已审查出9张不当追问，另有C26一张提问预设了已承诺工作。最终首次13张、恢复C19后14张。原9张不当追问均消失，C26改为待采纳；C14增加了应保留的条件卡，C25把项目对接和机构孵化分开保留。

仍有1张不当确认：C20的“这个文稿可以吧”被解释成“文稿与视频一并确认”。核验已指出新增动作缺乏依据，定向修正仍未消除该假设，最终保留一张含义未核实的泛化确认。因此，“任务零误报”不等于“纪要零冗余”。

C17的已发送和进行中状态进入报告，不再生成两张兜底确认；C11备用方案、C24转述、C29主持流程、C30导览安排仍能在上下文中读取。facts/decisions与context_records可能重复展示同一含义，本轮没有做语义去重。

## 5. 剩余根因与下一步

**M2仍是主要未解决项。** 单独旧任务场景中，最终版正确解释为范围决定，却被核验器质疑并同时标为遗漏，形成两张错误确认；真实M1→M2重放则直接多出一项候选和一张确认。“今天改一下范围”仍容易被当成需另派人执行的动作。授权历史决策不足以消除这种错误，不能仅扩大history就认定问题已修复。

下一组实验应固定M2和“范围决定后明确安排灰度配置”的正例，比较看见/不看见前序解释的边界判断。先验证它能否区分决定发生时间与实施期限，再决定是否增加模型阶段。保留这次没有改善的C1结果，不把决策与任务证据重合当作自动删除条件。

**C20与P07b属于确认资格和内容充分性问题。** 前者是模型新增动作导致的确认，后者是对象名称省略导致过度保守。应分别以“原文只提材料/明确安排处理材料”和“正常省略/确有竞争指代”作对照，检查工作内容和提问前提。不能通过隐藏所有classification争议或空missing_fields来消除卡片。

**结构失败仍独立存在。** 最终54例首次53例processed、1例partial；正反例首次31例processed、2例partial。失败分别为引文定位和缺失time.change。这三例均按原配置恢复一次成功，未引入循环重试或放宽引文校验。下一步可研究更简洁的证据输出协议，减少长JSON中的结构负担。

当前语料和合成例用于开发与回归，不是新会议盲测。上述百分比描述这批固定输入，不能推断线上泛化效果。
