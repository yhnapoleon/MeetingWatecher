# 旧任务更新实施计划

设计：[字段更新与必要澄清](../../task-updates-design.md)。本会话按用户授权直接执行，采用 test-driven-development 和最终独立代码审查。

1. 冻结输入及新行为契约，保存旧八例基线和代码快照。
2. tests/test_context_updates.py 从正常 Service 入口证明旧任务改期/进度失败；补边界与反例测试。
3. context_updates.py 实现日期操作验证及旧事件处理；context_state.py 区分汇报、歧义、执行受阻；context_pipeline.py 接入协议4。
4. extract.py 验证字段变更，Service/Simulator执行并审计；权限不放宽，防止旧值覆盖与重复写入；纪要正确显示执行受阻原因。
5. 合入时间提示并解释/核验change；全量测试通过后独立审查。
6. 正常入口跑12例及既有回归、跨会回放；保存首次失败、至多一次结构恢复、复核结果与成本，更新报告和交接。

不扩大隐式需求或短UI的新修复范围；旧语义标签不改。真实模型和程序测试分开报告。

## 执行结果（2026-11-15）

六步已完成。独立审查发现同步摘要会执行未经支持的内容修改，补失败测试后移除摘要更新，并追加冻结的 TU13 混合修改反例。实际模型暴露 TU11 缺少改期确认入口，最终程序按日期证据检查负责人后生成明确问题，复用同一响应验证。

111 项测试通过；旧契约与新契约分开记分，十三例新契约基线3/13、初版首次11/13、一次结构恢复12/13，最终程序重放13/13。最终独立跨会回放首次12/12。六难例语义F1仍为72.7%，默认未切换。详见[结果与局限](../../task-updates-results.md)。本轮没有解决同一目标多个矛盾最终更新、建议误判、研究目的遗漏和新任务相对时间多问。
