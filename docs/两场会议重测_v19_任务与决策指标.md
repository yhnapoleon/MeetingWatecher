## 当前效果与剩余问题

**“稍后在展示中补充”本轮没有变成制作任务。** 原句为 `ES2002b.A.dialog-act.dharshi.9`：“I'll add it later, I guess the presentation.” 本轮先解释为含义不明，核验读取前后发言后将其改为会议发言，修补与复核接受为 `context_only / meeting_discourse`，最终既没有任务，也没有澄清卡。该条本轮编号为 R13；旧报告中的 R21 与本轮组件分工 R21 不是同一条记录。[第二场完整结果](../runs/2026-11-18-full-v19-retest/ES2002b/result.json)

**仍有 1 条任务误提。** 营销人员说“if that's possible we might consider getting into it”（`ES2002b.D.dialog-act.dharshi.158`），是在建议考虑语音识别。模型把它归成 `conditional_work`，最终 R14 同时进入 candidate item 与可建任务确认卡。原文尚未形成“条件成立便执行”的承诺，按冻结严格任务口径计 1 FP。这与旧结果的语音识别误提是同类问题，不能因为保留了条件措辞就计为正确任务。

**决策漏掉了红外传输。** 第 738–742 段，项目经理建议把创新放在用户界面，沿用已验证的红外方式。首轮决策草稿包含此项，独立核验 topic 10 也判为有效，但最终裁决没有保留，因此 AMI 参考 D7 记 1 FN。任务分支的背景记录中仍有这条内容，不能替代决策分支的命中。

两场另保留 4 张不能直接建任务的卡：第一场的价格比较需求和设计范围澄清，第二场的企业标识需求和分组设计建议。第一场设计范围被放入“待澄清意向”，说明任务入口的精确率不等于澄清卡分类精确率，人工阅读负担仍在。两场全部确认卡共 9 张，其中其余 5 张与任务结果重叠，已按记录去重。[第一场确认卡](../runs/2026-11-18-full-v19-retest/ES2002a/requirements.json) · [第二场确认卡](../runs/2026-11-18-full-v19-retest/ES2002b/requirements.json)

## 复现入口

在项目根目录运行以下命令，仅重新汇总已有人工判分、验证最终数据库，不调用模型：

```powershell
$env:PYTHONUTF8='1'
python experiments/full-meeting/score_retest.py runs/2026-11-18-full-v19-retest
python experiments/full-meeting/verify_retest.py runs/2026-11-18-full-v19-retest
```

判分文件绑定最终 result.json 的 SHA-256；脚本要求每条任务、每行决策都有审核记录，并验证参考编号及去重计数。原始输入、推理配置、模型请求与响应、源码快照、数据库、纪要和各阶段结果均保存在各会议目录内。

如需再次调用模型，建立新的输出目录，复制对应会议的 input.json 与 inference.json，再运行：

```powershell
python experiments/full-meeting/run.py --out <新的会议输出目录> --live --review-decisions
```

这个入口从空 SQLite 开始。发生需要显式恢复的 partial 时，可用 `python experiments/full-meeting/retry_retest.py <输出目录>` 保留首次失败并调用一次现有恢复入口。生产代码和提示在本轮未修改；实验脚本仅补决策核验开关、partial 留存、判分与离线验收。
