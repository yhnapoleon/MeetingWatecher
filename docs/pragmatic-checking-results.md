# 短回应、工作范围与时间指向：修复和实验

C02 中，主持人先说明下一场会议时间，再把设计工作交给工业设计师；设计师随即说 “Yep”。上一版已经提取出正确的工作和接受回应，核验却以“也可能回应会议时间”为由降成候选。这不是原文出现了冲突，而是核验要求排除所有理论上的其他解释。

本轮把判断改为：结合说话人、当前问答目的、分工结构和相邻回应，采用正常对话中最合理的解释。实际发生转题、拒绝、限定接受范围或由其他人回应时，再按这些事实处理。明确工作可以在开展过程中细化；不要求会话写成完整项目说明书。

## 改动及依据

[Purver 等的行动项研究](https://aclanthology.org/2007.sigdial-1.4/)把行动安排放在讨论和承接构成的对话片段中处理。本项目据此继续用完整片段连接分工与短回应，而非要求一条回复独立包含所有内容。[Plank 等对标注分歧的研究](https://aclanthology.org/P14-2083/)提示应区分语言解释差异和明确错误；本轮将原始摘要的具体化与输入逐字稿必须支持的内容分开。

`context-v1` 协议6接入三项改动：

1. 解释和核验都允许正常上下文承接。收到邮件等附带说明不自动切断接受关系；核验也会指出把明确安排降成隐式需求、添加多余确认等错误。
2. 核验指出记录或事件字段错误后，针对这些记录修正一次，再独立核验。允许补回遗漏事件、撤掉错误事件；其他记录、事件及其核验保持不变。修正后的语义仍有问题时，继续展示对应待确认内容。
3. 工作描述先表达动作和对象，再保留改变执行内容的要求。附带的“未定截止时间”不扩写成材料内部的缺陷，已回答的事实不变成新的研究目的。

修正属于一次附加机会。若该步骤结构或调用失败，保留初次核验的结果及待确认记录，trace 保存错误。正常 Service 仍可完成已成立工作；同一来源再次导入复用结果，不自动反复修正。首次解释或首次核验失败仍使用原有的 partial 恢复机制。

## 标注复查

C09 的营销负责人问下次会前具体看什么，主持人回答说明书，并解释大家堆着却不用的背景。原始 AMI 摘要写成“研究消费者对说明书的看法”，旧标签把这个具体目标设为必需内容。逐字稿支持“研究说明书相关问题”；消费者看法是合理展开，但不是唯一展开方式。完整源对话在解释背景后还有一句营销负责人的 Okay，当前评测片段未包含它；本轮不修改输入片段。

旧标签保持原样，新口径单独保存在 [pragmatic-audit](../data/action-semantics-v2/pragmatic-audit/manifest.json)。C03 市场角色的短回应按接受安排理解。C26 的提议标签保持原样，继续观察提议与承诺的区别。

另一个自编样例 PN02 说“营销这边具体研究什么”，只明确了团队；原测试期待直接指派个人，过于具体。审计后接受团队候选。补充的 PN03 将原话改为“我具体研究什么”，模型能形成个人任务。原测试及期望保留，汇总同时列出原检查与审计后的检查。

## 相同六个难例的结果

六段原文共有六项应保留工作，C03含两项，C26是建议。下表统计内容、负责人、承接、时间、操作全部正确的任务数；“多出”表示与当前标签相比额外形成的候选。

| 方案 | 旧标签完全正确 | 审计标签完全正确 | 多出候选 |
| --- | ---: | ---: | ---: |
| 上一版输出 | 3/6 | 3/6 | 0 |
| 固定上一版解释，只换核验 | 5/6 | 6/6 | 0 |
| 新解释＋新核验，关闭修正 | 4/6 | 5/6 | 1 |
| 对上述同一输出接入一次修正 | 5/6 | 6/6 | 1 |
| 最终提示重新解释、核验及修正 | 5/6 | 6/6 | 0 |

旧口径完全正确召回从50.0%升到83.3%；最后一项差异是 C09 的标注口径。采用审计标签后最终为6/6。仅改标签对上一版输出仍是3/6，因此任务恢复并非仅由评分标准改变造成。

“固定解释只换核验”直接使用原始 records/events，确认核验过严是独立原因。“新解释＋核验”首次漏掉UI工作，自动修正依据核验意见补回了它。相同一轮的市场工作、邮件实体等其他记录没有被重写。C20 的文稿解释修改后仍不成立，复核继续保留待确认，不形成额外任务。

额外保留了一轮“旧解释提示重新采样＋新核验”，旧/新标签为4/6、5/6。该轮请求没有命中预期的解释缓存，不能当作固定解释对照，未混入上表。

## 指向和实际行为检查

十个中文对照首次任务数和写入数按原期望通过9/10；未通过的一项是上述 PN02 标注问题。审计后还有两项描述错误：PT01 把任务没定期限写成条款没期限；PT04 把已回答的付款时间问题加成新的核对目的。

| 对照 | 最终观察 |
| --- | --- |
| 负责人收到安排后说“好”，前面有会议时间 | 创建对应任务，会议时间不当成任务期限 |
| 回复明确说只接受会议时间、任务还要评估 | 保留任务候选 |
| 小周替被分派的小林说“好” | 小林的工作仍是候选 |
| 分工后附带“材料通过邮件发给你”，负责人说“好” | 接受分工，不把邮件单独生成任务 |
| 只抱怨大家不看说明书 | 不生成已承诺任务 |
| 个人询问研究什么并接受回答 | 创建研究说明书任务，保留相对期限 |
| 合同/任务时间四组对照 | 修改前语义2/4正确，动作优先写法后4/4正确 |

四组时间对照冻结相同的账本、事实和决策，只重新解释和核验。PT01 最终写为“核对合同付款条款；目前没有约定截止时间”，不再断言付款条款本身无期限。PT02 明确要求列出条款缺少付款期限的问题，这个要求仍被保留。所有四例均实际创建核对任务，不设置任务截止日期。

旧任务的完成、明确改期、试探改期三个代表用例也从正常 Service 入口重新调用模型验证：完成任务且保留原期限、把期限改到指定日期、试探改期保留旧日期并待确认，全部通过。程序测试覆盖修正补事件、撤事件、其他事件保持、修正失败保留原结果以及下层缓存恢复。

最终123项程序测试通过。独立只读审查检查了目标覆盖、事件补删、ID和证据、复核与缓存路径，无待修Critical/Important；审查指出的可选修正恢复语义已明确为“一次尽力修正”，并用正常Service验证失败时其他任务照常创建、再次导入不重复调用和写入。

## 仍有波动的地方

“我们可以会后细化”在本轮不同解释输出中出现过 suggested 和团队承诺两种判断；最终轮正确保留为建议，但这个边界尚不稳定。C20 的文稿被解释为“也给大家确认”时，一次修正仍可能重复同一错误，当前主要靠再次核验保留确认记录。下一步应加入不同措辞、相邻任务和后续回应的成组样例，检查这种波动，而不是继续要求所有回复说得更明确。

## 原件和复现

本轮是已知错例与合成对照实验，语义复核和标签审计由代理完成。新增119次模型调用，共536,830 token，缓存复用不重复计费统计。所有模型语义输出均保留首次结果。固定解释实验首次出现脚本包装函数参数错误，影响事实和决策调用；修复脚本后完整复用已有模型响应，零新增调用完成 Service 验证，原失败输出仍保留。
