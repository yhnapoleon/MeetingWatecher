# 完整会议失败：系统溯源与方案

**后续实施：** 用户确认后已完成P0修复和单场恢复，结果见[修复报告](完整会议证据协议_修复结果.md)。下文保留调查阶段的观测及方案，未改写首轮失败。

2026-11-17。诊断对象为完整会议ES2002a的首轮失败，范围是模型请求构造、证据协议、校验、恢复和保存。本轮没有修改生产代码，也没有调用会议模型；仅复用保存的请求响应做离线实验，并查阅官方接口资料。

**直接阻断原因是输出证据类型错误；系统根因是同一证据契约没有贯穿提示、输出schema和恢复链路。** 模型已生成三项分工，但系统给出了相互冲突的格式信息，又缺少能够纠正这类错误的恢复路径。不能将这次失败归因于任务语义太难、输出被截断或数据库丢失。

建议先完成“输出契约统一＋有界证据修补＋真实失败回归”，再定向恢复这场会议。缓存和输入膨胀另列后续工作，避免把解决阻断扩大为整套框架重写。[可执行实施计划](superpowers/plans/2026-11-17-evidence-protocol-repair.md)

## 1. 从输入到失败的证据链

| 边界 | 实际观测 | 判断 |
| --- | --- | --- |

| Service→保存 | partial、16事实、6决策、4未决已保存；重开和重复提交一致 | 持久化正常，没有把未校验任务执行出去 |

## 2. 离线因果验证

诊断脚本在socket被禁用的环境运行。只在内存里改变一项：把输出证据对象替换为其已有的segment_id，保持其他字段不变，再送入当前真实解码器和解释校验器。原始响应、数据库及正式结果均未改写。

| 检查 | 第一次响应 | 第二次响应 |
| --- | ---: | ---: |
| 错误证据槽位 | 26 | 27 |
| 证据对象数 | 96 | 90 |
| 原始segment_id确实存在 | 96/96 | 90/90 |
| 字符区间满足非空且未越界 | 93/96 | 90/90 |
| 其中仅截取一个字符 | 0 | 90 |
| 原样进入解码器 | 拒绝 | 拒绝 |
| 仅换成ID数组后，完整结构校验 | 通过 | 通过 |
| 仅换成ID数组后，真实解释校验 | 通过，3事件 | 通过，3事件 |
| 现有证据修补入口 | 不接受 | 不接受 |

这证明了本次解释节点的直接阻断点是证据表示，不是其他任务字段结构。**不证明草稿已经语义正确，更不证明可以自动删除offset后正式放行。** 删除offset会扩大引用范围；第一次有越界值，第二次大量单字符引用也未提供可靠的字符级证据。正式修复应重新选择证据，并经过现有独立工作核验。

证据：[离线审计JSON](../runs/2026-11-17-evidence-protocol-diagnosis/audit.json) · [可复现诊断脚本](../experiments/full-meeting/diagnose_protocol.py)。运行：`python experiments/full-meeting/diagnose_protocol.py`。

## 3. 为什么已有成功样例与测试没有发现

GN25、GN29此前的low解释请求也含同一句对象说明，也没有output_schema，但都返回了合法字符串引用并被接受。因此，不能声称该句必然导致每次失败，或本次换成low才引入问题。可确定的是系统存在歧义，遇到对象输出后又无法恢复；模型选择哪种表示具有不稳定性。仅删除提示冲突的改善幅度仍需真实调用验证。

代码快照显示，冲突尾句至少已存在于`2026-11-17-interpret-reliability/focus/source.zip`；其后的final-source、interpret-budget-low及本轮整场快照均保留它。任务边界修复前后当前wire文件摘要相同。这将问题追到原始ID及字符偏移传输改造期间，而非最新progress/report分流。仓库没有Git历史，不能据此断言更精确的引入提交。

现有`test_context_wire`的5项、`test_reference_repair`的8项全部通过。它们验证了输入span压缩、Q别名转换、未知ID修补、预算及重复调用等，但未覆盖完整请求中的提示/schema一致性，也未覆盖“记录完整、证据对象类型错误”的实际响应。测试成功与本次失败并不矛盾：缺的是跨边界案例，而不是更多同类字符串引用测试。

## 4. 系统层面的问题分级

### P0：解释协议没有统一定义并执行

内部Python schema已经存在，但解释阶段只将它转成空数组示例拼进提示，没有像check/repair阶段一样携带完整output_schema。输入ledger使用精确span，输出使用整段ID，本可共存，却在公共提示尾句中混写。应让解释请求schema、示例、本地结构校验和严格恢复均来自同一份INTERPRET定义，明确区分输入span与输出ref。

影响范围包括使用`_recorded_stage`的interpret_work、check_work、repair_work、check_repair公共提示；其中“缺少机器schema”目前直接确认在interpret_work。tracking和minutes走其他请求构造路径，不应未经核查一并修改其引用类型。

### P0：恢复分类过粗，入口拒绝了可局部修补的草稿

当前将引用类型错误、未知ID、缺字段等汇成schema_invalid；证据补丁又只接受整体结构完全符合当前schema的草稿。应检查“除证据值外的结构与身份是否完整”，只允许对预先声明的证据槽位修补。不能通过放宽业务校验、丢弃错误字段或无限重试来绕过问题。

### P0：错误反馈不可操作，且严格恢复路径不可达

现有错误把整组无效值展开后截断，早期槽位占满反馈。应保留完整审计，但给模型结构化的错误类型、字段路径、期望/实际类型和正确例子，重复错误聚合后只发有限示例。interpret_work必须携带schema，才能使用已有严格恢复；证据补丁本身也应在受支持接口上使用严格工具参数。

### P1：缓存依赖比实际阶段依赖更宽

`context_v2.run`用整份pipeline配置构造共同父目录。离线探针只改interpret提示摘要，就改变了该父目录，因此已成功的tracking节点也换了查找位置。现有“同配置重复提交不调用模型”成立，但不等于“修复解释提示后能自动复用tracking”。

短期验证可在独立实验目录中，核对原文、历史、tracking提示/配置/实现摘要后显式导入已接受tracking，并记录来源，不能把旧节点拷入新目录就算验证。长期再把tracking缓存归属于实际tracking依赖，同时保留校验版本、模型身份和输入摘要；不默认接受过期缓存。

### P1：输入紧凑化没有覆盖所有阶段

6000字节/128段限制约束的是每次新增窗口；实际tracking请求仍带此前全部发言前缀、累计ledger、证据目录及schema枚举。首轮11次调用中的79.4万tokens并非全部来自任务思考或重试。

| 实际请求 | API输入tokens | 主要输入体积（UTF-8字节，不等于token） |
| --- | ---: | --- |
| 最后一个tracking窗口 | 118,689 | previous 119,310；meeting 87,913；evidence_catalog 57,063；schema 48,353 |
| 第一次解释 | 72,834 | meeting 87,913；ledger 74,565；candidates 12,081 |
| 首次纪要核验 | 121,411 | schema 144,041；meeting 87,913；evidence_catalog 45,057 |

tracking与三次纪要检查合计559,559 tokens，占本轮总量约70.5%。应先消除同一请求内重复的原文与枚举、复用现有确定性投影，再考虑历史压缩；不能未经语义验证删掉早期发言或只保留摘要。缓存命中量与未命中量应单列，total_tokens不直接等于计费成本。

### P1：局部失败的展示仍有歧义

纪要顶部已注明partial，属于正确保护；但“行动项”下仍显示“无”。用户只看该节容易误以为没有任务。利用现有`_errors.field`即可显示“行动项提取未完成”，与成功提取但为空区分，无需新增业务状态模型。

## 5. 官方资料调研及选择

| 官方结论 | 对当前方案的约束 |
| --- | --- |
| JSON Output保证合法JSON，并要求提示中给出目标格式示例 | `json_object`不能代替字段schema或本地校验。[JSON Output](https://api-docs.deepseek.com/guides/json_mode/) |
| Strict工具模式按function JSON Schema约束参数；使用beta地址，且对象字段必须required、additionalProperties=false | 复用项目现有strict工具适配，不另造输出框架；继续保留本地证据成员和业务核验。[Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/) |
| Strict支持思考模式，但thinking下不支持required或指定工具名的tool_choice，会返回400 | 当前强制submit_result必须关闭思考；可用于证据修补，不能直接把它用于保留low思考的首轮解释。[Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/) |
| Schema的properties不会自动禁止其他字段，required与additionalProperties负责不同约束 | 输出接口明确封闭字段集合，未知字段不能被适配器静默忽略。[JSON Schema对象规则](https://json-schema.org/understanding-json-schema/reference/object) |
| 服务端上下文缓存复用相同请求前缀 | 这是成本优化，与应用层“节点已经通过校验、不再请求”不同，不能替代阶段缓存依赖修正。[Context Caching](https://api-docs.deepseek.com/guides/kv_cache/) |

推荐方案保留首轮解释的现有low/32768设置，同时提供明确输出schema。遇到仅证据格式/ID问题时，保留语义草稿，最多一次非思考strict证据补丁，再完整结构、身份、引用和语义核验。其他结构错误走现有有界完整恢复。暂不选“所有输出直接改为对象”“无条件对象转ID”“提高预算多试几次”或“一律关闭思考”：这些选择要么改变契约/证据范围，要么没有解决已证实的边界问题。

## 6. 实施与验收顺序

1. **修复协议边界。** 同一schema生成解释输出契约与非空引用示例；输入span说明与输出ID规则分开；非法输出继续拒绝。
2. **修复恢复路径。** 结构化引用错误，完整非证据结构才允许补丁；严格模式只用于受支持接口与非思考格式修补。保留请求数、时间、token上限及终止状态。
3. **用真实失败验证。** 两份保存响应都应进入正确修补分支；模拟补丁不得改任务描述、负责人、时间或记录身份，仍需工作核验。空证据、未知ID、缺结构、重复身份、截断输出、402、重复提交均有对应边界检查。
4. **仅恢复这一场验证效果。** 新目录保留新旧证据，经过验证后显式复用tracking；事实/决策保留。由于成功工作结果改变了纪要核验上下文，需要重新核对依赖它的纪要阶段，不能仅删除旧错误使状态变为processed。首轮最多8次HTTP，达到任一现有节点上限即停止，不自动扩大预算或换会。
5. **验收用户可见产物。** 三项参考分工进入正式可用任务/确认入口，负责人对应正确；新增输出逐项核对原文；工作时段不变成硬截止；完整Service保存、重开、重复提交一致。区分“复用tracking后的完整Service恢复”与“全阶段重新推理”，不把单例成功当泛化成绩。

P1的缓存、输入体积和失败展示另行实施，不作为P0混合改动。当前仍处于诊断和方案阶段，ES2002a首轮状态仍为partial，生产策略仍version16。
