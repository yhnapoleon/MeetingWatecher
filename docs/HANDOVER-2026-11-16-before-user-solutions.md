## 2. 已定位的具体原因

### 多余追问并非全由模型生成

v4 small-v2/B-r2/M2 最终问：“请确认这项工作的具体内容、负责人，以及是否决定执行。”

保存结果的零调用复现显示：reduce_v2 根据再核验清空 missing_fields/question；reduce_context 又将 check.issues 中的 owner 当作未补齐信息加回，并因 commitment=unknown 添加 commitment，最终套用通用问句。这里混淆了“模型解释需要修正”与“用户仍需补充什么”，还混淆了执行决定与个人承接。实际原话只没明确个人负责人。

证据：[question-trace.json](../runs/2026-11-16-user-review/question-trace.json)。

### introduced_by 缺失源于模型输出，契约没有及时阻止

本轮前 A-r1/G-omitted 的原始 repair 响应已缺 introduced_by，后处理未删除。context_protocol.py 把它加入 properties 却没加入 required；v3 继承该结构，生成的“完整 JSON”示例不含此字段，而文字提示要求新增记录填写。schema 验证允许缺失，直到末端 apply_repair 读取字段才失败。

已知缺陷是说明/示例/消费者契约不一致且校验过晚，不能仅靠一例证明模型遗漏完全由示例导致。旧测试多数直接构造了完整绑定。v4 已有部分程序绑定机制，但 A 继承 v3 未使用。后续优先考虑复用确定性绑定或区分新增/已有记录协议。

此前单加 introduced_by=O1 的离线合并对照通过，仅证明阻断点，不改变原失败分。

### “Incomplete event checks”两例实际是多造 E2

前轮将其称为“漏事件”不准确。a-cross-r2/M2 和 D-r2/G-omitted 输入都只有 E1，模型均返回 E1、E2：
- 前者将范围调整改判 work，直接核验尚未创建的范围任务。
- 后者发现发送测试结果的遗漏，直接核验尚未创建的发送任务。

两份响应正常结束，不是截断。核验阶段混入了新增/改写事件职责；输出 schema 允许任意 event_id，末端集合校验拒绝整个输出，且缺/多/重复共用一个错误名。失败发生在修正计划前，正确 E1 也未转成旧任务更新。

离线仅移除额外 E2 后，现有 check 均通过，但仍需分别修正 R2 或补 O1，不能因此将最终任务判成功。按用户新定义，前者提出范围工作不再算语义错误，越过阶段生成 E2 仍是协议错误。

证据：[protocol-trace.json](../runs/2026-11-16-user-review/protocol-trace.json)。
