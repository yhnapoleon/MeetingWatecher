# Context-v5 最终 18 次失败的原因

2026-11-16。分析对象是 `full-compact-final` 中 95 个场景、两轮运行后的 18 次失败，涉及 12 个场景。以下结论来自保存的原话、模型请求与响应、阶段结果，以及两项离线复现；本次没有调用模型，未改生产逻辑，原评测结果仍为 172/190。

后续独立审计与系统方案见[设计文档](superpowers/specs/2026-11-16-context-v5-system-remediation-design.md)。该审计保留十次 unresolved 失败，但明确它们来自事后语义复核；任务的 context_only 不证明纪要不得保留未决。P05a r1 已保留培训归属，错误更准确地说是将片段未给答案升级为本场未决；C09 不代表研究细节全定，C13 不代表完整会议无其他后续，P08b 应修复命题而保留真实未知。下文为首次诊断记录，使用时应一并阅读后续审计边界。

主要问题有两层：模型在部分场景中误判了问题归属、工作资格或描述含义；程序没有在最终输出处发现这些错误，其中 HT04 还存在可确定复现的问题文本与缺口不一致。18 次按主要故障位置归类如下，P08b 第一轮另有任务描述偏移，不重复计数。

| 主要故障位置 | 次数 | 场景与轮次 |
|---|---:|---|
| 独立 facts/unresolved 分支的语义错误未经复核进入纪要 | 10 | C09 两轮；P05a、P06a 两轮；P05b 第一轮；P08b 两轮；C13 第二轮 |
| 非本场工作被当作提议或需要补问的工作 | 4 | C24 两轮；C11 第一轮；C20 第二轮 |
| 旧任务关联不明，却生成承接问题 | 1 | HT04 第一轮 |
| 推理耗尽输出预算 | 2 | CP01 两轮 |
| 返回的 JSON 缺少数组闭合符 | 1 | C14 第一轮 |

## 1. 十次未决事项错误：生成分支独立，最终没有核对归属和状态

C09 中，营销先问下次会议前研究什么，后文回答 “Instruction manuals”，随后得到 “Okay”。工作分支正确提取了说明书研究任务，纪要却仍写“营销……具体关注哪些方面……尚未确定”。两条分支对同一个问题给出了相反结果。

对这十次失败逐一检查，已确认：facts 请求包含完整原文；错误的 unresolved 已出现在原始模型响应中，并原样进入最终结果；check_work 请求没有 unresolved 字段。因此这里不是输入丢段，也不是纪要渲染改写了正确输出。

[extract.py](../meeting_eval/extract.py) 的 `evidence_extract` 并行执行 facts、decisions 和任务流水线；facts 独立生成 facts/unresolved。工作分支的核验与修正只处理工作记录和事件。合并后的 `validate` 检查 statement 类型、证据编号等结构条件，不检查这条问题是否属于本场、是否已被后文回答、是否与任务结果矛盾。有效的证据编号可以指向一句真实问句，却不能证明它仍是本场未决事项。

| 场景 | 具体错误 | 工作分支或原文提供的反证 |
|---|---|---|
| C09，两轮 | 把先前的研究范围问题保留为未决 | 后文已回答说明书；任务分支已保留对应工作 |
| P05a，两轮；P05b，第一轮 | 把培训中转述的“能发群里吗”列为本场待答问题 | 工作分支把引用部分判为 context_only；P05b 另有本场核对名单工作，二者不能混同 |
| P06a，两轮 | 把“我在举一个老师们过去常问的问题：怎么恢复出厂设置？”变成当前未答问题 | 原文明确是过去问题的举例；工作分支为 context_only |
| C13，第二轮 | 把“语音识别未纳入最终产品”改成“会议结束时仍未解决” | 原文是在回顾产品取舍，并说各项问题已处理、“that's good”；未纳入不等于仍待决定 |
| P08b，两轮 | 把“能否支持录像我去了解一下，如果我能查到的话”改成“小林能否支持录像、能否查到录像” | 小林是了解情况的人，“查到”的是相关信息；原文没有说由小林提供录像支持或寻找录像文件 |

P08b 不宜把所有未知信息直接删除：录像支持情况确实尚待了解，错误在于主语和查询对象被改写。第一轮的任务描述还额外加入了“会议录像”，这个限定原文没有；检查器沿用该限定并判为 supported。第二轮任务描述未出现这一限定，但 unresolved 仍有相同偏移。

facts 提示已经要求“前面提问、后面回答的不留在 unresolved”，因此 C09 不是缺少这条规则。提示把“未被采纳的建议及确实待回答的问题”纳入 unresolved，却未同样明确引用、举例与本场议题的归属；即便补充归属规则，最终合并处仍需要核对实际输出。不能直接用工作分支的 context_only 删除全部未决事项，因为真实的产品选择也可能没有执行任务，却仍需要决定。

## 2. 四次工作资格误判：错误发生在不同阶段

**C24：外层转述没有约束内部问句。** 原话以“我都会听到老师们这么说”引出教师的常见问题，随后举“信息发群让家长核对可以吗”“体质健康结果能发群吗”。第一轮追踪把两条线索记为 context_only，但解释阶段把第二问改为本场建议，检查器也认可。第二轮在追踪阶段就把转述内容记为 work，后续继续沿用。完整原文仍在请求中，问题是模型解释了引号内的动作，却没有维持外层话语归属。提示已有这条边界，不能再用“没有告诉模型注意引用”概括原因。

**C11：首次检查发现错误，修正和复检没有保住这个判断。** “如果语音识别在财务上不可行，可以改用哨子”是产品备选方案。第一轮的阶段链为：

`解释 work → 首检 context_only，并指出 future_work 证据不足 → 修正仍返回 work/future_work → 复检改判 supported → 最终问是否采纳提议`

修正保留了原工作描述和关键分类，复检又将其解释为“可待采纳的工作建议”。第二轮同样经过分类纠正，但修正改成 context_only，最终没有多余问题。已能定位到修正后的分类判断反转；保存的轨迹不足以解释模型为何反转。复检覆盖前次判断本身未必错误，但这里它没有给出原文中新增的执行工作依据。

**C20：先预设文稿需要处理，再把缺少动作当成待补信息。** 原话明确安排剪辑视频、给大家确认，随后只说“还有这个文稿可以吧”。第二轮追踪已写成“会后还有文稿需要处理或确认”，解释记录 R2 保留 ambiguous，检查器认为具体动作是需要询问的缺口。于是“只提及对象”变成“已经存在一项工作，只是不知道做什么”。第一轮追踪也有文稿含义不明的线索，但下游将其保留为 entity_only，没有追问。这里不是自动补入的彭老师实体直接生成了任务，最早的预设出现在文稿追踪描述中。

四次都涉及工作资格，但不能归为同一个阶段故障。下一步应检验“原话是否已经建立这项工作”，再判断承接和缺失信息；保留当前真实提议、当前采用转述内容、明确并列执行等正例，避免用引用词或缺动作字段一概过滤。

## 3. HT04：模型漏报关联缺口，程序把问题留错了

原话报告上周的登录失败案例整理已经完成并发群，历史中却有两条内容相同的任务。第一轮模型正确写出 `state=completed`、`relation=ambiguous` 和两个候选任务，但记录的 `missing_fields=[]`，首检也给出空的 gap_checks。对 ambiguous 的 supported 判断只表示“确实无法唯一关联”，不表示关联已经解决。

后续代码走了以下路径：

1. [context_protocol_v3.py](../meeting_eval/context_protocol_v3.py) 的 `adapt_check` 要求原记录已有缺口被检查，但没有根据 ambiguous relation 补出关联缺口。空缺口通过了协议检查。
2. [context_state.py](../meeting_eval/context_state.py) 的 `reduce_context` 仅把 relation=existing 视为已有任务。ambiguous 落入另一分支，加上完成汇报中的 commitment=unknown，于是自动增加 commitment 缺口并生成“是否已经承接”的问题。
3. [context_v3.py](../meeting_eval/context_v3.py) 的 `reduce_v3` 识别到这是完成汇报，删除 commitment 缺口，追加可选旧任务列表，但没有重新生成问题。最终出现 `missing_fields=[]`，问题仍问“是否承接”。

离线执行保存的 pipeline，通过同一版本 `reduce_v2` 和 `reduce_v3`，完整复现了最终 review_records。只在内存中补入关联缺口和“这次完成的是哪一条旧任务？”后，最终问题就针对旧任务选择，且仍不执行创建或更新。第二轮模型主动给出了 relation 缺口，正常进入这条路径。

因此这例有两个相连的原因：上游漏报真实的关联缺口，程序又从 commitment=unknown 推导出不适用于完成汇报的问题，并在删除缺口后留下旧问题。修复应让关联状态、可执行操作、缺口与问题保持一致；没有证据表明此次错误更新了历史任务。

## 4. CP01：在看到最终澄清之前就耗尽预算

两轮均失败于第一个追踪检查点，输入仅为前 8 段，尚未读到第 9 段的范围澄清和第 10 段的承接回应。响应已经收到，`finish_reason=length`；客户端随后以 `Incomplete model response` 中止任务分支。

| 轮次 | 输入 tokens | 输出上限及实际输出 tokens | 其中 reasoning tokens | 最终内容字符数 |
|---|---:|---:|---:|---:|
| 第一轮 | 6,650 | 16,384 | 16,384 | 0 |
| 第二轮 | 6,650 | 16,384 | 15,922 | 1,309，未完成 |

直接原因是推理消耗了绝大部分输出预算；两轮都未获得完整增量结果，后续澄清无机会进入流水线。不能把它判为“模型看了完整对话仍不理解承接”。前缀含尚未明确的工作范围，当前调用又要求同时维护实体、线索和逐段增量；这些可能增加推理负担，但仅凭本次记录，不能确定哪个因素导致耗尽，也不能保证增加预算就能稳定通过。后续应固定这一失败前缀，隔离比较推理设置或输出契约的影响。

## 5. C14：正常结束的响应仍不是合法 JSON

C14 第一轮第一个追踪检查点成功，第二个检查点收到 813 字符内容，`finish_reason=stop`，输出 tokens 为 2,674，未触及 16,384 上限。`json.loads` 在位置 811 抛错，尾部的数组少了 `]`。

离线在该位置插入一个 `]` 后，JSON 解析和 `expand_delta` 的协议、证据、更新顺序校验均通过。这证明当前阻断点是模型生成的 JSON 语法，而非旧版追踪更新倒序，也不是本地校验器误拒绝有效响应。当前客户端请求 json_object 格式，仍以本地解析的实际结果为准。

补字符只用于定位，没有替换历史输出，也没有运行后续模型阶段。补后的线索最新状态为 context_only，但候选仍被保留；后续能否从完整原文正确解释条件性调研，尚未验证。最终 items、updates 各记录一次同源异常，按失败场景计为一次。

## 后续处理顺序

1. 修复 HT04 的确定性状态与问题错配，用保存的上游结果验证不再询问重新承接，且歧义消除前仍不更新任务。
2. 在最终结果核验中覆盖 unresolved 的本场归属、最终状态和主宾语含义，同时保留真实未决问题。这对应十次失败的共同缺口。
3. 固定 C11 的分类反转、C20 的对象提及、C24 的外层引用和 P08b 的描述偏移，验证工作资格及描述核验，而非靠反复重跑挑选一次正确响应。
4. 单独处理 CP01 的推理预算与 C14 的输出格式。两者发生机制不同，格式检查不能解决预算耗尽；格式修复也不能证明语义正确。

诊断运行验证了运行快照内 134 个文件与本地对应文件一致，并在结束时核对所读 396 份证据哈希未变化。十次 facts 错误均断言了完整输入和原始 unresolved 与最终结果一致；HT04 的最终问题被精确重放；C14 的解析及增量校验通过。模型为何在个别语义判断中摇摆、CP01 怎样配置才能稳定完成，仍需后续受控实验，本次不作已解决结论。
