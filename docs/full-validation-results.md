# 完整复测：任务找得较全，误报集中在任务边界

当前 context-v1 协议6在30段真实会议摘录中，生成24项任务或候选。按审计后的统一口径，其中17项完全正确、7项多余，任务准确率70.8%；应找到18项，找到17项，召回率94.4%。主要问题是把现场活动、产品决策、转述和提议放进了任务列表。短回应和连续分工在本轮保持正确。

本轮固定当前模型、程序和提示重新调用，未在跑测中调优。覆盖30段真实语料、1个连续分工窗口、10个上下文/取消场景、13个旧任务更新场景、M1/M2跨会流程及123项程序测试。真实语料的原开发集和历史保留集均已使用过，本轮是完整回归；语义复核由代理逐条对照原文完成。

两套口径相差的三项是：C09不要求唯一的“研究消费者看法”目的；C22、C23中的“会后”是开展时段，不是交付截止期限。后两项沿用v2对开发集的时间规则，在这两例模型输出产生前完成审计。旧标签与首次结果均保留，没有用恢复结果替换首次分数。

## 漏项与结构失败

首次有两例未完整处理，均在上下文跟踪阶段：

- C14：同一线索的更新没有按实际发言顺序排列，程序校验中止。该例应保留“如果能做到，我去了解电视遥控器能否支持录像功能”的条件性工作候选。
- C28：引用短语在同一段中重复，输出未标明出现位置，无法唯一定位原话。该例是历史回顾，本身没有新增任务。

在复制的运行目录中，各按相同配置恢复一次，两个都完成了处理。C28没有任务，符合原文。C14恢复后准确解释出这项条件性工作，也保存为可见待确认需求，但执行规则没有把 conditional 事件放入任务候选，因此候选列表仍漏这一项。应把“是否属于工作候选”与“是否已无条件承接”分开处理。

这7次恢复调用单独保存，首次的28/30完整处理率、17/18任务召回不被改写。

逐条查看M2输出发现，系统在正确更新旧任务、记录产品范围决策之外，还生成了“调整登录改版第一批范围”的任务候选，并把“今天”写入其期限。原12项验收检查只核对持久化和业务状态，没有覆盖这种多余候选；这项已单独记录为语义错误。旧任务M2场景也出现相同表现，状态/日期契约通过不代表整份提取无误。

## 下一步修改顺序

首先处理任务边界：在解释时识别当前分派、产品决策、现场活动、既有安排及历史/引用内容。产品决定可以约束任务，但不应默认再生成一项独立任务。把本轮七个误报和对应的真实工作组成对照，保留正常短回应承接能力。

其次统一候选与待确认需求：已明确动作、对象、负责人，但带条件的工作应能作为候选被找到，同时显示承接条件。C14可以作为入口样例。

然后改善账本结构输出：按发言顺序保存更新；重复引用带位置。分别检验结构恢复与语义结果，保持本轮完整语料作为后续比较基准。
