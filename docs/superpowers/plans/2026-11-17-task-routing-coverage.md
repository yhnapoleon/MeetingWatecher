# 进展分流与条件工作覆盖实施计划

**目标：** 修复无历史任务的进展汇报误入新建卡；验证背景内独立条件工作能否由现有核验和修复流程补回。

**依据：** [离线排查](../../任务边界与条件保留_离线排查.md)及用户在方案后明确要求“开始实施并测试”。本会话直接实施，末尾独立代码复核。

**架构：** 保留 context-v5 当前阶段划分。状态与关系决定报告/新建/更新入口；核验请求增加非工作记录引用范围，复用 coverage_findings 和有界 repair/recheck。Python 3.13、unittest、现有 Service/SQLite/模型客户端。

## 约束与复核重点

- 用户要求只跑必要测试，采用受影响离线测试与最小真实样例，不跑全量60/115例；冻结标签不变。
- 保留旧 run，使用新目录；生产变更前保存明确文件清单快照，本目录无 Git，不创建工作树或提交。
- 不把进度的 set 改成 keep；保留时间证据。既有任务改期和条件候选不得丢失。
- 无可执行操作不等于可新建；未核验状态、未知状态和其他字段变更应保留具体复核/能力限制。
- 被非工作记录引用的原话仍可能有遗漏；同一发言含任务和背景不能因共享证据跳过。
- 真实核验配置保持历史值，复用 GN25 原文、ledger、interpret；额外纯背景反例应保持无任务。
- 总 HTTP 上限6次（含技术重试和 repair/recheck）；不耗尽额度凑测试，付款/额度错误终止。每次保留原始输入、响应、成本与状态。
