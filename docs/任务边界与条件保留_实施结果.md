## 1. GN29：保留进度，不再生成空问题的新任务卡

原始输出 R8 表示交付物完成一半，R23 表示第三方 ontology 工作进度。两条均为 `progress + new`，但携带 `time.change=set`，被旧 report 分支拒绝。后续归并把“没有可执行状态更新”包装成 `can_add_task=true` 的 ambiguous 卡，问题却为空。

修改分为两处：

- `context_new_work.reduce_untracked_report` 接收核验支持、无旧任务关联的 progress/completed 汇报，允许保留明确的时间设置或取消信息，并在 report 中保存完整 time。它不把 set 改成 keep。若还包含其他字段变更，保存报告并明确提示当前无法执行该变更。
- `context_state.reduce_context` 不再仅凭 `relation=new` 放行新建。有事件的确认卡必须同时是核验支持的 `future_work`。未知、未核验或不可执行的状态保留复核问题/能力限制，不能因回退获得新建权限。没有事件的原有潜在需求确认路径不变。

用原始 GN29 的完整 checked 输出，经 Service 正常入口写入独立 SQLite 后验证：

| 检查 | 结果 |
|---|---|
| R8、R23 | 两张错误确认卡消失，转为 progress report，时间字段逐项保留 |
| 原有任务项 | 11 条 items 与历史结果完全一致；末条仍包含两个原子目标 |
| 其他确认卡与更新 | 完全一致 |
| 报告 | 原有 3 条继续保留，共 5 条 |
| Service.pending | E5/E15 的 no_supported_state_change 消失 |
| 保存与恢复 | 重复调用仅提取一次；重开数据库读回一致；无平台账号映射，任务表仍为 0 |

沿用冻结逐目标匹配，只移除已确认的两个 FP：**8TP/5FP/0FN，P=61.5%，R=100%**，此前 P=53.3%。这是固定模型输出的程序归并回放，不是重新跑 GN29 的推理成绩，更不是独立泛化成绩。其他 5 个额外预测、T1 负责人争议、T6 条件丢失仍按原口径保留；R23 的报告描述仍混有展示内容，代码没有替模型重写它。

## 2. GN25：覆盖入口已补齐，模型仍把条件承诺当背景

原文 `qm.Bed011.639` 表示：若大家认为 Grad B 参加 Santa Barbara 会议合适，团队就支付费用。解释 R6 已经描述了这句话，却把整个参会与来访讨论归入 context_only，核验也以“未形成决定或分派”为由认可。

本次在 `context_v5` 的 `coverage_review` 增加 `nonwork_record_evidence`，列出背景、实体、暂缓、撤回及已解决记录所引用的发言。即使同句已被其他工作引用，也继续检查其中是否还有独立动作。核验提示要求先识别动作及条件，再比对工作是否已保留；条件尚未成立与没有作出条件承诺分开判断。遗漏仍进入现有 coverage_findings，未添加额外模型阶段。

用冻结的 GN25 全文、history、tracking 和 interpret 运行任务分支，只重新调用 check。对照 BG01 是本次新写的纯背景负例：介绍会议日期和公布的学生票价，明确尚未讨论参会或资助；它包含 if 条件句，但不构成支付承诺。该反例只能检验局部过提取风险，不能代表自然会议分布。

| 运行 | 核验设置 | GN25 | BG01 | 请求 / token |
|---|---|---|---|---|
| live-r2 | 历史设置：关闭思考，temperature=0，16,384 输出上限 | 2TP/0FP/1FN，仍漏 T3；R6 supported/context_only，coverage=[] | 0 任务项、0 确认卡、0 遗漏 | 2 / 42,397 |
| live-r3-low-check | enabled/low，temperature=1，同样 16,384 上限 | 同上，仍漏 T3 | 同上 | 2 / 52,770 |

已逐字核对两轮 GN25 的完整 messages：系统提示与用户 payload 相同，输出上限相同；只改变接口要求的 thinking、reasoning_effort、temperature。low 轮 GN25 使用 9,967 个 reasoning token，完整返回，没有预算耗尽或技术失败，却仍把原话解释成“条件性费用说明，尚未形成明确工作安排”。两轮都没有产生修复目标，因此 repair/recheck 没有执行。

这组结果不支持“补上覆盖清单就能修复漏项”，也不支持把 low 核验设为默认。当前能确认模型看到了条件句，问题仍在工作资格判断。下一步若继续，需要验证更独立的动作/承诺判断如何避免被整条背景分类带偏；不应继续重复添加相同提示，也不能用程序关键词直接把 if 句变成任务。

当前代码保留这个覆盖入口于可选 context-v5，版号为 16；默认策略仍是 split-v3，默认核验思考配置没有变化。该入口的任务召回收益尚未得到本轮验证。

## 3. 验证、失败记录与代码复核

新增状态分流与请求边界测试在修改前复现失败，修改后通过。最终只运行受影响的 66 项检查，覆盖报告、条件候选、旧任务更新、字段保留、人工确认、v5 请求、wire 引用和实验入口，全部通过。

实验入口的本地初测还发现错误范围使用 fields 而非现有 field 契约，已改为复用生产 `Extractor.evidence_extract`，付款终止错误只阻断 items/updates。独立只读代码复核发现重入时无条件跳过缓存结果会绕过停止状态；已补 terminal_error/waiting_retry/recovery_required 三种缓存反例，先复现再修复为重入同样检查停止状态。这两个问题均在离线验证中发现；真实 4 次请求没有触发它们。
